01Fundamentals

QoS does not create bandwidth. It decides who suffers when there is not enough, and it only does anything at all at a point of congestion.

The four impairments

ImpairmentWhat it isVoice targetCaused by
BandwidthAvailable throughput~80 kbps per G.711 call with overheadLink capacity, contention
Delay (latency)One-way transit time< 150 ms one-way end to endPropagation, serialisation, queuing
JitterVariation in delay< 30 msVariable queue depth
LossPackets discarded< 1%Queue overflow, policing, errors

Of the four, only queuing delay and loss are things QoS can influence. Propagation delay is physics, and serialisation delay is a function of link speed and packet size. If your round trip to the data centre is 180 ms because it is on another continent, no QoS policy will fix it.

The question to ask first"Where is the congestion?" QoS configured on an interface that never fills does nothing but consume CPU and confuse the next engineer. Find the bottleneck — usually a WAN circuit, a sub-line-rate handoff, or an uplink oversubscription ratio — and apply policy there.

The three models

ModelHow it worksStatus
Best EffortNo differentiation. FIFO, tail dropThe default everywhere
IntServPer-flow reservation signalled end to end with RSVPDoes not scale. Survives in MPLS-TE and some voice admission control
DiffServPackets marked into a small number of classes; each hop applies a per-hop behaviourWhat everyone deploys

DiffServ scales because routers hold state per class, not per flow. A core router with a million flows still has six or twelve queues. The trade-off is that there is no end-to-end guarantee — only a consistent treatment at each hop, which is why marking consistency across a network matters so much.

The DiffServ toolkit

  1. Classification — identify which traffic is which.
  2. Marking — write that decision into the packet so later hops need not reclassify.
  3. Policing — enforce a rate by dropping or remarking excess.
  4. Shaping — enforce a rate by buffering excess.
  5. Queuing and scheduling — decide the order packets leave.
  6. Congestion avoidance — drop selectively before the queue is full.
  7. Link efficiency — fragmentation, interleaving, header compression. Mostly historical.

Classify and mark once, as close to the source as possible. Everything else is applied where congestion occurs.

Trust boundary

The point where you begin believing the markings in arriving packets. Inside it, markings are trusted and acted on. Outside it, they are rewritten or cleared.

Put it as close to the edge as you can while still controlling it — normally the access switch port. A PC can set DSCP 46 on its own traffic; if you trust the access port unconditionally, any user can put their file transfer in the voice queue.

! Access port with an IP phone and a PC behind it
interface GigabitEthernet1/0/10
 ! trust the phone, but have the phone re-mark the PC to 0
 auto qos trust device cisco-phone
 ! or explicitly
 trust device cisco-phone
 service-policy input ACCESS-EDGE-IN

Why the WAN handoff is the hard one

The WAN router has a 1 Gbps physical port but the service provider sells a 200 Mbps CIR. The router sees no congestion — it can clock out a gigabit happily — so its queues never build and its QoS policy never engages. The provider polices at 200 Mbps and drops the excess, including voice.

The fix is a shaper on your side at or just below the CIR, which creates artificial congestion the router can then manage with its own queuing policy. This is the single most common QoS requirement on any WAN, and the most commonly missed. It is scenario 05.

Queuing without shaping on a sub-line-rate circuit does nothingIf the physical port is faster than the contracted rate, the router never queues, so LLQ, CBWFQ and WRED are all inert. Shape first, queue inside the shaper.

IPv4 ToS byte · legacy and current interpretations, with EF decoded.

Layer 2 marking

FieldBitsWhereNotes

CoS evaporates on untagged linksCoS lives in the 802.1Q tag. An access port strips the tag, so the marking is gone the moment the frame leaves. Mark with DSCP, which lives in the IP header and survives every layer-2 hop. Use CoS only where you know the link is trunked and the next device reads it.

ECN

The two low-order bits let routers signal congestion by marking rather than dropping. The sender's TCP stack reduces its rate as though it had seen a loss, without the retransmission.

BitsNameMeaning
00Non-ECTEndpoint does not support ECN. Routers must drop instead
10ECT(0)ECN capable
01ECT(1)ECN capable
11CECongestion Experienced — set by a router instead of dropping

Both endpoints must negotiate ECN in the TCP handshake. A router setting CE on a non-ECT packet is a bug; the correct action there is to drop.

04DSCP values and per-hop behaviours

Four PHB families. Learn the AF arithmetic and the rest follows.

The four families

The AF arithmetic

AF is written AFxy where x is the class (1–4, higher is better) and y is the drop precedence (1–3, higher is dropped sooner).

DSCP = 8x + 2y

AF11 = 8(1) + 2(1) = 10
AF23 = 8(2) + 2(3) = 22
AF41 = 8(4) + 2(1) = 34
AF43 = 8(4) + 2(3) = 38

The drop precedence is the pointAll three values in a class share one queue and one bandwidth guarantee. The difference is which gets discarded first when that queue fills, via DSCP-based WRED. Classifying in the core

class-map match-any VOICE

Past the trust boundary, match on DSCP only. It is a single field comparison rather than an ACL walk or deep inspection, and it is the entire point of marking at the edge.

match-all versus match-anymatch-all requires every criterion (AND); match-any requires one (OR). The default is match-all, which silently matches nothing if you list several DSCP values expecting OR behaviour. For a list of DSCP values you almost always want match-any.

NBAR2 and the encryption problem

class-map match-any BUSINESS-APPS

 match protocol attribute traffic-class transactional-data
!
show ip nbar protocol-discovery interface Gi0/1
show ip nbar protocol-pack active

NBAR2 recognises applications by signature rather than port, and groups them by attribute so policy survives new applications appearing. It is genuinely useful at a branch edge.

Encryption has eroded deep inspectionTLS 1.3 with encrypted SNI, QUIC over UDP 443, and VPN tunnels all hide what NBAR used to read. Classification is drifting back toward endpoint marking and metadata — which is another argument for getting the trust boundary and endpoint marking right rather than relying on inspection in the network.

06MQC — Modular QoS CLI

QoS action order · ingress and egress, with what each can do.

The three-step structure

! 1. class-map — what traffic
class-map match-any VOICE
 match dscp ef

! 2. policy-map — what to do with it
policy-map WAN-EGRESS
 class VOICE
  priority percent 10
 class class-default
  fair-queue
  random-detect

! 3. service-policy — where it applies
interface GigabitEthernet0/0
 service-policy output WAN-EGRESS

One input policy and one output policy per interface. Any class not explicitly matched falls into class-default, which always exists whether you configure it or not.

A class with bandwidth percent 20 can use 100% of the link if nothing else wants it. To cap a class always, add an explicit police or shape.

bandwidth percent is a minimum guarantee during congestion, not a cap. Unused capacity is shared among classes that want it, in proportion to their configured weights.

By default IOS reserves 25% of the interface for control traffic and overhead, so configured bandwidth can total only 75%. Override with max-reserved-bandwidth 100 if you are accounting for control traffic in your own classes — which you should be, via a CS6 class.

bandwidth remaining percent

policy-map CHILD
 class VOICE
  priority percent 10
 class TRANSACTIONAL
  bandwidth remaining percent 40
 class class-default
  bandwidth remaining percent 60

Shares out what is left after the priority class has taken its share, rather than a percentage of the whole interface. This is the form to use inside a hierarchical policy, because the child policy does not know the parent shaper's rate — percentages of "the interface" would be meaningless or wrong.

Use remaining percent inside any shaped policyIf the parent shapes to 200 Mbps on a 1 Gbps port, bandwidth percent 25 in the child is ambiguous at best. bandwidth remaining percent is unambiguous and survives a change to the shaper rate without needing recalculation.

Queue limits and the tx-ring

policy-map WAN-EGRESS
 class VOICE
  priority percent 10
  queue-limit 64 packets
 class class-default
  queue-limit 512 packets
!
interface GigabitEthernet0/0
 tx-ring-limit 3

Below the software queues sits the tx-ring, a small hardware FIFO. Packets there are already committed — QoS cannot reorder them. A deep tx-ring therefore adds latency that your priority queue cannot avoid, which is why it is reduced on low-speed links.

Queue depth is a latency-versus-loss trade. A deep queue absorbs bursts but adds delay; a shallow queue drops sooner but keeps latency low. For voice, shallow is right — a voice packet delayed 200 ms is as useless as one dropped, and has consumed buffer in the meantime.

Bufferbloat is a real failure modeOversized buffers on a congested link produce hundreds of milliseconds of queuing delay. Interactive traffic becomes unusable while throughput looks fine and the interface reports no drops. If users report sluggishness with no errors anywhere, measure latency under load, not at rest.

08LLQ and bandwidth allocation

How LLQ works

LLQ adds a strict-priority queue to CBWFQ. Packets in it are served ahead of everything else, giving the lowest possible delay and jitter. To prevent starvation, the priority queue has an implicit policer that engages during congestion.

policy-map WAN-EGRESS
 class VOICE
  priority percent 10
 class VIDEO
  priority percent 23
 class class-default
  fair-queue
Link statePriority class behaviour
Not congestedCan exceed its configured rate. The policer is not enforcing
CongestedPoliced to its configured rate. Excess is dropped
The priority policer drops, it does not queueExceed the priority rate during congestion and those packets are discarded, not delayed. For voice that means choppy audio precisely when the network is busy — the moment you most needed it to work. Size the priority queue for the real call volume plus headroom, and use call admission control to stop more calls being placed than the queue can carry.

Sizing the voice queue

A G.711 call with IP, UDP and RTP headers over Ethernet is roughly 80–90 kbps each way. G.729 is about 26–32 kbps. Multiply by concurrent calls and add headroom.

Example: 200 Mbps WAN CIR, 40 concurrent G.711 calls

  40 calls x 90 kbps = 3.6 Mbps
  Add ~20% headroom   = 4.3 Mbps
  As a percentage     = 4.3 / 200 = ~2.2%

policy-map WAN-CHILD
 class VOICE
  priority percent 4          ! rounded up, with margin

Note how small that is. Voice rarely needs much bandwidth — it needs predictable bandwidth. Allocating 30% to voice because it feels important wastes capacity that other classes could guarantee.

The 33% guideline

Cisco's long-standing recommendation is to keep total priority bandwidth at or below one third of the link. It is a guideline, not an enforced limit, and the reasoning is sound: a large strict-priority allocation means that during congestion the non-priority classes are squeezed into whatever remains, and their guarantees become meaningless.

If your design needs more than 33% in priority, the usual causes are that the link is too small, or that something is in the priority queue that should not be — signalling, or a video class that would be better served by a generous bandwidth guarantee.

Multi-level priority

policy-map WAN-CHILD
 class VOICE
  priority level 1 percent 4
 class TELEPRESENCE
  priority level 2 percent 15
 class class-default
  fair-queue

Level 1 is served before level 2. Useful when two classes both need low latency but one must never be affected by the other — voice ahead of immersive video, typically. Each level keeps its own policer.

09Congestion avoidance: WRED and ECN

The problem with tail drop

When a queue fills, a FIFO drops every arriving packet. Many TCP flows lose packets at the same instant, all back off together, the link empties, then all ramp up together and fill it again. This is global synchronisation, and it produces a sawtooth utilisation pattern that wastes capacity.

RED breaks the synchronisation by dropping a few packets randomly before the queue is full, so a handful of flows back off early and the rest keep running.

WRED parameters

ParameterMeaning
Minimum thresholdAverage queue depth below which nothing is dropped
Maximum thresholdDepth above which everything is dropped — tail drop resumes
Mark probability denominatorAt max threshold, 1 in N packets is dropped. Default 10
Exponential weighting constantHow fast the average queue depth tracks the instantaneous depth. Default 9
 
policy-map WAN-CHILD
 class TRANSACTIONAL
  bandwidth remaining percent 30
  random-detect dscp-based
  random-detect dscp af21 32 40 10
  random-detect dscp af22 28 40 10
  random-detect dscp af23 24 40 10

Read those as: AF23 starts being dropped at an average depth of 24, AF22 at 28, AF21 at 32. All reach full drop at 40. So within one class, the highest drop precedence sheds first — which is the entire reason the AF drop precedences exist.

Where WRED is wrong

Never apply WRED to voice or videoRED works by exploiting TCP's congestion response. UDP voice and video do not back off — dropping their packets degrades quality and reduces nothing. Use tail drop with a shallow queue for real-time classes, and WRED only on TCP-dominated classes.

Also avoid it on classes dominated by small numbers of large flows, where dropping from the few flows present just hurts them without the statistical benefit RED depends on.

ECN instead of dropping

policy-map WAN-CHILD
 class TRANSACTIONAL
  bandwidth remaining percent 30
  random-detect dscp-based
  random-detect ecn

With random-detect ecn, a router that would have dropped an ECN-capable packet instead sets the CE bits and forwards it. The receiver echoes the signal, the sender reduces its window, and no retransmission is needed. Non-ECN-capable packets are still dropped as before.

The benefit is real for long-lived TCP flows across high-latency paths, where a retransmission costs a full round trip. Data-centre deployments use it heavily, with DCTCP.

Modern AQM

RED's weakness is that it is tuned in queue depth, which does not translate to a latency target and needs retuning per link speed. Modern algorithms target delay instead:

  • CoDel — measures how long packets sit in the queue and drops when the minimum delay over an interval stays above target. Self-tuning.
  • FQ-CoDel — CoDel plus per-flow fair queuing. Very effective against bufferbloat.
  • PIE — proportional-integral controller targeting a delay figure. Used in DOCSIS.

Availability varies by platform. Where you have the option on an edge or broadband-facing device, FQ-CoDel usually outperforms hand-tuned WRED for mixed traffic.

10Policing

Policing against shaping · the same six intervals of offered traffic.

Token bucket maths

A policer holds a bucket of tokens. Tokens are added at the CIR, the bucket holds at most Bc bits, and a packet may pass only if enough tokens are present.

Tc = Bc / CIR          ! the interval, in seconds
Bc = CIR x Tc          ! burst size, in bits

Example: CIR 10 Mbps, Tc 10 ms
  Bc = 10,000,000 x 0.010 = 100,000 bits = 12,500 bytes
Bc settingEffect
Too smallBursty TCP is punished. Throughput falls well below the CIR even though average demand fits
Too largeLong bursts pass unchecked, defeating the point and causing downstream congestion
Rule of thumbBc = CIR × 1.5 ÷ 8 bytes is a common default, roughly 1.5 seconds of burst for TCP friendliness
Small Bc wrecks TCP throughputTCP sends in bursts of a full window. A policer with a tight Bc drops mid-burst, TCP halves its window, and measured throughput can sit at a fraction of the policed rate. A customer complaining their 100 Mbps circuit only delivers 30 Mbps on a file transfer is often seeing this. See scenario 04.

The three policer types

TypeParametersColours
Single-rate two-colourCIR, Bcconform, exceed
Single-rate three-colour (srTCM, RFC 2697)CIR, Bc, Beconform, exceed, violate
Two-rate three-colour (trTCM, RFC 2698)CIR, PIR, Bc, Beconform, exceed, violate
 
! Two-colour: pass or drop
police 10000000 conform-action transmit exceed-action drop

! Three-colour, single rate: remark rather than drop the middle band
police cir 10000000 bc 1875000 be 3750000
  conform-action transmit
  exceed-action set-dscp-transmit af22
  violate-action drop

! Two-rate: separate committed and peak rates

  conform-action transmit
  exceed-action set-dscp-transmit af23
  violate-action drop

! Percentage form, adapts to interface speed
police cir percent 20 bc 100 ms be 200 ms
Remark rather than drop where you canMarking exceeding traffic down to a higher drop precedence — AF21 to AF22, say — lets it through when the network is quiet and sheds it first when congested. That is strictly better than dropping it at the policer, and it is what the AF drop precedences were designed for.

Where to police

  • Ingress at the edge — enforce what a customer, VLAN or port may send, and re-mark anything outside contract.
  • On the priority class — LLQ does this implicitly, but an explicit policer on the voice class at the edge stops a misbehaving endpoint flooding EF.
  • Scavenger — cap known-low-value traffic hard.
  • Control plane — CoPP, which is policing applied to traffic destined for the router itself.

11Shaping

Shaping versus policing

 PolicingShaping

The short version: police what arrives, shape what leaves. You police to protect yourself from others; you shape to avoid being policed by others.

Configuration

! Shape to the contracted rate
policy-map WAN-PARENT
 class class-default
  shape average 200000000              ! 200 Mbps
  service-policy WAN-CHILD

! Explicit Bc for a smaller Tc — important for voice
  shape average 200000000 2000000      ! CIR, Bc
! Tc = Bc / CIR = 2,000,000 / 200,000,000 = 10 ms

! Percentage of interface
  shape average percent 20

! Peak shaping — allows Bc + Be per interval. Rarely a good idea
  shape peak 200000000
Default Tc is often 125 ms, which is far too coarse for voiceA shaper releases a burst then pauses until the next interval. With Tc = 125 ms, a voice packet arriving just after a burst waits up to 125 ms before anything else is sent — blowing the jitter budget on its own. Set Bc so that Tc lands around 10 ms on any link carrying real-time traffic.
Target Tc = 10 ms, so Bc = CIR / 100

  200 Mbps circuit:  Bc = 2,000,000 bits
   50 Mbps circuit:  Bc =   500,000 bits
   10 Mbps circuit:  Bc =   100,000 bits

Shaping to what, exactly?

Shape slightly below the contracted rate, not exactly at it. Providers usually police on layer-2 frame size including the Ethernet header, preamble and inter-frame gap, while your shaper may count only the layer-3 payload. Shaping at exactly 200 Mbps can still see the provider police you.

  • Start at roughly 95% of CIR and test.
  • Ask the provider what their policer counts — some platforms let you account for the overhead explicitly.
  • On Ethernet handoffs, shape average ... account user-defined 20 or similar adjusts for the overhead where supported.

Without the parent shaper the child does nothing, because a 1 Gbps interface carrying 200 Mbps never queues. This two-level structure is the single most important QoS pattern on any WAN.

Per-site shaping on a hub

A hub with a 1 Gbps circuit serving fifty branches, each with a 10 Mbps tail. Without per-site shaping the hub can blast 1 Gbps at a 10 Mbps branch, and the provider drops the excess — including the branch's voice.

! Per-branch shaping, selected by destination
class-map match-all BRANCH-01

policy-map HUB-PARENT

  service-policy WAN-CHILD

  shape average 20000000 200000
  service-policy WAN-CHILD

  shape average 50000000
  service-policy LEVEL3-QUEUING
 class VLAN-120
  shape average 30000000
  service-policy LEVEL3-QUEUING
!

  shape average 200000000
  service-policy LEVEL2-VLAN

Port shaper, then per-VLAN shapers, then per-class queuing inside each. Platform support for three levels varies considerably — check before designing around it.

Always use bandwidth remaining percent in a childThe child policy does not know the parent's rate. bandwidth percent 25 in a child under a 200 Mbps shaper on a 1 Gbps port is ambiguous and platform-dependent. bandwidth remaining percent is well defined at every level and survives a shaper-rate change without recalculation.

13Campus switch QoS

Why switches are different

Switch QoS is implemented in hardware with a fixed number of queues per port — commonly expressed as 1P3Q3T or 2P6Q4T, meaning priority queues, normal queues and drop thresholds per queue. You cannot define arbitrary classes; you map DSCP values into the queues the silicon provides.

Older Catalyst platforms use the mls qos model; modern IOS-XE Catalyst uses MQC. Both appear in production, so recognise each.

mls qos srr-queue output dscp-map queue 1 threshold 3 46

Microbursts

A switch port shows 15% average utilisation and yet the counters show output drops. The cause is almost always a microburst: a sub-millisecond spike that exceeds line rate and overflows the egress buffer, invisible to any counter averaged over five minutes or even five seconds.

Classic causes: many-to-one patterns (incast), a 10G source feeding a 1G destination, or synchronised backups.

show interface Te1/1/1 | include output drops|queue
show platform hardware fed switch active qos queue stats interface Te1/1/1
! some platforms expose peak buffer usage
show platform hardware fed switch active qos queue config interface Te1/1/1

Mitigations: increase the buffer allocation for the affected queue, enable a deeper queue-set threshold, reduce the speed mismatch, or spread the sources in time. QoS classes help only if the drops are hitting traffic you care about more than the rest — the burst itself is a buffer problem, not a scheduling one. This is scenario 10.

14WAN and MPLS QoS

The provider boundary

Your DSCP markings mean nothing to the provider unless the contract says otherwise. A typical MPLS service offers three to six classes and publishes a DSCP-to-class mapping. Anything outside it is remapped or ignored, and some providers rewrite DSCP entirely.

  • Get the provider's class map in writing before designing.
  • Mark to their values on egress if they differ from yours, and restore your values on ingress at the far end if needed.
  • Verify with a capture at both ends — do not assume markings survived. This is scenario 02.

MPLS EXP and tunnelling modes

Inside the MPLS core, routers queue on the 3-bit EXP field in the label, not on the customer's DSCP. How EXP and DSCP interact at the edges is set by the tunnelling mode.

ModeOn pushOn popEgress PE queues on
UniformDSCP copied to EXPEXP copied back to DSCPEXP
PipeEXP set by provider policyOriginal DSCP preservedEXP
Short pipeEXP set by provider policyOriginal DSCP preservedCustomer DSCP
Uniform mode lets the provider rewrite your DSCPIf the core re-marks EXP during congestion, uniform mode copies that back into your IP header on the way out. Your AF31 can arrive as something else entirely. Short pipe is usually what an enterprise wants, because the customer marking survives end to end — but it is the provider's choice, so ask.

QoS over VPN and overlays

! Copy the inner DSCP to the tunnel header — usually the default
interface Tunnel0
 tunnel mode gre ip
 ! qos pre-classify lets the policy see the ORIGINAL headers
 qos pre-classify

! IPsec: preserve DSCP into the outer header
crypto ipsec profile PROF
 set security-association ...

qos pre-classify matters whenever you classify on anything other than DSCP. Without it, the service policy on the physical interface sees only the tunnel's outer header — same source, same destination, for every flow — and your ACL-based classification matches nothing. With it, the original inner headers are available to the classifier.

The outer header still needs a usable marking, because transit routers only see that. Most tunnel implementations copy the inner DSCP outward by default; verify rather than assume.

SD-WAN

SD-WAN changes the emphasis rather than the mechanics. Classification, marking, queuing and shaping all still apply per transport. What is added:

  • Application-aware routing — measure loss, latency and jitter per path with BFD probes, and steer classes to whichever transport currently meets an SLA.
  • Per-transport shapers — each underlay has its own contracted rate.
  • Forward error correction and packet duplication for critical classes on lossy paths.

The classes and DSCP values should stay the same as the rest of your network. SD-WAN is a steering layer on top of DiffServ, not a replacement for it.

15Wireless QoS

WMM and access categories

802.11 is a shared, half-duplex medium with contention. WMM (based on 802.11e) gives four access categories, differentiated by how long a station waits before transmitting and how large its random backoff window is — so higher categories win contention more often.

Access categoryUPMaps from
AC_VO — Voice6, 7EF, CS6, CS7
AC_VI — Video4, 5AF41–43, CS4, CS5
AC_BE — Best effort0, 3DF, CS3, AF31–33
AC_BK — Background1, 2CS1, AF11–13

The DSCP-to-UP mapping trap

The naive mapping is wrong for voiceTaking the top three DSCP bits as the UP value maps EF (46, binary 101110) to UP 5 — which is video, not voice. RFC 8325 defines the correct mapping, and modern controllers implement it. On older gear, verify that EF lands in AC_VO and not AC_VI, or your voice shares a category with video and loses the contention advantage you configured it for.
! Catalyst 9800 WLC
wireless profile policy BRANCH-POLICY
 service-policy input platinum-up
 service-policy output platinum
!
! trust the DSCP arriving from the wired side
qos wireless-default-untrust

show wireless profile policy detailed BRANCH-POLICY
show policy-map interface wireless ssid

What actually helps on wireless

QoS marking matters less on Wi-Fi than three other things:

  1. Airtime. A slow client transmitting at a low data rate consumes airtime that every other client loses. Disabling very low data rates often does more for voice quality than any queue tuning.
  2. Channel planning and co-channel interference. Contention you cannot schedule your way out of.
  3. Client density per radio.

Configure WMM correctly, verify the DSCP-to-UP mapping, then spend your effort on RF. The scheduler cannot fix a medium that is busy.

16Design guidance

How many classes?

ModelClassesSuits
4-classVoice (EF), Signalling (CS3), Business (AF21), Best effort (DF)Most enterprises. Start here
8-classAdds video, network control, bulk, scavengerNetworks with real video volume
12-classFull RFC 4594Service providers, very large enterprises

More classes means more to configure consistently on every device and more to get wrong. A well-implemented four-class policy beats a twelve-class policy applied inconsistently — and inconsistency is the normal outcome of complexity. Use the standard DSCP values even in a small model, so expanding later is a configuration change rather than a remarking exercise.

A worked four-class policy

class-map match-any VOICE
 match dscp ef
class-map match-any SIGNALLING
 match dscp cs3 cs6
class-map match-any BUSINESS

!

  priority percent 10
 class SIGNALLING
  bandwidth remaining percent 5

  bandwidth remaining percent 40
  random-detect dscp-based

  bandwidth remaining percent 55
  fair-queue
  random-detect

  shape average 200000000 2000000
  service-policy WAN-CHILD
!
interface GigabitEthernet0/0

Rules worth following

  1. Mark once, at the edge. Everything else matches on DSCP.
  2. Trust boundary at the access port. Never trust an endpoint you do not control.
  3. Signalling is CS3, voice bearer is EF. Not the same class.
  4. Total priority at or below 33%. More than that and your guarantees stop meaning anything.
  5. Shape on any sub-line-rate circuit. Without it the queuing policy is inert.
  6. Tc around 10 ms wherever real-time traffic crosses a shaper.
  7. WRED on TCP classes only. Never on voice or video.
  8. Give class-default at least 25%. Most of your traffic lives there.
  9. Protect the control plane with a CS6 class and CoPP.
  10. Document the DSCP map and treat it as an interface contract between teams.

Measuring, not guessing

Counters tell you about drops. They do not tell you about latency or jitter, which is what users actually experience. For that:

! IP SLA jitter probe matching your voice marking
ip sla 100
 udp-jitter 10.20.1.1 16400 codec g711alaw
 tos 184                                   ! 184 = DSCP 46 << 2
 frequency 60
ip sla schedule 100 life forever start-time now
!
show ip sla statistics 100
show ip sla statistics aggregated 100

Note the tos value: the ToS byte is the DSCP shifted left by two bits, so EF (46) becomes 184. Setting it ensures the probe travels in the same queue as real voice — a probe in the default class measures nothing useful about your voice path.

18Real-world scenarios

Ten incidents on the lab topology, from reported symptom to fix. Work out the cause before expanding the diagnosis.

Voice is choppy, and LLQ is configured correctly
Reported

Users at the branch report choppy audio during business hours. The WAN policy has a priority class for EF and it looks right.

What you see 
R1# show policy-map interface Gi0/0 output class VOICE

       Class-map: VOICE (match-any)
         28491028 packets, 4812910284 bytes
         Match: dscp ef (46)
         Priority: 4% (8000 kbps), burst bytes 200000,
           b/w exceed drops: 1842910

The class is matching, so classification is fine. But the LLQ policer is dropping heavily.

Diagnosis 
! How much voice is actually offered?
R1# show policy-map interface Gi0/0 output class VOICE | include bytes
  28491028 packets, 4812910284 bytes
  30 second offered rate 11482000 bps, drop rate 3410000 bps

! The allocation
  Priority: 4% (8000 kbps)

11.5 Mbps of voice offered into an 8 Mbps priority allocation. The policer drops the difference, and because it drops rather than queues, the loss is spread across every active call.

R1# show call active voice brief | count
Number of lines which match regexp = 147
! sized for 40 calls, carrying 147
Root cause

Call volume grew well past the original design. The priority queue was sized for 40 concurrent calls; the branch now runs 147 at peak.

Fix 
! 147 calls x 90 kbps = 13.2 Mbps, plus headroom = ~16 Mbps
! On a 200 Mbps shaper that is 8%
policy-map WAN-CHILD
 class VOICE
  priority percent 8

And the real fix — stop more calls being placed than the queue can carry:

! Call admission control via CUCM locations, or RSVP-based CAC
! so call 148 gets a busy signal instead of degrading all 147
TakeawayThe LLQ policer drops, it does not delay. Exceeding the priority rate degrades every call at once rather than rejecting one. Always pair a priority queue with call admission control, and re-check the sizing whenever call volumes change. b/w exceed drops climbing is the definitive signal.
DSCP markings arrive at the branch as zero
Reported

The hub marks correctly. The branch sees everything as best effort, so the branch egress policy puts voice in class-default.

What you see 
! At the hub, leaving
HUB# show policy-map interface Gi0/0 output class VOICE
       Class-map: VOICE (match-any)
         28491028 packets   ! marking correctly on the way out

! At the branch, arriving
BRANCH# show policy-map interface Gi0/1 input class VOICE
       Class-map: VOICE (match-any)
         0 packets, 0 bytes
       Class-map: class-default (match-any)
         184291028 packets   ! everything landed here
Diagnosis 
BRANCH# monitor capture CAP interface Gi0/1 in match ipv4 any any
BRANCH# monitor capture CAP start
BRANCH# show monitor capture CAP buffer detail | include DSCP
    Differentiated Services Field: 0x00 (DSCP: CS0, ECN: Not-ECT)
    Differentiated Services Field: 0x00 (DSCP: CS0, ECN: Not-ECT)

Everything arrives at DSCP 0. The provider is clearing the field. Checking the contract confirms it: the service was ordered as a single-class best-effort product, and the provider's PE re-marks all ingress traffic to zero.

Root cause

No QoS class of service purchased on the MPLS circuit. The provider's uniform-mode behaviour copies their EXP marking back into DSCP on egress, and their EXP is 0 for the best-effort product.

Fix — two options 
! A. Buy the CoS product and mark to THEIR values
!    Provider maps: EF -> their RT class, AF31 -> their Business class
policy-map PROVIDER-MAP-OUT
 class VOICE
  set dscp ef
 class BUSINESS
  set dscp af31

! B. If CoS cannot be bought — re-mark at the branch on ingress
!    Classify on the inner addresses/ports instead of DSCP
ip access-list extended VOICE-FROM-HUB
 permit udp 10.10.110.0 0.0.0.255 any range 16384 32767
!
class-map match-all REMARK-VOICE
 match access-group name VOICE-FROM-HUB
policy-map BRANCH-IN
 class REMARK-VOICE
  set dscp ef
!
interface GigabitEthernet0/1
 service-policy input BRANCH-IN

Option B restores the marking locally so the branch LAN treats it correctly, but it cannot help across the provider's network, where the damage already happened.

TakeawayNever assume markings survive a provider. Capture at both ends and compare. Get the DSCP-to-class mapping in the contract, and understand which MPLS tunnelling mode the provider uses — uniform mode means their re-marking propagates into your IP header.
Shaper configured, and latency got worse
Reported

A shaper was added to a 50 Mbps circuit to stop provider drops. Drops stopped, but voice jitter went from 8 ms to 90 ms.

What you see 
R1# show policy-map interface Gi0/0 output | include shape|Bc|queue depth
     shape (average) cir 50000000, bc 6250000, be 6250000
       target shape rate 50000000
       (queue depth/total drops/no-buffer drops) 184/0/0
Diagnosis 
Tc = Bc / CIR
Tc = 6,250,000 / 50,000,000 = 0.125 s = 125 ms

The default Bc produced a 125 ms interval. The shaper releases a burst then pauses for the rest of the interval. A voice packet arriving just after a burst waits up to 125 ms before the next one opens — that single mechanism blows the entire 30 ms jitter budget.

Root cause

Bc left at the platform default. The shaper was correct in rate but far too coarse in time for real-time traffic.

Fix 
! Target Tc = 10 ms, so Bc = CIR / 100
! 50,000,000 / 100 = 500,000 bits

policy-map WAN-PARENT
 class class-default
  shape average 50000000 500000
  service-policy WAN-CHILD
R1# show policy-map interface Gi0/0 output | include shape|queue depth
     shape (average) cir 50000000, bc 500000, be 500000
       (queue depth/total drops/no-buffer drops) 6/0/0

! jitter back to 11 ms
TakeawayA shaper's Bc determines its granularity, and the default is usually 125 ms — fine for bulk data, catastrophic for voice. On any link carrying real-time traffic, set Bc so Tc lands near 10 ms: Bc = CIR / 100. The shaper then releases smaller bursts far more often, and the priority queue can actually do its job.
A 100 Mbps circuit only delivers 30 Mbps on file transfers
Reported

A 100 Mbps policed service. Large file transfers reach only about 30 Mbps. The provider insists the circuit is clean and their counters show no policing.

What you see 
R1# show policy-map interface Gi0/0 input class BULK
       Class-map: BULK (match-any)
         police:
           cir 100000000 bps, bc 12500 bytes
         conformed 1842910 packets, 2841028401 bytes; actions: transmit
         exceeded 481029 packets, 710284018 bytes; actions: drop
Diagnosis 
Bc = 12,500 bytes = 100,000 bits
Tc = Bc / CIR = 100,000 / 100,000,000 = 1 ms

A 1 ms token bucket. TCP sends a full congestion window as a burst — on a high-bandwidth-delay path that can be hundreds of kilobytes arriving back to back. The bucket holds 12.5 KB. Everything past that in each burst is dropped, TCP halves its window, and the achieved rate settles far below the policed rate.

R1# show interface Gi0/0 | include reliability|output drops
! no interface drops — the loss is entirely at the policer
Root cause

Bc far too small for a TCP-dominated workload. The policer enforces the average rate correctly but punishes the burst behaviour TCP depends on.

Fix 
! Allow ~1.5 s of burst, a common TCP-friendly figure
! Bc = CIR x 1.5 / 8 = 100,000,000 x 1.5 / 8 = 18,750,000 bytes
! Many platforms cap this; use the largest supported value

policy-map INGRESS-POLICE
 class BULK
  police cir 100000000 bc 1875000
    conform-action transmit
    exceed-action set-dscp-transmit af12
    violate-action drop

Note the second improvement: exceeding traffic is now re-marked rather than dropped, so it still gets through when the network is quiet and is shed first under congestion.

TakeawayA policer with a small Bc produces throughput far below its configured rate for TCP, while reporting the rate as correct. If a circuit underdelivers on bulk transfers but ping and small flows look fine, check Bc before anything else. Prefer shaping over policing for TCP-heavy traffic, and remark rather than drop where the option exists.
QoS policy is applied and makes no difference at all
Reported

A full LLQ policy on the WAN interface. Voice still degrades under load. The policy is attached and shows no errors.

What you see 
R1# show policy-map interface Gi0/0 output

 Service-policy output: WAN-EGRESS
   Class-map: VOICE (match-any)
     28491028 packets, 4812910284 bytes
     Priority: 10% (100000 kbps), burst bytes 2500000,
       b/w exceed drops: 0
   Class-map: class-default (match-any)
     482910284 packets
       (queue depth/total drops/no-buffer drops) 0/0/0

No drops anywhere, queue depth zero, and yet voice is bad. The policy is not engaging because the router never sees congestion.

Diagnosis 
R1# show interface Gi0/0 | include BW|rate
  MTU 1500 bytes, BW 1000000 Kbit/sec
  30 second output rate 198412000 bits/sec

! Contract with the provider:
!   physical handoff 1 Gbps, committed rate 200 Mbps

The router has a gigabit port and is clocking out 198 Mbps. From its point of view there is no congestion at all, so the queues stay empty and LLQ never has anything to prioritise. The provider polices at 200 Mbps and drops the excess — indiscriminately, including EF.

Root cause

Sub-line-rate circuit with no shaper. The classic. Queuing policy on an interface that never queues does nothing whatsoever.

Fix 
! Parent shaper creates the congestion the child can manage
policy-map WAN-PARENT
 class class-default
  shape average 190000000 1900000     ! 95% of CIR, Tc = 10 ms
  service-policy WAN-EGRESS
!
interface GigabitEthernet0/0
 no service-policy output WAN-EGRESS
 service-policy output WAN-PARENT
R1# show policy-map interface Gi0/0 output | include queue depth|exceed
       (queue depth/total drops/no-buffer drops) 8/1204/0
       b/w exceed drops: 0
! now it is queuing, and the drops are landing in class-default where they belong
TakeawayOn any circuit where the physical port is faster than the contracted rate, you must shape to the contract before any queuing policy means anything. Shape at about 95% of CIR — providers usually police on layer-2 frame size including overhead your shaper may not count. This is the most common QoS design error in existence.
Video quality collapsed after enabling WRED
Reported

WRED was enabled across all classes to reduce tail drop. TCP applications improved. Video conferencing became unwatchable.

What you see 
R1# show policy-map interface Gi0/0 output class VIDEO

       Class-map: VIDEO (match-any)
         Match: dscp af41 af42 af43 cs4
         Queueing
           bandwidth remaining 25%
         Exp-weight-constant: 9 (1/512)
         Mean queue depth: 26 packets
           dscp  Transmitted     Random drop    Tail drop
           af41  2841028/4.1G    184291/284M     0/0
           cs4   481029/710M     38210/58M       0/0
Diagnosis

WRED is randomly discarding video packets. The mechanism depends on TCP responding to loss by reducing its window — video over UDP/RTP does no such thing. The sender keeps transmitting at the same rate, so the drops achieve no congestion relief whatsoever and simply destroy frames.

Worse, video is unusually sensitive: losing part of a reference frame corrupts every frame that depends on it until the next keyframe arrives.

Root cause

WRED applied to a UDP real-time class. Correct for TCP, actively harmful here.

Fix 
policy-map WAN-CHILD
 class VOICE
  priority percent 4
  ! no WRED — tail drop with a shallow queue
  queue-limit 64 packets
 class VIDEO
  bandwidth remaining percent 25
  ! no WRED here either
  queue-limit 128 packets
 class TRANSACTIONAL
  bandwidth remaining percent 30
  random-detect dscp-based          ! TCP — correct place for it
 class class-default
  bandwidth remaining percent 41
  fair-queue
  random-detect                     ! TCP-dominated — fine
TakeawayWRED only works on traffic that responds to loss. Apply it to TCP-dominated classes and never to voice or video. For real-time classes use tail drop with a deliberately shallow queue — a late real-time packet is useless anyway, so dropping it quickly is better than delaying everything behind it.
Enabling QoS on the campus switch took voice down
Reported

mls qos was enabled globally on an access switch during a QoS rollout. All phones on that switch immediately had one-way audio and poor quality.

The class matches nothing after moving to a tunnel

A branch was migrated from direct MPLS to a DMVPN tunnel over broadband. The same QoS policy was applied to the physical interface. Every class shows zero packets except class-default.

The ACL cannot see the original addresses, so nothing matches.

R1# show monitor capture CAP buffer detail | include Src|Dst|Protocol
    Protocol: GRE (47)
    Src: 203.0.113.10, Dst: 198.51.100.20
! every packet looks identical to the classifier
Fix — two options 
! A. qos pre-classify — lets the policy see the ORIGINAL headers
interface Tunnel0
 qos pre-classify

! B. Better: classify on DSCP, which IS copied to the outer header
class-map match-any VOICE
 match dscp ef
class-map match-any BUSINESS
 match dscp af21 af22 af23

Option B is the right long-term answer. Mark at the edge, classify on DSCP everywhere else, and tunnelling becomes a non-issue because the DSCP is copied into the outer header by default.

! Verify the outer header carries the marking
R1# show monitor capture CAP buffer detail | include DSCP
    Differentiated Services Field: 0xb8 (DSCP: EF, ECN: Not-ECT)
TakeawayACL-based classification breaks the moment traffic is encapsulated, because the classifier sees only the outer header. qos pre-classify is the patch; marking at the edge and matching on DSCP is the design. This is another argument for doing classification once, as close to the source as possible.
The child policy's percentages do not add up to what you expected
Reported

A hierarchical policy shapes to 200 Mbps with a child policy allocating percentages. The business class is getting far less than the 30% configured.

What you see 
R1# show run | section policy-map
policy-map WAN-CHILD
 class VOICE
  priority percent 10
 class BUSINESS
  bandwidth percent 30
 class class-default
  bandwidth percent 40
!
policy-map WAN-PARENT
 class class-default
  shape average 200000000
  service-policy WAN-CHILD
R1# show policy-map interface Gi0/0 output class BUSINESS | include bandwidth|drops
           bandwidth 30% (300000 kbps)
           (queue depth/total drops/no-buffer drops) 104/8402910/0

300 Mbps reserved inside a 200 Mbps shaper. The percentages are being taken against the interface rate of 1 Gbps, not the shaper rate.

Diagnosis

Platform behaviour for bandwidth percent inside a shaped parent is inconsistent — some take the parent rate, some the interface rate, and the result is either a nonsensical reservation or a rejected configuration. Here the reservations exceed the actual available rate, so the scheduler cannot honour them and the class starves.

Fix 
policy-map WAN-CHILD
 class VOICE
  priority percent 10
 class BUSINESS
  bandwidth remaining percent 50
 class class-default
  bandwidth remaining percent 50
  fair-queue

bandwidth remaining percent divides up what is left after the priority class takes its share, and is unambiguous at every level of the hierarchy.

R1# show policy-map interface Gi0/0 output class BUSINESS | include bandwidth|drops
           bandwidth remaining 50%
           (queue depth/total drops/no-buffer drops) 12/2104/0
TakeawayInside any shaped parent, use bandwidth remaining percent, never bandwidth percent. The child policy has no reliable knowledge of the parent's rate, and the interpretation varies by platform. The remaining-percent form is well defined everywhere and survives a change to the shaper rate without recalculating every class.
Output drops on a switch port at 12% utilisation
Reported

An access switch uplink reports steadily increasing output drops. Monitoring shows average utilisation around 12%. Users report occasional application timeouts.

What you see 
SW1# show interface TenGigabitEthernet1/1/1 | include rate|drops
  30 second input rate 1842000000 bits/sec
  30 second output rate 1204000000 bits/sec      ! ~12% of 10G
     Total output drops: 4829104

Drops with no sustained congestion. Averaged counters hide what is happening.

Diagnosis 
SW1# show platform hardware fed switch active qos queue stats interface Te1/1/1

 Queue Buffers   Enqueue-TH0  Enqueue-TH1  Enqueue-TH2  Drop-TH0 Drop-TH1 Drop-TH2
   0      0        184291028            0            0         0        0        0
   1      0                0    481029384            0         0        0  4829104
   2      0                0            0            0         0        0        0

All drops in one queue, at the highest threshold. Combined with low average utilisation, this is a microburst: a sub-millisecond spike exceeding line rate that overflows the egress buffer before any averaging window notices.

! What is bursting?
SW1# show interface Te1/1/1 counters | include broadcast|multicast

! Correlate with the application — here, 40 servers backing up
! simultaneously to one target through this uplink: classic incast
Root cause

Many-to-one incast. Forty 1 Gbps sources briefly converging on one 10 Gbps uplink produce instantaneous demand far above 10 Gbps, and the buffer cannot absorb it.

Fix — in order of effectiveness 
! 1. Give the affected queue more buffer
interface TenGigabitEthernet1/1/1
 service-policy output UPLINK-OUT
!
policy-map UPLINK-OUT
 class BULK
  bandwidth remaining percent 20
  queue-limit 2048 packets          ! deeper buffer for bursty bulk
 class VOICE
  priority level 1
  queue-limit 64 packets            ! keep real-time shallow

! 2. Separate the bursty traffic so it cannot hurt others
class-map match-any BULK
 match dscp af11 af12 af13 cs1

! 3. Stagger the backups — the actual root cause
TakeawayOutput drops at low average utilisation are microbursts, and no five-minute counter will ever show them. Look at per-queue hardware statistics, and correlate with what the application is doing. The buffer is the constraint, not the scheduler — so QoS classes help only by isolating the bursty traffic from traffic you care about. The real fix is usually in the application's timing.
