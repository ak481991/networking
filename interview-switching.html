01Frame forwarding

The opening calibration questions. They look trivial, which is exactly why a precise answer about table population, flooding behaviour and what happens when a table fills buys credit for everything that follows.

Walk me through what a switch does with a frame, from arrival to transmission.Core

It learns the source MAC against the ingress port and VLAN, then looks up the destination. A known unicast is forwarded out the single port in the table. An unknown unicast, a broadcast or a multicast with no snooping entry is flooded to every other port in that VLAN.

Detail
  1. Receive and validate. FCS is checked. A corrupt frame is counted as a CRC error and discarded — it is never forwarded, which is why CRC errors on one port do not propagate but do indicate a physical problem.
  2. Determine the VLAN. From the 802.1Q tag on a trunk, or from the access VLAN configured on the port. Everything after this is per-VLAN.
  3. Learn the source. The source MAC is inserted or refreshed against (port, VLAN) with an age timer, 300 seconds by default.
  4. Look up the destination in the MAC address table for that VLAN.
  5. Forward or flood. Hit → out that one port. Miss, or broadcast, or unregistered multicast → flood to all other ports in the VLAN that are in an STP forwarding state.
  6. Tag or untag on egress according to the outgoing port's configuration, and transmit.

Two details worth volunteering because they show precision:

  • The table is keyed on MAC and VLAN, not MAC alone. The same MAC can legitimately appear in several VLANs, which is normal for a router subinterface or a firewall.
  • Learning and forwarding are independent. A switch learns from a frame it then floods. That is how the return frame finds its way back as a known unicast, and why the first frame of any conversation floods and the second does not.

What happens when the MAC address table fills up?Deep

The switch cannot learn new addresses, so traffic to any destination not already in the table is flooded to every port in the VLAN. The switch keeps working — it degrades into a hub for unknown destinations, with the bandwidth and security consequences that implies.

Detail

This is the mechanism behind MAC flooding as an attack: an attacker generates frames from thousands of random source addresses, fills the table, and the switch starts flooding real traffic to the attacker's port where it can be captured. The switch reports no error, because from its point of view it is behaving correctly.

What is the difference between the MAC address table and TCAM, and why does TCAM matter?Deep

The MAC address table is exact-match lookup — usually a hash table in dedicated memory. TCAM is content-addressable memory that supports wildcards, so it can match a pattern with "don't care" bits in a single clock cycle. That is what makes line-rate ACL, QoS and longest-prefix matching possible, and it is a finite, shared resource.

Detail
MAC tableTCAM
Match typeExactTernary — 0, 1, or don't care

Why it matters operationally: TCAM is shared between features and carved by the SDM template. A switch with large ACLs, TrustSec policy and many routes can run out, and the failure modes are the dangerous kind:

  • Silent non-programming. The ACL is in the configuration, accepted without error, and not in hardware. Traffic is not filtered. From the CLI everything looks correct.
  • Punt to CPU. Some platforms fall back to software for unprogrammed entries, so the feature works and the CPU spikes and throughput collapses.
  • Capture and SPAN filters failing, because they need TCAM too — which is why a capture filter that behaves impossibly is often a resource problem rather than a syntax problem.

What is unknown unicast flooding, why does it become a problem, and how do you control it?Expert

A frame to a destination not in the MAC table is flooded to every port in the VLAN. In normal operation that is a brief, self-correcting event. It becomes a problem when something causes it continuously — asymmetric paths, aging mismatches, or a silent host — at which point every port in the VLAN carries traffic intended for one of them.

Detail

The mechanisms that make flooding persistent are the content of this question:

  • Asymmetric routing with a firewall or load balancer. Traffic to the server arrives via one path, the reply leaves by another, so the switch never learns the server's MAC from a frame in the direction it needs. Every packet to that server floods, forever. This is the classic case, and in a datacentre it can be gigabits of flooding.
  • MAC aging shorter than ARP aging. The MAC entry expires while the host's ARP entry for the gateway is still valid, so the host sends without triggering any frame that would refresh the switch's table. Default ARP timeout is 4 hours and MAC aging 5 minutes, which is the wrong way round — and it works only because normal hosts send something within five minutes.
  • Genuinely silent hosts. A device that only ever receives — some printers, monitoring taps, licence dongles — never populates the table, so all traffic to it floods.
  • Topology changes flushing tables, which is normal and transient, and the reason TCN handling matters.

The timer-alignment answerWhere asymmetric traffic is by design — a firewall sandwich, a one-armed load balancer — the robust fix is to make MAC aging longer than ARP aging, or shorten ARP so the host re-ARPs and refreshes the switch's table. Lengthening MAC aging keeps the entry alive through the quiet period; shortening ARP timeout generates the frames that refresh it. Either removes the flooding without changing the traffic design, and choosing between them is a real design conversation rather than a configuration lookup.
Follow-ups to expect
  • "How is this different from a broadcast storm?" — a storm is traffic multiplying, usually in a loop. Unknown unicast flooding does not multiply; one frame goes to many ports. Both consume bandwidth, only one grows without bound, and the remedies differ.
  • "Where would you use switchport block unicast?" — on ports where flooded traffic is never legitimate: a port-channel to a known single device, a server port, a port facing a security boundary. Not on uplinks, where it would break normal forwarding.
What they're testingWhether you have diagnosed persistent flooding, which is a genuinely confusing symptom — traffic appearing on ports it has no business being on, with no loop and no error. The asymmetric-path and aging-mismatch explanations are what distinguishes experience from theory here.

02ARP & host services

Where layer 2 meets the host. The two reliable discriminators are keeping the ARP table and the MAC table separate in your head, and knowing what decides which subnet a DHCP client lands in.

What is the difference between the ARP table and the MAC address table? How do they interact?Core

They answer different questions. The ARP table maps an IP address to a MAC address and lives on anything doing layer 3. The MAC address table maps a MAC address to a port and lives on the switch. A frame needs both answers: ARP to find out who to address it to, and the MAC table to find out where to send it.

Detail

MapsIP → MACMAC + VLAN → port

The sequence for host A sending to host B on the same subnet: A checks its own ARP table, broadcasts an ARP request if there is no entry, the switch floods that broadcast and learns A's MAC from it, B replies unicast, the switch learns B's MAC from the reply, and A now has the mapping. Two tables populated by one exchange.

The two-step host hunt is worth saying out loud"Find the host" is ARP for the MAC, then MAC table for the port, and on a multi-switch path you repeat the second step hop by hop following the uplink. Candidates who try to find a host from the ARP table alone get an address and no location; candidates who try the MAC table alone need the MAC they do not have. Naming it as a two-table lookup is a small thing that demonstrates you have actually traced a host on a campus.
What they're testingWhether you keep the two tables distinct. Candidates who conflate them struggle with the next question, because the mismatch between their lifetimes only makes sense if you know they are separate.
How does ARP affect how large you make a VLAN?Deep

Every ARP request is a broadcast that every host in the VLAN must receive and process, whether or not it is the target. So ARP load scales with the number of hosts times how often they resolve, and on a large flat VLAN it becomes a measurable tax on every endpoint — which is one of the two main reasons to keep broadcast domains small.

Detail

The arithmetic to reason about out loud: n hosts each resolving a handful of addresses produces n times that many broadcasts, and each one is processed by all n hosts. The work is proportional to n squared, which is why a /24 is unremarkable and a /16 flat VLAN is a problem. Add gratuitous ARP from failovers and VM moves, plus the occasional scan sweeping the subnet, and the baseline broadcast rate grows faster than the host count.

What they're testingWhether you can justify small broadcast domains quantitatively rather than by convention. The n-squared framing and the ARP-scan consequence are the two points that make the argument concrete.
Clients in a VLAN are getting addresses from the wrong subnet. The relay is configured. Why?Deep

Because the DHCP server chooses the scope from the giaddr field, and giaddr is set to the primary address of the interface that received the broadcast. If the SVI has secondary addresses, or if the relay source has been set to a loopback, clients get addresses from whichever subnet that address belongs to — not from the one you intended.

Detail

The relay's job is small and consequential: receive the client's broadcast, write its own receiving-interface address into giaddr, and unicast the packet to the server. The server then matches giaddr against its configured scopes. So giaddr is the entire mechanism by which a server knows which subnet a client is on, and anything that changes it changes the allocation.

How does IPv6 neighbour discovery change the layer 2 picture?Deep

It replaces broadcast with multicast. An IPv6 host joins a solicited-node multicast group derived from the low 24 bits of its address, and neighbour solicitations are sent to that group — so instead of interrupting every host on the segment, a resolution typically interrupts one. The cost is that the switch now needs MLD snooping to keep that efficiency, and that a host legitimately has several addresses and therefore several groups.

Follow-ups to expect

03VLANs & trunking

The native VLAN is the single most productive question in this area, because it leads to tag format, VLAN leaking and the double-tagging attack in one thread. VTP is usually asked to see whether you will recommend it.

Describe the 802.1Q tag. What is the native VLAN and why does a mismatch matter?Core

The tag is four bytes inserted after the source MAC: a two-byte TPID of 0x8100, then a two-byte control field containing three bits of priority, one drop-eligible bit, and a twelve-bit VLAN ID. The native VLAN is the one VLAN carried untagged on a trunk, and a mismatch causes traffic to silently cross between two different VLANs.

Detail
802.1Q tag, 4 bytes
FieldBitsPurpose
TPID160x8100 marks the frame as tagged
PCP3Priority, 0–7 — this is layer 2 CoS

The tag pushes the maximum frame to 1522 bytes, which is why "baby giant" support exists and why QinQ needs another four on top of that.

Native VLAN mismatch is the interesting part. If switch A has native VLAN 1 and switch B has native VLAN 99 on the same trunk, then A sends VLAN 1 traffic untagged and B receives untagged traffic and places it in VLAN 99. Two VLANs are now bridged together in one direction. Consequences:

  • Hosts in two separate broadcast domains can reach each other — a security boundary has disappeared.
  • STP sees inconsistent topology information. CDP logs a native VLAN mismatch, which is usually how it is found.
  • It can create a loop between VLANs that each individually have a loop-free topology.

The double-tagging attack follows directly from thisAn attacker on an access port whose VLAN happens to be the trunk's native VLAN sends a frame with two tags. The first switch sees the outer tag matching the native VLAN, strips it, and forwards the frame onto the trunk still carrying the inner tag — which the next switch honours, delivering the frame into a VLAN the attacker has no access to. The mitigations are all the same discipline: never use the native VLAN on access ports, set the native VLAN to an unused ID, and prefer vlan dot1q tag native so nothing is untagged at all. Volunteering this unprompted is what turns a basic question into a good answer.
What they're testingWhether the native VLAN is something you reason about or something you leave at default. The leaking consequence and the double-tagging attack are both graded as bonus, and both come from the same one-sentence understanding.

How does an IP phone end up in the voice VLAN, and why is that port not a trunk?Deep

How does a switch decide which port is the root port and which are designated? Give the comparison in order.Core

Four comparisons, in strict order: lowest root path cost, then lowest sender bridge ID, then lowest sender port ID, then lowest receiving port ID. The first comparison that differs decides it, and the order is what the question is really asking for.

Detail
  1. Lowest cost to the root. The sum of the costs of the links along the path.
  2. Lowest sender bridge ID. If two paths cost the same, prefer the one through the lower-numbered neighbour.
  3. Lowest sender port ID. Two links to the same neighbour at the same cost — prefer the one from their lower port.
  4. Lowest receiving port ID. The final local tiebreaker.

What specifically makes RSTP converge in under a second?Deep

Four mechanisms: the proposal/agreement handshake on point-to-point links, edge ports going straight to forwarding, BPDUs acting as keepalives so three missed hellos age a neighbour out in six seconds instead of twenty, and every switch originating its own BPDUs rather than relaying the root's.

Detail
  1. Proposal and agreement. On a point-to-point link, a switch wanting to make a port designated-forwarding sends a BPDU with the proposal bit set. The neighbour blocks its other non-edge ports — the sync operation — and replies with the agreement bit. The port transitions to forwarding immediately. Loop freedom is guaranteed by the sync rather than by waiting out a timer.
  2. Edge ports. A port declared edge (PortFast) transitions straight to forwarding with no delay and generates no topology change when it flaps. On a campus with thousands of access ports this is most of the practical benefit.
  3. BPDUs as keepalives. Every switch sends BPDUs every hello interval. Three missed hellos — six seconds — and the information is aged out immediately, rather than waiting max age. Indirect failures are detected far faster.
  4. Every switch originates BPDUs. In 802.1D only the root generated them and others relayed, so information propagated slowly and a switch had little independent knowledge. In RSTP each switch originates, which is what makes the keepalive behaviour and the handshake possible.

Link type matters and is the thing to watch: the proposal/agreement handshake works only on point-to-point links. A port RSTP believes is shared falls back to timer-based 802.1D behaviour, which is why a half-duplex or hub-connected port destroys convergence for that segment.

Explain MST. What defines a region, and what happens when regions do not match?Deep

MST maps many VLANs onto a few spanning-tree instances, so a thousand VLANs can share two instances instead of running a thousand state machines. A region is defined by three things that must match exactly on every member: the region name, the revision number, and the VLAN-to-instance mapping. If any differ, the switches are in different regions and treat each other as boundaries.

Detail
  • Instance 0 is the IST — the internal spanning tree. It carries the information exchanged with the outside world, and every VLAN not explicitly mapped elsewhere belongs to it.
  • To the outside, the whole region looks like a single virtual bridge. External switches see one bridge ID, which is what lets MST interoperate with other STP flavours at the boundary.
  • The typical design is two instances for a campus: odd VLANs to instance 1 with the root on one distribution switch, even VLANs to instance 2 with the root on the other. That achieves per-VLAN load sharing across uplinks with two state machines instead of hundreds.
  • The mapping is what matters, not the instance count — a region with the right name and revision but one VLAN mapped differently is a different region.

You are connecting an MST region to a switch running Rapid PVST+. What happens?Expert

Root guard versus loop guard is the reliable discriminator, because the two are easy to confuse and protect against opposite conditions. The storm question is asked to find out what you do under pressure.

What do PortFast, BPDU guard and BPDU filter do? Which is dangerous?Core

PortFast moves an access port straight to forwarding and stops it generating topology changes. BPDU guard err-disables the port if a BPDU arrives, which is how you stop someone plugging a switch into a user port. BPDU filter is the dangerous one — applied at interface level it stops sending and ignores received BPDUs, which disables spanning tree on that port entirely.

The global form is conditional and self-protecting — it only suppresses BPDUs on PortFast ports, and the moment one is received the port loses PortFast status and resumes normal STP operation.

Root guard versus loop guard. What does each protect against, and where do you put them?Deep

Root guard reacts to a superior BPDU — it blocks the port rather than allow an unexpected switch to become root. Loop guard reacts to the absence of BPDUs on a port that should be receiving them — it blocks rather than let the port transition to forwarding and create a loop. Opposite triggers, opposite placements.

Why loop guard exists: a blocking port stays blocking only while it keeps hearing better BPDUs. What is UDLD, what is the difference between normal and aggressive mode, and what does it catch that STP does not?Deep

UDLD echoes its own device and port identity to the neighbour and expects to see itself echoed back, which proves the link works in both directions. It catches a unidirectional failure — a broken fibre strand, a dead transmitter, a miswired patch — where the interface stays up and traffic flows one way only. Normal mode detects and reports; aggressive mode err-disables the port.

A campus is down with what looks like a broadcast storm. What do you do in the first two minutes?Expert

Stop the loop before diagnosing it. Get console or out-of-band access, find the two ports the switch is reporting MAC flaps between, and shut one of them. Service comes back, the evidence is still there, and then you investigate. Trying to understand the topology while the CPU is saturated and the switches are unreachable wastes the outage.

The first two minutes
  1. Get out-of-band access. A switch in a storm may not respond to SSH at all, because the CPU is consumed processing broadcast. Console or a terminal server is what you need, and if you do not have it, that is the lesson from this incident.
  2. Read the logs for the loop boundary. show logging | include MACFLAP names two ports. That is the loop, handed to you.
  3. Shut one of them. One command, service restored. Prefer the one that is clearly the anomaly — a port that recently changed, an access port rather than a designed uplink.
  4. Confirm recovery. CPU falling, broadcast rate falling, management reachable again.
  5. Only now diagnose. With the port shut, the state is preserved and you have time.

Because member selection is a hash of chosen header fields, not a measurement of load. A single flow always takes one member and cannot exceed its bandwidth.

How does spanning tree see an EtherChannel, and what are the consequences?Expert

As a single logical port with a single cost and a single state. That is the main benefit — parallel links with no blocking, and no reconvergence when a member fails. It also means STP cannot protect you from a problem inside the bundle, and that member changes can alter the bundle's cost and therefore the topology.

Detail

Consequences worth naming:

  • No blocked redundant path. Two links between switches as a bundle give you both; as independent links, STP blocks one. This is the reason to bundle.
  • Member failure is not a topology change. The bundle stays up, STP sees nothing, no TCN, no MAC flush. Convergence is sub-second and local.
  • But the cost can change. With the long path-cost method, the bundle's cost is derived from the aggregate bandwidth, so losing a member can raise the cost enough to make another path preferable — triggering a real reconvergence from what should have been a non-event. On platforms where the cost is derived this way, that is a genuine design consideration for bundles that are close to a cost tie with an alternate path.
  • STP cannot see inside. If members are miswired — one going to a different switch — the bundle may still form and STP will treat it as one port. This is what misconfiguration guard and LACP's own verification are for.

  • "Does a bundle help or hurt convergence?" — helps substantially, because member failure is handled locally by the bundle rather than by spanning tree. It is the single most effective way to remove STP events from a campus, and that is a stronger argument for bundling than the bandwidth.
  • "What about a bundle across a vPC or stack?" — then a whole switch can fail without a topology change, which is the real goal. The bundle hides member and chassis failures from STP, and that is why multi-chassis aggregation exists.
What they're testingWhether you see bundling as a convergence tool rather than only a bandwidth tool. The cost-change-on-member-failure subtlety is the expert detail and very few candidates raise it.

Why is preempt delay important? What goes wrong without it?Deep

A router that has just booted or just had its uplink restored can win the HSRP election within seconds — before its routing protocols have converged and its forwarding table is populated. It becomes the active gateway and black-holes traffic until the IGP or BGP finishes. Preempt delay holds it in standby until it is actually able to forward.

Detail

The sequence without a delay:

  1. Distribution switch reloads after a maintenance window.
  2. SVIs come up in a few seconds. HSRP hellos start.
  3. It has the higher configured priority, so it preempts and becomes active almost immediately.
  4. Hosts ARP for the gateway and get this router's virtual MAC. All traffic now goes to it.
  5. Its OSPF or BGP adjacencies are still forming and its routing table is nearly empty, so it drops almost everything.
  6. Thirty to ninety seconds of outage, caused by the recovery, not by the original failure.

This is a self-inflicted outage during planned maintenance, which makes it particularly memorable for everyone involved.

08Multicast at layer 2

Multicast is where a switch's default behaviour is to flood, and every mechanism here exists to narrow that. The questions that discriminate are querier placement, why fast-leave is sometimes unsafe, and what PIM snooping does that IGMP snooping cannot.

How does a switch forward multicast by default, and what does IGMP snooping change?Core

By default it floods, because a multicast destination MAC is never a source address and therefore never appears in the MAC table — so every multicast frame is an unknown destination and goes out every port in the VLAN. IGMP snooping has the switch listen to the IGMP conversation between hosts and routers and build a per-VLAN, per-group list of which ports actually asked for the traffic.

Detail

The key insight is that multicast MAC addresses cannot be learned. A switch populates its MAC table from source addresses, and no host ever sources a frame from a multicast address — so there is no learning mechanism and flooding is the only safe default. Snooping replaces that default with inference: if a host sent a membership report for a group on a port, that port wants the group.

Where should the IGMP querier be, and what happens in a VLAN with no layer 3 device?Deep

The querier is normally the layer 3 gateway for the VLAN, because queries are what keep membership alive. In a VLAN with no SVI anywhere — a stretched layer 2 segment whose gateway lives elsewhere, or a pure layer 2 VLAN — nobody sends queries, the snooping entries age out, and the switch reverts to flooding. The fix is a snooping querier configured on a switch.

Detail

The dependency chain: hosts only send membership reports in response to queries (plus an unsolicited report when they first join). Snooping entries age based on not having seen a report. So no queries means no reports, which means the entries expire, which means flooding resumes — and flooding is the safe default, so nothing logs an error.

What does PIM snooping do that IGMP snooping cannot?Expert

IGMP snooping constrains multicast toward hosts, by listening to their membership reports. On a segment shared by several multicast routers, the routers signal interest with PIM joins rather than IGMP reports — so IGMP snooping has nothing to learn from, treats every router port as an mrouter port, and floods every group to every router. PIM snooping listens to PIM join and prune messages and constrains the traffic to the routers that actually asked.

Detail

The scenario: a transit VLAN in a core with four PIM routers on it. Router A is the only one with receivers for group 239.1.1.1 downstream, so it sends a PIM join toward the source. Without PIM snooping, the switch sees PIM hellos from all four routers, marks all four ports as mrouter ports, and floods the group's traffic to all of them — so three routers receive a high-rate stream they have no use for, and discard it after consuming the bandwidth on the way in.

An SVI is down even though the VLAN exists and is not shut down. Why?Deep

Autostate. An SVI is only brought up when at least one port in that VLAN is up and in a spanning-tree forwarding state. If every access port in the VLAN is down and the VLAN is not carried on any up trunk, the SVI goes down regardless of its own configuration.

Detail

The conditions for an SVI to be up:

  • The VLAN exists in the VLAN database.
  • The VLAN is not shut down.
  • The SVI itself is not administratively down.
  • At least one port in the VLAN is up and STP-forwarding — an access port, or a trunk that permits the VLAN.

The purpose is sensible: an SVI for a VLAN with nothing in it should not advertise a connected route or attract traffic. It becomes confusing when the only member is a trunk whose allowed list was changed, or when a VLAN exists on a distribution switch purely for routing and the access switches are all down.

  • "Why does this matter for routing?" — an SVI going down withdraws its connected route and any dependent static or redistributed routes, and brings down any routing adjacency or FHRP group on it.   • "Would you ever turn autostate off?" — rarely. A legitimate case is a VLAN that must keep its SVI and its route up for a service that is temporarily down, such as during a migration. Turning it off globally means SVIs for empty VLANs stay up and keep attracting traffic, which is a worse default.
What they're testingWhether you know the STP-forwarding requirement, not just the port-up requirement. It is a precise piece of knowledge and the symptom — an SVI down for no apparent reason — is a real support call.

Make the case for routed access. What do you give up?Deep

Routed access puts layer 3 on the access switch, so the links to distribution are routed point-to-point. Spanning tree and FHRP disappear between the layers, each access switch becomes its own failure domain, and convergence is handled by the IGP in sub-second time. What you give up is the ability to span a VLAN across access switches.

What you gain
  • No spanning tree between access and distribution. No blocked uplinks, no TCNs propagating, no loop risk in the uplink path, and both uplinks carry traffic via ECMP.
  • No FHRP. The access switch is the default gateway. No election, no preempt, no tracking, no alignment with an STP root.
  • A small failure domain. A broadcast storm or a layer 2 problem is contained to one access switch instead of spreading through a VLAN that spans the floor.
  • Deterministic, fast convergence. An IGP with tuned timers or BFD converges in well under a second, consistently, and is far easier to reason about than STP plus FHRP plus tracking interacting.
  • Simpler troubleshooting. One protocol decides the path.
What you give up
  • VLANs cannot span access switches. This is the real constraint. Any application requiring two hosts on different switches to be layer 2 adjacent — some clustering, some legacy appliances, some storage — will not work.
  • More IP addressing and more routing configuration per access switch, which argues for templating and automation.
  • Route and TCAM capacity on access hardware, which means choosing the right SDM template and verifying the platform can hold the routes.
  • Wireless and mobility designs that assumed a stretched VLAN need rethinking — usually solved by tunnelling to a controller or by a fabric overlay.

A layer 3 switch is forwarding at line rate, then an ACL is applied and throughput collapses. What happened?Expert

The ACL could not be programmed into hardware, so matching traffic is being punted to the CPU and forwarded in software. The CPU cannot forward at line rate, so throughput drops to a fraction and CPU utilisation goes to the ceiling — while the ACL appears correctly configured and is working.

Detail

Three mechanisms produce this, and they need distinguishing:

  • TCAM exhaustion. The ACL needs more entries than remain. Depending on the platform it is either not programmed at all — so traffic passes unfiltered — or programmed partially with the remainder punted. Both are bad and they fail in opposite directions, which is why you must check rather than assume.
  • An unsupported match condition. Some ACE constructs cannot be expressed in hardware on a given platform — certain TCP flag combinations, logging, non-contiguous masks, or time ranges. Any ACE with log in particular typically forces punting, which is why logging on a high-rate ACL is a self-inflicted outage.
  • Feature interaction. The ACL combined with another TCAM consumer — QoS classification, TrustSec policy, a SPAN filter, policy-based routing — exceeds the carve for that region, and the SDM template needs changing.

What they're testingWhether you understand a switch as hardware with finite resources, and whether the software-versus-hardware state distinction is instinctive. The log keyword detail is specific and practical, and it is the kind of answer that ends an interview section well.

Design questions, where the interviewer wants assumptions stated out loud and trade-offs named. There is no single right answer to any of these, and candidates who give one without asking about constraints lose marks for it.

When do you need a three-tier design rather than a collapsed core?Core

When you have enough distribution blocks that interconnecting them directly becomes unmanageable. With two or three blocks, a mesh between distribution pairs is fine and a dedicated core adds cost and latency for nothing. Past that, the link count grows quadratically and a core layer turns it back into a star.

Other reasons a core earns its place, beyond link count:

  • A stable, simple layer to add blocks against. New buildings connect to the core without touching any existing distribution block. That operational property is often worth more than the topology argument.
  • Separation of concerns. The core does fast layer 3 forwarding and nothing else — no policy, no ACLs, no services. Changes happen at distribution, so the core is stable for years.
  • Deterministic hop count. Every block is two hops from every other, so latency is predictable.
  • Physical reality. Multiple buildings with fibre converging at one point mean a core exists physically whether or not you call it one.
Say the questions you would ask firstHow many buildings and wiring closets, how many users, where does the WAN and internet edge attach, where do data-centre and services connect, what is the growth plan, and is this greenfield or an evolution of something existing. What they're testingWhether you size the design to the problem. The quadratic link-count argument is the quantitative justification; the "stable layer to grow against" point is the operational one, and mentioning both is better than either alone.
What is a failure domain in a campus, and how do you keep them small?Deep

A failure domain is the set of things that break together. In a campus the dominant one is the layer 2 broadcast domain, because a loop, a storm or a rogue DHCP server affects everything in it. Keeping them small means not stretching VLANs, pushing the layer 3 boundary toward the access layer, and not merging failure domains with features that look convenient.

The practical rules that follow:

  • Do not stretch VLANs between access switches unless an application requires it, and then do it deliberately and document why. A VLAN spanning a floor turns one switch's problem into everyone's.
  • Push the layer 3 boundary down. Routed access makes each access switch its own layer 2 domain, which is the single most effective containment measure available.
  • Be deliberate about stacking. A stack is operationally one device; a software upgrade or a control-plane fault affects all members.
  • Check physical correlation. Two "redundant" distribution switches in the same rack on the same circuit are one power failure domain, however good the logical design is.
  • Size for the degraded case. If one of two distribution switches carries everything during a failure, it must have the capacity, not half of it.
The question to ask about any redundancy claim"What fails together?" A vPC pair shares a peer-link. A stack shares a control plane and a software image. Two uplinks may share a riser or a conduit. Two power supplies may share a PDU. Redundancy that is only logical is the most common gap in otherwise good designs, and asking that one question out loud is the strongest thing you can do in a design interview.
Follow-ups to expect
  • "How big should a VLAN be?" — refuse a number and give the reasoning: small enough that a broadcast storm in it is survivable and that ARP and broadcast overhead are negligible, which in practice means a /24 or smaller per access switch or closet. The limiting factor is blast radius, not address space.
  • "What about a management VLAN spanning the campus?" — a common and defensible exception, kept small, with no user ports, filtered, and ideally replaced by out-of-band management so it is not a shared failure domain with production at all.
What they're testingWhether you think in blast radius. "What fails together" is the question that distinguishes design thinking, and the physical-correlation point catches people who have only ever drawn logical diagrams.
Compare stacking, StackWise Virtual and independent switches. What are the failure modes?Deep

Stacking merges several access switches into one logical switch with one control plane. StackWise Virtual does the same for two larger chassis. Both buy operational simplicity — one configuration, cross-member bundling, no spanning tree inside — and both create a shared control plane, which means a software fault or an upgrade affects everything in it.

  • Stack split. The stack ring breaks in two places, producing two stacks that each believe they are the whole — with the same configuration, the same management IP and the same SVIs. Duplicate addresses and unpredictable forwarding follow.
  • Active member failure. The standby takes over; with SSO on capable platforms this is near-hitless, and on older stacks it is a brief disruption.
  • Dual-active in StackWise Virtual. The SVL link fails while both chassis are healthy, so both become active. Dual-active detection — fast hello on a dedicated link, enhanced PAgP via a shared neighbour, or BFD — detects it and puts one chassis into recovery mode, shutting its interfaces.

  • Correlated software fault. One control plane means one bug can take out every member, which is the argument against stacking for anything that must not fail as a unit.

Where should the layer 2 to layer 3 boundary be?Deep

As close to the access layer as the applications allow. At distribution is the classic position and requires spanning tree and FHRP; at the access layer gives you routed access with neither; and in a fabric design there is effectively no boundary, because layer 2 adjacency becomes an overlay service on a routed network.

Follow-ups to expect
  • "What about wireless?" — with central switching, client traffic is tunnelled in CAPWAP to the controller, so the client VLAN exists where the controller is and the access switches only need to reach it over layer 3.   • "And guest or IoT segmentation?" — segmentation belongs in policy — VRFs, SGTs, or a fabric with multiple VNIs — rather than in stretched VLANs. Using VLANs as the segmentation mechanism is what forces them to span, so solving segmentation properly is what frees the boundary to move down.
What they're testingWhether you identify the single constraint that decides it. Candidates who list the three options without naming layer 2 adjacency as the deciding question have the taxonomy but not the reasoning.

What is Dynamic ARP Inspection protecting against, and how does it know what is valid?Deep

It protects against ARP spoofing — a host claiming to own an IP address it does not, usually the default gateway, to intercept traffic. DAI validates every ARP packet on untrusted ports against the DHCP snooping binding table, and drops any where the MAC-to-IP mapping does not match a known lease.

Detail

The attack it stops: ARP has no authentication, so any host can send an unsolicited ARP reply claiming the gateway's IP maps to its own MAC. Every host on the segment updates its ARP cache and sends its traffic to the attacker, who can read it, modify it, and forward it on. Nothing in the network notices, and nothing on the hosts does either.

What does IP Source Guard add on top of DHCP snooping and DAI?Deep

Detail

Where switching stops being about spanning tree and starts being about buffers and ECMP. The buffer and incast questions are the ones that separate people who have operated a fabric from people who have read about one.

Why leaf-spine rather than three-tier? What changes?Deep

Three-tier was designed for north-south traffic, where most flows went from a server to a user or to the internet. Data-centre traffic is predominantly east-west, server to server, and a three-tier design makes that path long and variable. Leaf-spine makes every server two hops from every other, with all links active via layer 3 ECMP and no spanning tree.

Properties of the Clos topology worth naming:

  • No leaf-to-leaf and no spine-to-spine links. Every leaf connects to every spine and nothing else. That regularity is what makes the hop count and the ECMP behaviour uniform.
  • Losing a spine costs 1/N of the fabric bandwidth and nothing else. With four spines a failure is a 25% capacity reduction, not an outage — so spine count is a resilience decision as much as a bandwidth one.
  • The underlay is pure layer 3. Usually eBGP with a unique AS per leaf, or OSPF; either way the goal is ECMP across all spines. bgp bestpath as-path multipath-relax is required for eBGP designs because AS_PATH contents differ per spine.
  • Layer 2 becomes an overlay. VXLAN with EVPN provides any layer 2 adjacency that is needed, over the routed underlay.

What does VXLAN add to a frame, and what does the underlay need to support?Deep

Fifty bytes: an outer Ethernet header, an outer IP header, a UDP header with destination port 4789, and an eight-byte VXLAN header carrying the 24-bit VNI. The underlay needs an MTU large enough to carry that, IP reachability between VTEP loopbacks, and ECMP — and the source UDP port is deliberately randomised to give that ECMP something to hash on.

Underlay requirements:

  • MTU of at least 1600, and in practice 9216 everywhere. A 1500-byte server frame becomes 1550, so a default-MTU underlay silently breaks large transfers while ping works.
  • IP reachability between VTEP loopbacks, which is the entire job of the underlay routing protocol.
  • ECMP across spines, so a leaf can use all its uplinks.
  • Multicast, or ingress replication, for broadcast and unknown traffic within a VNI. Ingress replication avoids running multicast in the underlay and is the common modern choice.

Why the source UDP port is randomised: the underlay cannot see the inner flow, so without help every packet between two VTEPs would hash identically and all traffic between a pair of leaves would take one spine. The VTEP therefore computes a hash of the inner headers and writes it into the outer source UDP port, which the underlay's ECMP hash does include. It is a deliberate design choice to restore per-flow load sharing, and it is the answer to "how does overlay traffic use all the spines".

A leaf is dropping packets on a port running at 20% average utilisation. Explain.Expert

Microbursts, almost certainly caused by incast. Many servers respond to one requester simultaneously, their traffic converges on one egress port, and the buffer overruns in microseconds. Averaged over any normal polling interval the utilisation looks low, so the graph and the drop counter disagree — and the drop counter is the one telling the truth.

Detail

Incast is the structural cause and worth naming explicitly: a distributed storage read, a MapReduce shuffle, a scatter-gather query or a parallel backup has N servers all transmitting to one at the same instant. Even if each sends modestly, N times that arrives at one egress port within a few microseconds. The port can only drain at line rate, so everything beyond the buffer is dropped.

What to do about it:

  • ECN rather than drops. Mark packets as congestion is building so senders reduce rate before the buffer overflows. This is the most effective single change, and it requires end-host support — which modern stacks have.
  • Buffer tuning. Allocate more shared buffer to the affected class or port. Finite, and borrowing from elsewhere.
  • Deeper-buffered hardware where incast is inherent to the workload — a platform choice, made at purchase.
  • Application-side change. Staggering responses, limiting fan-out, or smaller request units. Usually the most effective and the least available to a network team.
  • More egress bandwidth, which raises the drain rate and shortens the burst — the brute-force answer.
The sentence that settles the argument with the server team"Average utilisation and drop counters measure different things, and for burst-driven loss the drop counter is the only one that is meaningful." Being able to explain why a 20%-utilised port drops traffic is one of the more useful things a network engineer can do in a data centre, because otherwise the loss gets attributed to the network with no path to a fix.
Follow-ups to expect

What is PFC, how does it differ from ECN, and what are the risks of lossless Ethernet?Expert

PFC is per-priority PAUSE — it stops the upstream device sending one traffic class while letting others continue, making that class lossless. ECN instead marks packets to tell the end hosts to slow down. PFC acts hop by hop and reacts in microseconds; ECN acts end to end and reacts in a round trip. The risk with PFC is that pausing propagates backwards and can deadlock the fabric.

Why lossless Ethernet exists: FCoE and RDMA — particularly RoCE — were designed assuming a lossless fabric, because their recovery from loss is extremely expensive compared with TCP's. Making one priority lossless lets storage and RDMA share a fabric with ordinary traffic.

Why it is risky:

  • Pause propagation. A congested leaf pauses the spine, which pauses other leaves, which pause their servers. Congestion at one port spreads backwards through the fabric and affects traffic that was never going near the problem.
  • Head-of-line blocking. A paused class holds up everything behind it in the same queue structure.
  • Deadlock. With a cyclic buffer dependency, a set of switches can each be waiting for the other to resume, and the lossless class stops permanently until something is reset. This is a documented and serious failure mode in large RoCE deployments.
  • All-or-nothing configuration. One hop in the path without matching PFC and queue configuration breaks losslessness, and the symptom appears as application-level errors rather than as a network fault.

How ESI multihoming works, in the terms you should use:

  • Route type 1 provides auto-discovery and aliasing: remote leaves learn that a MAC behind that ESI is reachable via any of the attached leaves, so they can load-share toward it even though only one of them advertised the MAC.
  • Type 1 also enables mass withdrawal: on a link failure, one withdrawal for the ESI invalidates every MAC behind it, rather than thousands of individual type 2 withdrawals. That is the convergence advantage.

Explain StackWise on a Catalyst 9300. What happens when the ring breaks?Deep

Members are cabled in a ring, one is elected active and runs the single control plane, one is standby with state synchronised by SSO, and the rest are members. Breaking the ring in one place leaves a working chain at reduced stack bandwidth. A stack split produces two switches with one identityTwo breaks in the ring — a cable pulled while another is already faulty, or two members reloading together — leave two partial stacks. Explain StackWise Virtual. What is dual-active detection and why does its path matter?Deep

StackWise Virtual makes two chassis behave as one logical switch, joined by a StackWise Virtual Link that carries both control and data traffic. If the SVL fails while both chassis are healthy, both become active — a dual-active condition. Dual-active detection exists to notice that and put one chassis into recovery mode, and it must not share a physical path with the SVL, or the failure that causes the problem also disables the detection.

Give me the vPC failure matrix. What happens for each combination of peer-link and keepalive failure?Expert

The questions that decide it
  1. Does anything need layer 2 adjacency across access switches?   2. What is the operational capacity? One configuration is genuinely easier to run than two, and a team that will not keep two configurations consistent is better served by StackWise Virtual even though it shares fate.
  3. How are upgrades done? Independent switches upgrade one at a time with the other carrying traffic. A shared control plane means ISSU or an outage.
  4. What is physically redundant? Two chassis in one rack on one circuit are one power failure domain whatever the logical design says.

One campus with two deliberately different distribution blocks and a data centre vPC pair. The two campus blocks exist so you can be asked to compare them, and that comparison — layer 2 access against routed access — is the most useful switching whiteboard conversation there is.

Reference campus · layer 2 access on block A, routed access on block B, vPC in the data centre.

Walk me through this topology.Deep

Two core switches running OSPF area 0, and three blocks hanging off them built three different ways. Block A is classic layer 2 access into a StackWise Virtual distribution pair, so VLANs span access switches and the distribution block is one logical device. Block B is routed access, so each access switch is a router and there is no spanning tree or FHRP between the layers. The data centre is a Nexus vPC pair with one server dual-homed and one single-homed — and that single-homed server is the thing I would ask about first.

Detail — narrate it block by block
  1. Core. Two 9600s in OSPF area 0. Everything below is a stub-ish area or a redistribution point. The cores do no layer 2.
  2. Block A. DIST-A1 and A2 are joined by StackWise Virtual, so they are one switch: one configuration, one STP instance that is automatically the root for the block, one SVI per VLAN and therefore no FHRP at all, and access uplinks that are cross-stack EtherChannels — so no uplink is blocked by spanning tree. VLANs 110 and 120 exist on both access stacks. The cost is a shared control plane and the SVL/DAD design burden.
  3. Block B. DIST-B1 and B2 are independent switches. Access uplinks are routed point-to-point links with BFD, each access switch owns its own prefixes, and VLANs are local to one switch. No spanning tree between access and distribution, no FHRP, no shared control plane, independent upgrades. The cost is that nothing can be layer-2 adjacent across access switches.
  4. Data centre. A vPC pair with a peer-link for data and a keepalive over the out-of-band management VRF. SRV-1 bundles to both switches. SRV-2 is single-homed to N9K-2 — an orphan port, which means it is exposed to the peer-link failure case unless vpc orphan-port suspend is configured.
Finish the walkthrough with an observation, not just a descriptionSomething like: "the interesting thing here is that blocks A and B solve the same problem differently, so I would want to know what drove the difference — if it was a genuine stretched-layer-2 requirement in block A I would respect it, and if it was just history I would standardise on B." What they're testingWhether you can narrate a diagram in a structured order and name what each design choice costs. Spotting the orphan port unprompted is the single highest-value detail in the picture.
Trace a frame from a host in VLAN 110 on ACC-A1 to a host in VLAN 120 on ACC-A2.Deep

Different VLANs, so it has to be routed, and in block A the only router is the logical distribution switch. The frame goes up to DIST-A, gets routed between two SVIs, and comes back down — and the detail worth volunteering is that the EtherChannel hash on the way back down can choose a port on the other chassis, so the frame crosses the StackWise Virtual Link. That is why the SVL carries data and not just control traffic.

The trace
  1. The host resolves its gateway. 10.10.110.50 wants 10.10.120.80, sees it is off-subnet, and ARPs for 10.10.110.1. The ARP broadcast floods VLAN 110 — across ACC-A1's stack, up the cross-stack EtherChannel, through DIST-A, and back down to ACC-A2 as well, because VLAN 110 spans both. Exactly one device answers, because the SVL pair is one logical switch with one SVI. No HSRP, no virtual MAC, no active/standby question.
  2. ACC-A1 forwards to the gateway MAC. MAC lookup in VLAN 110 finds the SVI MAC learned on the uplink port-channel. The hash picks one physical member, which lands on either DIST-A1 or DIST-A2 — and the host has no idea which, which is the entire point of the design.
  3. DIST-A routes. The destination MAC is its own SVI MAC, so it moves up to layer 3. 10.10.120.0/24 is directly connected via SVI 120. ARP for 10.10.120.80 if it is not already cached. Rewrite the headers: source MAC becomes the SVI 120 MAC, destination becomes the host's MAC, TTL decrements by one.
  4. Egress — and the SVL. The destination MAC is known on the downlink port-channel to ACC-A2. The hash picks a member, and that member may physically live on the chassis the frame did not arrive on — so the frame traverses the SVL to get there. Normal, expected, and the reason SVL bandwidth is a capacity-planning input rather than an afterthought.
  5. ACC-A2 delivers. MAC lookup in VLAN 120 within the stack, out the access port.

Count: three MAC lookups, one route lookup, up to two ARP resolutions, one header rewrite, and one possible SVL crossing.

Then contrast with block B unpromptedIn block B the same question cannot be asked, because VLANs do not span access switches — two hosts on different access switches are necessarily in different subnets and the traffic is routed three times: the source access switch routes it onto its uplink, the distribution switch routes it across, and the destination access switch routes it to the host. More routing hops, no flooding anywhere, no shared layer 2 failure domain, and convergence governed by the routing protocol and BFD rather than by spanning tree. Volunteering that comparison is what the two-block topology is for.
Follow-ups to expect
  • "Where would you look if it failed?" — show mac address-table address on both access stacks to confirm learning, show ip arp on DIST-A for both hosts, show etherchannel summary and show interfaces port-channel for member state, and show stackwise-virtual link to confirm the SVL is healthy. In that order, because it follows the path.
  • "What if the two hosts were in the same VLAN on different access stacks?" — then it is pure layer 2 and never reaches layer 3: ACC-A1 to DIST-A to ACC-A2, no routing, no TTL decrement, and the frame still potentially crosses the SVL for the same hashing reason.
What they're testingWhether you know that a StackWise Virtual pair has one SVI and needs no FHRP, and whether you volunteer the SVL data-plane crossing. Both are details that separate people who have run this design from people who have read about it.
The StackWise Virtual Link between DIST-A1 and DIST-A2 fails. Then, separately, DIST-B1 fails entirely. Compare what happens.Expert

The SVL failure is the more disruptive of the two despite both chassis staying powered, because dual-active detection deliberately shuts one chassis down — block A halves its capacity and depends on DAD having an independent path. The DIST-B1 failure is almost a non-event: routed access means it is just a route withdrawal, and with BFD the access switches reconverge in well under a second. That asymmetry is the argument for routed access.

Case A — SVL fails, both chassis healthy
  1. Both chassis lose sight of each other over the SVL and each would become active.
  2. Dual-active detection fires over its independent path. One chassis loses and enters recovery mode, shutting every interface except the SVL and the detection links.
  3. Every downstream cross-stack EtherChannel loses the members that landed on that chassis. LACP removes them; the bundles stay up on the surviving members.
  4. The surviving chassis still has the SVI, the STP root role and the configuration, so forwarding continues — at roughly half the uplink and downlink capacity.
  5. When the SVL is repaired, the recovery-mode chassis reloads to rejoin, which is a second, planned disruption.
And if DAD had failed too, this is the worst outcome in the diagramTwo chassis, both active, both with the same SVI IP and MAC, both STP root, both with half of every downstream bundle. The access stacks see the gateway MAC on two different port-channel members belonging to two different switches, MACs flap everywhere, and because both chassis forward between VLANs you have a layer 2 loop through the access layer. That is why the DAD path must be physically independent of the SVL — not in the same fibre bundle, not in the same conduit, not through the same intermediate device. The same requirement applies to the vPC peer-keepalive next door, which is why it runs over the out-of-band management network in this design.
Case B — DIST-B1 fails entirely
  1. ACC-B1 and ACC-B2 each lose one of two equal-cost routed uplinks. BFD detects it in milliseconds, well before any routing protocol hello timer would.
  2. The routing protocol withdraws the paths through B1; traffic uses the remaining equal-cost path through B2. No flooding, no MAC flush, no spanning tree reconvergence, no FHRP election.
  3. CORE-1 and CORE-2 lose their adjacencies to B1 and reconverge the same way.
  4. Capacity halves, as in case A — but the convergence is sub-second and involves no state rebuild anywhere.

What would you change about this design?Expert

Four things, in order of how much they would reduce risk: fix the orphan port, verify the dual-active detection path is genuinely independent, interrogate whether block A's spanning VLANs are still a real requirement, and make the two campus blocks the same design. The first two are small changes with large consequences; the second two are projects.

In priority order
  1. SRV-2's orphan port. Either dual-home it, or configure vpc orphan-port suspend so its port follows vPC state. As it stands, if the peer-link fails and N9K-2 becomes the secondary, N9K-2 suspends its vPC member ports but SRV-2's port stays up — and SRV-2 is isolated while appearing healthy. One line of configuration, one real outage avoided.
  2. Prove the DAD path is independent of the SVL. Not "configured" — physically independent. Trace the cabling and the conduit. If the fast-hello link shares a path with the SVL, block A has no protection against its own worst failure mode, and nothing in the running configuration reveals that.
  3. Interrogate block A's spanning VLANs. Find out what actually requires VLAN 110 to exist on two access stacks. Very often the answer is a legacy application, a wireless design decision, or nobody remembers. If it is nothing real, block A can migrate to routed access and the campus gets simpler. If it is real, keep block A — but know what you are paying for.
  4. Standardise. Two distribution designs in one campus doubles the runbooks, doubles what an on-call engineer has to hold in their head at 2 a.m., and makes every change a question of which block it applies to. Converging on one design is worth real effort even when both designs work.
Things I would check before proposing any of it
  • show vpc consistency-parameters global and per-interface on both Nexus switches — a type 1 mismatch is latent until something reloads, and then it suspends the vPC.
  • Stack member priorities and uplink distribution on all four access stacks — uplinks on a single member turn a member failure into a block outage.
  • Whether the core pair and both distribution blocks are on software the operations team can actually upgrade, because an HA design nobody dares upgrade is not an HA design.
  • Power and rack diversity, which no amount of logical redundancy substitutes for.
Rank by risk reduced per unit of effort, and say soInterviewers are not looking for the longest list; they are looking for someone who would fix the orphan port this afternoon and open a conversation about standardising next quarter. Leading with the one-line fix that removes a real failure mode, then naming the project-sized changes separately, is what a senior answer sounds like.
What they're testingWhether you can prioritise, whether you check things before proposing changes, and whether you distinguish a configuration fix from an architecture project. The "prove it physically" instinct on DAD is a strong signal.

Three buildings, 2,000 users, new build. Design the campus switching.Deep

Ask first: how many wiring closets per building, what fibre exists between them, where the WAN and internet attach, is there a server room, what is the wireless plan, and does anything require layer 2 adjacency between buildings. That last question decides the layer 2/3 boundary and therefore most of the design.

The design
  • Collapsed core. Three buildings is well inside the range where a distribution pair per building homed to one core pair beats adding a separate core tier. Put the two core switches in different rooms on different power if the building allows.
  • A distribution pair per building, each dual-homed to both core switches with routed 100 G links.
  • Access stacks per closet, dual-homed to the building distribution with a cross-stack EtherChannel, so a member failure or an uplink failure is not a topology change.
  • Routed access if nothing needs cross-switch layer 2 — layer 3 from each access stack to distribution, OSPF with an area per building, summarised at the distribution layer. No spanning tree between layers, no FHRP, each closet its own failure domain.
  • If layer 2 must span, boundary at distribution: Rapid PVST+ or MST, with STP root and HSRP active aligned per VLAN and odd/even VLANs split across the distribution pair.
  • Wireless centrally switched to a controller pair in the server room, so the access layer needs only layer 3 reachability to it. This removes most of the pressure to stretch VLANs.
  • Addressing: a contiguous block per building so one area summary works, a /24 or smaller per closet, /31s on routed uplinks, loopbacks from a documented range for router IDs.

Follow-ups to expect
  • "Why not three-tier?" — three distribution blocks is three meshed pairs, which is manageable. A core earns its place past four blocks, or when you want a stable layer to add buildings against without touching existing ones.
  • "What would make you change the design?" — a genuine stretched-layer-2 requirement moves the boundary to distribution; very high per-port bandwidth needs change the uplink sizing; a plan to add five more buildings argues for a real core now rather than a retrofit later.

You have inherited a flat network — one VLAN, 1,200 hosts, one broadcast domain. Migrate it with no planned downtime.Expert

Build the new structure alongside the old and move hosts into it incrementally, rather than cutting over. Create the new VLANs and SVIs, route between old and new so both are reachable throughout, then migrate closet by closet by changing access port VLANs — each host's move is a DHCP renewal, not an outage.

The approach
  1. Discover first. You cannot segment what you cannot inventory. Collect the MAC table and ARP table across the estate, map addresses to ports and to switches, and identify everything with a static address — printers, cameras, badge readers, lab gear, appliances. The static-address inventory is always wrong and it is what breaks migrations.
  2. Find the layer 2 adjacency dependencies. Clustering, appliance heartbeats, discovery-based applications, anything using broadcast or link-local multicast to find peers. These determine which hosts must stay together.
  3. Design the target. One VLAN per closet or per function, sized at a /24 or smaller, with a documented addressing plan and the layer 3 boundary where you want it to end up.
  4. Build it empty. Create the VLANs, SVIs and routing. Nothing is using them yet, so this step is non-disruptive and fully reversible.
  5. Make old and new route to each other. The existing flat subnet's gateway and the new SVIs must have reachability both ways, so a host that moves can still reach everything it could before. This is the step that makes the migration incremental instead of a cutover.
  6. Migrate a pilot. One closet, ideally one with tolerant users. Change the access VLAN, hosts DHCP into the new subnet, verify.
  7. Roll forward closet by closet, with a rollback that is a single VLAN change per port.
  8. Handle statics by hand, scheduled individually, because each one needs reconfiguring at the device.
  9. Shrink the old subnet last, once it is empty, and decommission it.

Shorten the DHCP lease weeks in advanceThis is the single highest-value preparatory step. With an eight-day lease, a host moved to a new VLAN keeps trying to use its old address until the lease expires or it is rebooted — so the migration appears to break things and the rollback looks necessary. Drop the lease to one or two hours a week beforehand, let every host cycle onto a short lease, and then each port change resolves itself within minutes. Mentioning this unprompted is a strong signal, because it only occurs to people who have done a migration and watched it go wrong.
Follow-ups to expect
  • "What about the hosts with static addresses?" — they are the long pole, not the switching. Inventory them early, schedule them individually, and in some cases leave the old subnet alive as a small segment for devices nobody can safely touch. Being realistic about this — rather than promising a clean sweep — is the credible answer.
  • "How do you know when you can delete the old VLAN?" — the MAC table and ARP table for it are empty, and have stayed empty for longer than the longest plausible duty cycle of anything attached. Weeks, not days, because of equipment that is only used occasionally.
  • "What is the biggest risk?" — an undiscovered layer 2 adjacency requirement splitting a pair of hosts that need to see each other's broadcasts. Hence the discovery phase, and hence a pilot before a rollout.
What they're testingWhether you can plan a change rather than configure one. The build-alongside-and-route-between pattern is the key structural idea, the DHCP lease detail is the experience marker, and being honest about static addresses is what keeps the plan credible.
Two hosts in the same VLAN on two different switches cannot reach each other. Work through it.Deep

Work up from the physical layer and inward from both ends, checking one link in the chain at a time: ports up, correct VLAN, VLAN exists on both switches, VLAN allowed on every trunk between them, trunks up with matching native VLANs, and spanning tree forwarding for that VLAN on the path. The failure is almost always one of those.

The sequence
  1. Both ports up and in the right VLAN. show interfaces status and show interfaces <x> switchport. An access VLAN typo is the most common single cause.
  2. Does the VLAN exist on both switches? show vlan brief. A VLAN configured on one switch and not the other means the trunk cannot carry it, and with VTP transparent there is nothing to propagate it.
  3. Is the VLAN allowed on every trunk in the path? show interfaces trunk on both ends of every link. This is the second most common cause, and it only breaks the VLANs that were missed.
  4. Are the trunks actually trunking? Mode mismatch, or two dynamic auto ends that settled on access.
  5. Native VLAN consistent? A mismatch leaks traffic between VLANs and produces bizarre partial connectivity.
  6. Is STP forwarding for that VLAN on the path? show spanning-tree vlan <x>. A blocked port on the only path, or a root-inconsistent or loop-inconsistent port, breaks one VLAN while others work.
  7. Are the MACs being learned? show mac address-table vlan <x> on both switches. Each should see the other host's MAC on the uplink.
  8. Is a security feature dropping it? Port security violation, DAI or IPSG with a missing binding, a protected port or PVLAN isolation, a VACL.
  9. Is ARP resolving? show ip arp on the hosts. If MACs are learned and ARP is not resolving, suspect DAI or a host firewall.

Bisect rather than walking end to endWith more than two switches in the path, do not check every hop in order — test the middle first. Put a test host or a switch SVI in the VLAN at the midpoint and see which half fails. Each test halves the remaining path, so a six-hop path takes three tests. Follow-ups to expect
  • "What if MACs are learned on both switches but traffic still fails?" — layer 2 is working, so the problem is above it: a host firewall, ARP not resolving, DAI dropping the ARP, IPSG dropping the IP traffic, or the hosts being in different subnets despite sharing a VLAN. That last one happens more than it should.
  • "How would you prove layer 2 is fine?" — put an SVI in the VLAN on both switches and ping between them. That tests the layer 2 path with devices you control, independent of whatever the hosts are doing, and it is the control case that splits the problem cleanly.
What they're testingWhether you are systematic. There are perhaps eight possible causes and a methodical engineer finds the right one in two minutes. The bisection advice and the SVI-as-control-case trick are what make this a senior answer rather than a checklist.
Design the access layer for a modern office: Wi-Fi 6E, IoT devices, guests, and corporate laptops.Expert

Four device classes with different trust levels, so the design question is segmentation and how it is enforced. The modern answer is one VLAN per closet with identity-based policy on top — 802.1X and MAB feeding dynamic authorisation — rather than a VLAN per device class stretched across the campus, because VLAN-based segmentation is what forces VLANs to span and failure domains to grow.

The design
  • Identity at the port. 802.1X for corporate laptops with certificates, MAB with profiling for IoT and printers, and a web-auth or open guest path. One port configuration everywhere; the policy decides what each device gets.
  • Multi-domain or multi-auth host mode so a phone and a PC on one port each authenticate separately.
  • Segmentation by group, not by VLAN. Assign a scalable group tag or a VRF at authorisation and enforce policy between groups. IoT cannot reach corporate, guests reach only the internet, and none of that depends on where the device plugged in.
  • Closed mode with a monitor-mode rollout. Deploy 802.1X in monitor mode first so you see what would have failed, then move to low-impact and finally closed. Going straight to closed mode is how an authentication project becomes an outage.
  • Multigig access ports and 25 G uplinks, because Wi-Fi 6E access points can sustain multi-gigabit and a 1 G AP port is the bottleneck. Check the oversubscription in the failure case.
  • PoE budget — 6E APs and modern cameras draw more than older devices, so the switch's total PoE budget, not just per-port capability, is the constraint. Plan for 802.3bt where needed.
  • Wireless centrally switched to the controller, so the access layer needs layer 3 reachability only and client VLANs do not have to exist in every closet.
  • Routed access, enabled by the above: with segmentation in policy and wireless tunnelled, there is little left that needs a stretched VLAN.
  • The full hardening template on every port — BPDU guard, DHCP snooping, DAI, IPSG, storm control — applied from configuration management, not by hand.

Everything else follows: if policy handles separation, VLANs can stay local, routed access becomes available, spanning tree and FHRP disappear between layers, and the design gets simpler rather than more complex as you add device classes. Follow-ups to expect
  • "What if the IoT devices cannot do 802.1X?" — MAB with profiling, and be honest that MAB authenticates a MAC address, which is spoofable. Mitigate with profiling that checks the device actually behaves like what it claims to be, tight authorisation so a compromised IoT identity reaches very little, and monitoring for profile changes. MAB is a compensating control, not an equivalent to 802.1X.
  • "How do you handle a failed RADIUS server?" — critical authentication VLAN or an inaccessible-authentication-bypass policy, so that when RADIUS is unreachable devices get a defined fallback rather than no access. Deciding what that fallback grants is a security decision to make deliberately, in advance, with the security team — not during the outage.
  • "PoE sizing?" — total budget per switch and per stack, not per port. A 48-port switch cannot deliver maximum power on every port, and a closet full of 6E APs and cameras can exceed the supply. It is a real constraint and a commonly missed one.
