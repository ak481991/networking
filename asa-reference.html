01Platforms and architecture

The ASA is a stateful, flow-based firewall. Almost everything about its behaviour follows from that one design decision, so start there.

Flow-based stateful inspection

The ASA does not evaluate every packet against the full rule set. The first packet of a connection takes the slow path, where ACLs, NAT, routing and inspection policy are all resolved, and the result is written into the connection table. Every subsequent packet of that flow takes the fast path, matched against the conn table entry and forwarded with far less work.

This explains a long list of real behaviours: an ACL change does not affect existing connections, return traffic needs no ACL, asymmetric routing breaks things badly, and clear conn is sometimes the only way to make a config change take effect.

The core mental modelTwo paths, one table. If something works for existing traffic but not new traffic, you are looking at a slow-path problem (ACL, NAT, route). If it breaks mid-session, you are looking at the conn table, a timeout, or inspection.

Hardware families

  • ASA 5500-X series — the classic x86 appliances (5506-X through 5585-X). Largely end of sale, still widely deployed.
  • Firepower 1000 / 2100 / 3100 series — current appliances, which run either the ASA image or FTD. The 2100 in particular can run ASA in appliance mode or platform mode (the latter managed through FXOS).
  • Firepower 4100 / 9300 — chassis platforms running FXOS, with ASA or FTD as a logical device. The 9300 takes multiple security modules.
  • ASAv — the virtual appliance for VMware, KVM, AWS, Azure and GCP, licensed by throughput tier.

On FXOS-based platforms remember there are two layers of configuration: the chassis (interfaces, port-channels, logical devices) and the ASA application itself. An interface must exist and be allocated at the FXOS layer before the ASA can see it.

Data plane and control plane

The data plane forwards traffic; the control plane handles management, routing protocols, VPN negotiation and anything addressed to the ASA itself. Traffic destined for the box is called to-the-box traffic and is governed by different rules than through-the-box traffic — notably it is checked against the control-plane ACL and the management access configuration, not your normal interface ACLs.

The accelerated path is often called the ASP (Accelerated Security Path). Its drop counters, exposed by show asp drop, are the single most useful diagnostic on the platform.

Memory structures worth knowing

Boot, images and upgrade

show version                       ! image, uptime, licence, serial
dir disk0:
boot system disk0:/asa9-16-4-55-smp-k8.bin
show bootvar
show running-config boot

copy tftp://10.1.1.1/asa.bin disk0:

Order matters: the ASA tries boot system entries in the order configured. Always verify the MD5 against Cisco's published value before reloading, and on a failover pair upgrade the standby first.

Licensing

Older platforms use activation keys (Base vs Security Plus, context counts, encryption, AnyConnect Premium). Newer platforms use Smart Licensing against a Smart Account. Check with show activation-key or show license all. Common gotchas: security contexts, failover (Security Plus on small platforms), and AnyConnect session counts are all licence-gated, and a licence mismatch between failover peers prevents the pair from forming.

02Packet flow: the order of operations

If you learn one thing about the ASA, learn this sequence. Nearly every troubleshooting question resolves to “which of these steps did the packet fail at?”, and packet-tracer walks the same list.

ASA slow path · 10 steps, 5 drop exits. Blue marks the two steps people most often get wrong.

The two steps everyone gets wrong

Un-NAT happens before the ACL (step 3 before 4). From 8.3 onward, your inbound ACL is written against the real destination address, not the mapped one. If you publish a server as 203.0.113.10 which NATs to 10.1.1.10, the outside ACL permits 10.1.1.10. Engineers coming from 8.2 or from other vendors get this backwards constantly.

Route lookup happens before source NAT (step 5 before 6). The egress interface is chosen by the routing table, and then the NAT rule for that interface pair is applied. A NAT rule alone will not pull traffic out of a different interface. The exception is NAT divert: a matching NAT rule with a specific destination interface can take precedence over the route for identity/twice NAT, which is why the route-lookup keyword exists to force normal routing.

Classic failurePublishing a server, permitting the public IP in the ACL, and wondering why it is denied. packet-tracer shows the ACL phase dropping on the translated address. Permit the real IP.

Fast path vs slow path

Step 2 is the fork. A packet matching an existing conn entry skips ACL, NAT lookup and route lookup entirely, going straight to inspection and egress. Consequences:

  • Changing an ACL does not tear down existing connections. Use clear conn address x.x.x.x to force re-evaluation.
  • Return traffic needs no ACL — the conn entry covers it. This is why ASA ACLs are written in one direction only.
  • A packet arriving for a flow the ASA does not know about (after a failover, or with asymmetric routing) is dropped, typically as tcp-not-syn or syslog 106015.

Reading packet-tracer against this list

packet-tracer prints its phases in exactly this order, so you can map a failure straight onto the diagram.

packet-tracer input outside tcp 198.51.100.5 12345 203.0.113.10 443 detailed

Phase: 1  ACCESS-LIST          ! implicit, interface check
Phase: 2  UN-NAT               ! step 3 — destination rewritten
Phase: 3  ACCESS-LIST          ! step 4 — the real test
Phase: 4  NAT                  ! step 6
Phase: 5  ROUTE-LOOKUP         ! step 5
Phase: 6  INSPECT              ! step 8
Phase: 7  FLOW-CREATION        ! step 7
Result: ALLOW | DROP (drop reason)

The last line gives you the ASP drop reason directly. Phase ordering in the output varies slightly by release and by whether NAT divert applies — read the phases themselves rather than memorising a fixed list.

03Interfaces and security levels

Security levels

Every named interface carries a level from 0 to 100. Convention: outside 0, inside 100, DMZ something in between. The level governs default behaviour when no ACL is applied:

  • Higher to lower — permitted by default.
  • Lower to higher — denied by default.
  • Same to same — denied, unless same-security-traffic permit inter-interface.
  • In and out of the same interface (hairpin) — denied, unless same-security-traffic permit intra-interface.

In practice most deployments apply an explicit ACL to every interface, which overrides the default entirely. The security level then matters mainly for same-security rules, for NAT interface pairing, and for which interface wins in a tie.

Interview staple“Traffic from DMZ (50) to inside (100) — what do you need?” An ACL on the DMZ interface permitting it, and a NAT rule (or NAT exemption) for that interface pair. The level alone denies it.

Interface configuration

interface GigabitEthernet0/0
 nameif outside
 security-level 0
 ip address 203.0.113.2 255.255.255.0
 no shutdown

interface GigabitEthernet0/1.10          ! subinterface
 vlan 10
 nameif dmz
 security-level 50
 ip address 10.10.10.1 255.255.255.0

interface Port-channel1
 lacp max-bundle 8
 nameif inside
 security-level 100

interface Management0/0
 management-only                          ! no through traffic

An interface with no nameif is invisible to policy. management-only blocks through-the-box traffic on that interface, which is what you want for an out-of-band management port.

Redundant and port-channel interfaces

A redundant interface pairs two physical ports in active/standby, failing over on link loss — simple, no switch configuration needed. A port-channel bundles ports with LACP for both redundancy and aggregate bandwidth, and is the usual modern choice. Both can carry subinterfaces.

MTU, fragments and MSS

mtu outside 1500
sysopt connection tcpmss 1380            ! clamp TCP MSS
fragment chain 1 outside                 ! disallow fragments
show fragment

The ASA reassembles fragments before inspection by default, which can be a resource issue under attack. sysopt connection tcpmss clamps the MSS in passing SYNs — essential when traffic crosses a tunnel, where the default 1380 is often still too high for IPsec with additional overhead.

Useful verification

show interface ip brief
show nameif
show interface GigabitEthernet0/0        ! errors, drops, duplex
show traffic
show arp

On show interface, watch input errors, overruns and no buffer. Overruns mean the interface received faster than the box could process — a capacity or interrupt problem, not a cabling one.

04ACLs and object groups

ACL types

TypeUsed for
ExtendedThe normal through-traffic policy: source, destination, protocol, ports
StandardDestination only. Used for route maps and split-tunnel lists, not interface policy
EtherTypeTransparent mode only, for non-IP traffic such as BPDUs, IPX, MPLS
WebtypeClientless SSL VPN URL filtering

Applying an ACL

access-list OUTSIDE_IN extended permit tcp any4 host 10.1.1.10 eq 443
access-list OUTSIDE_IN extended deny ip any4 any4 log
access-group OUTSIDE_IN in interface outside

access-group GLOBAL_POLICY global        ! applies to all interfaces, after per-intf

Direction is nearly always in. An out ACL is evaluated on the egress interface after routing and is rarely needed. There is an implicit deny ip any any at the end of every applied ACL — but add an explicit one with log, because the implicit rule does not generate syslogs.

A global ACL applies to traffic on every interface and is evaluated after interface ACLs. Useful for a blanket blocklist without touching each interface.

Object groups

object network SRV-WEB
 host 10.1.1.10

object-group network DMZ-SERVERS
 network-object host 10.10.10.5
 network-object host 10.10.10.6
 group-object SRV-WEB                    ! nesting is allowed

object-group service WEB-PORTS tcp
 port-object eq www
 port-object eq https

access-list OUTSIDE_IN extended permit tcp any4 object-group DMZ-SERVERS object-group WEB-PORTS

Object groups expand into individual ACEs internally. show access-list shows both the configured line and the expanded entries with their hit counts, which is where you actually read hits.

Reading hit counts

show access-list OUTSIDE_IN
show access-list OUTSIDE_IN | include hitcnt=[1-9]   ! only rules being used
clear access-list OUTSIDE_IN counters

Zero hit counts over a long period are the basis of rule cleanup. Be careful: a rule can legitimately have zero hits because a rule above it shadows it, so check order before deleting.

Operational habitBefore any ACL change, show access-list and save it. The ASA has no built-in rule-change rollback, and no access-list on a line with object groups can remove more than you intended.

Logging and time ranges

access-list OUTSIDE_IN extended deny ip any4 any4 log 4 interval 300

time-range BUSINESS-HOURS
 periodic weekdays 08:00 to 18:00
access-list X extended permit ip any4 any4 time-range BUSINESS-HOURS

ACL logging produces syslog 106100 with per-flow aggregation at the configured interval, instead of 106023 per denied packet. On a busy deny-all rule, always set an interval or you will flood the log.

05NAT

The 8.3 rewrite changed NAT completely, and it remains the most misconfigured feature on the platform. Learn the three sections and the ordering rules and most of it falls out.

The three NAT sections

SectionNameOrder within the section
1Manual NAT (twice NAT)In the order you configure it. First match wins
2Auto NAT (object NAT)Automatic: static before dynamic, then fewest real IPs, then lowest IP, then name alphabetically
3Manual NAT after-autoIn configured order, evaluated last

The ASA walks section 1, then 2, then 3, and the first matching rule wins. This is why a broad manual NAT rule configured early can silently shadow every object NAT you write afterwards.

show nat                                 ! all rules in evaluation order, with hits
show nat detail
show run nat

Auto NAT (object NAT)

Defined inside a network object. Simpler, covers most cases, translates source only on the way out (or destination on the way in for a static).

! Dynamic PAT: inside hosts share the outside interface IP
object network INSIDE-NET
 subnet 10.1.0.0 255.255.0.0
 nat (inside,outside) dynamic interface

! Static one-to-one: publish a server
object network SRV-WEB
 host 10.1.1.10
 nat (inside,outside) static 203.0.113.10

! Static PAT: port forward only 443
object network SRV-WEB-443
 host 10.1.1.10
 nat (inside,outside) static interface service tcp 443 443

Manual NAT (twice NAT)

Matches on source and destination together, which is what you need for policy NAT and for VPN exemption.

! NAT exemption: do not translate inside-to-VPN-peer traffic
nat (inside,outside) source static INSIDE-NET INSIDE-NET \
    destination static REMOTE-NET REMOTE-NET no-proxy-arp route-lookup

! Policy NAT: translate differently depending on destination
nat (inside,outside) 1 source dynamic INSIDE-NET PARTNER-POOL \
    destination static PARTNER-NET PARTNER-NET

Two keywords you will use constantly on exemption rules:

  • no-proxy-arp — stops the ASA answering ARP for the mapped addresses, which otherwise black-holes traffic on a shared segment.
  • route-lookup — forces a normal routing-table decision for the egress interface instead of letting the NAT rule's interface pair dictate it. Essential when the NAT would otherwise divert traffic out of the wrong interface.
The number one VPN faultTraffic to a VPN peer being PATed to the outside interface instead of entering the tunnel, because no exemption rule exists or it sits below a broader rule. packet-tracer shows the wrong NAT rule matching in the NAT phase. Fix with an exemption rule placed above the PAT rule in section 1.

Identity NAT, and the order trick

Identity NAT translates an address to itself — the mechanism behind NAT exemption. To control placement explicitly:

nat (inside,outside) 1 source static A A destination static B B   ! line 1 of section 1
nat (inside,outside) after-auto source dynamic ANY interface       ! section 3

The numeric argument sets the line number within section 1. after-auto pushes a rule into section 3, which is the clean way to write a catch-all PAT that must never shadow anything specific.

Verifying translations

show xlate                               ! active translations
show xlate detail
show xlate local 10.1.1.10
clear xlate local 10.1.1.10              ! also kills the conn
show nat pool                            ! PAT pool utilisation

clear xlate tears down the associated connections too, so treat it as disruptive. PAT pool exhaustion shows as syslog 305006 or ASP drop nat-no-xlate-to-pat-pool; the fix is a larger pool, pat-pool with round-robin, or extended PAT.

Pre-8.3 vs post-8.3

Pre-8.3 used nat / global pairs with NAT IDs, static (inside,outside) statements, and ACLs written against the mapped address. Post-8.3 uses the object and manual syntax above with ACLs against the real address. You still meet old configs and migration scripts, so recognise the old form — and remember that a migrated config very often has its ACLs wrong for exactly this reason.

06Routing

Static routes and tracking

route outside 0.0.0.0 0.0.0.0 203.0.113.1 1
route backup 0.0.0.0 0.0.0.0 198.51.100.1 254     ! floating static

sla monitor 10
 type echo protocol ipIcmpEcho 8.8.8.8 interface outside
 frequency 10
sla monitor schedule 10 life forever start-time now

track 1 rtr 10 reachability
route outside 0.0.0.0 0.0.0.0 203.0.113.1 1 track 1

SLA-tracked default routes are the standard dual-ISP pattern on ASA. Without tracking, a floating static only takes over if the interface goes down — which does not happen when the failure is upstream.

Dynamic routing

The ASA supports OSPFv2/v3, EIGRP, RIP and BGP. Points that come up:

  • The ASA is a security device first; it will not form adjacencies through itself transparently in routed mode.
  • Dynamic routing is supported in multiple context mode from 9.0 onward, but not every protocol in every mode — check the release notes.
  • Routing protocol traffic is to-the-box, so it must be permitted by the control-plane policy if you have tightened it.
  • Redistribution between protocols is supported but limited compared with IOS.
show route
show route | include 10.1.1
show ospf neighbor
show bgp summary
show asp table routing | include 10.1.1.0     ! what the dataplane actually uses

Asymmetric routing and TCP state bypass

A stateful firewall needs to see both directions of a flow. If routing sends the return path around the ASA, or through a different ASA, mid-flow packets arrive with no matching conn and are dropped as tcp-not-syn.

Proper fixes are routing fixes. Where you genuinely cannot make traffic symmetric, TCP state bypass disables stateful checks for selected flows:

access-list BYPASS extended permit ip 10.1.0.0 255.255.0.0 10.2.0.0 255.255.0.0
class-map TCP-BYPASS
 match access-list BYPASS
policy-map PM-BYPASS
 class TCP-BYPASS
  set connection advanced-options tcp-state-bypass
service-policy PM-BYPASS interface inside
Understand the costTCP state bypass turns off sequence checking and most inspection for those flows. It is a workaround for a topology problem, not a feature. Scope it as narrowly as possible.

07Modular Policy Framework and inspection

MPF is the ASA's equivalent of MQC: classify traffic, apply actions, attach the policy to an interface or globally.

The three-part structure

class-map INSPECT-ICMP                   ! 1. what traffic
 match default-inspection-traffic

policy-map global_policy                 ! 2. what to do with it
 class inspection_default
  inspect dns preset_dns_map
  inspect ftp
  inspect icmp
  inspect esmtp
 class class-default
  set connection timeout idle 1:00:00

service-policy global_policy global      ! 3. where it applies

Only one service policy per interface, plus one global policy. An interface policy takes precedence over the global policy for the traffic it matches.

Why inspection matters

Inspection engines do two jobs: they open secondary connections ("pinholes") for protocols that negotiate dynamic ports, and they enforce protocol conformance.

InspectWhy you need it
icmpWithout it, ICMP echo replies are not treated as return traffic and need an explicit ACL. Almost always enable it
ftpOpens the data channel for active and passive FTP, and rewrites embedded addresses under NAT
dnsEnforces message length, does DNS doctoring, protects against some spoofing
sip, skinny, h323Voice signalling: opens RTP pinholes and fixes embedded addresses
esmtpMail command filtering. A frequent cause of mysterious mail problems — often the right move is to disable it
sqlnet, tftp, rtsp, pptpSame pattern: dynamic ports or embedded addressing
Inspection as the culpritWhen an application half-works through the ASA — connects then hangs, or works one direction — suspect its inspect engine before anything else. Test by disabling that inspect temporarily and re-running. ESMTP and SIP are the usual offenders.

Connection limits and TCP normalisation

policy-map PM-LIMITS
 class class-default
  set connection conn-max 10000 embryonic-conn-max 1000
  set connection timeout idle 0:30:00 embryonic 0:00:30

tcp-map TM-PERMISSIVE
 urgent-flag allow
 exceed-mss allow
 check-retransmission

policy-map PM-LIMITS
 class SOME-CLASS
  set connection advanced-options TM-PERMISSIVE

Embryonic connection limits are the ASA's built-in SYN-flood protection: beyond the threshold it intercepts and proxies the handshake. TCP normalisation drops packets that violate TCP rules — which occasionally breaks legitimate but badly behaved applications, hence the permissive tcp-map pattern.

Verification

show service-policy
show service-policy inspect dns
show service-policy interface outside
show conn detail                          ! flags show which inspect applies

show service-policy gives per-class packet counts and drop counts, which tells you whether an inspect engine is actually dropping your traffic.

08Connections, xlates and timeouts

Reading the conn table

show conn
show conn count
show conn address 10.1.1.10
show conn port 443

A typical line:

TCP outside 198.51.100.5:49152 inside 10.1.1.10:443, idle 0:00:12, bytes 84210, flags UIO

The flags are the valuable part. show conn detail prints a legend. The ones to know:

FlagMeaning
UUp — the TCP handshake completed
I / OInbound / outbound data has passed
a / AAwaiting outside/inside ACK to SYN — a half-open connection

R / rOutside/inside has sent a RST; connection tearing down

Fast diagnosisLots of connections stuck at saA or aB means SYNs are going out and nothing is coming back — the far side or the return path is the problem, not the ASA's policy, because the conn was built.

Timeouts

show running-config timeout
timeout conn 1:00:00 half-closed 0:10:00 udp 0:02:00
timeout xlate 3:00:00
timeout sunrpc 0:10:00 h323 0:05:00 sip 0:30:00
timeout floating-conn 0:00:30

Defaults are one hour for TCP conns and two minutes for UDP. Idle timeouts are the usual explanation for a session that dies after a predictable interval — long-lived idle TCP sessions (database connections, SSH jump sessions) being the classic case. Either raise the timeout for that class via MPF or enable keepalives on the application.

timeout floating-conn matters when a better route appears for an existing flow; it controls how long the old flow survives.

Local-host and threat detection

show local-host                           ! per-host conn and xlate counts
show local-host 10.1.1.10 detail
show threat-detection statistics top host-stats
show threat-detection rate
shun 198.51.100.5                         ! block a host immediately
show shun

show local-host is the fastest way to find the host responsible for a connection-count spike. shun installs an immediate block that is independent of the ACL and survives until cleared — useful during an incident, and easy to forget about afterwards.

09Failover

Modes

  • Active/Standby — one unit passes traffic, the other waits. Works in single and multiple context mode. The common deployment.
  • Active/Active — requires multiple context mode. Contexts are split into two failover groups, each active on a different unit, so both units carry traffic. More complex; size each unit to carry everything after a failure.

Both are stateful if you configure a state link: conn table, xlate table, ARP table and some VPN state replicate, so existing sessions survive a failover. Without the state link, failover is stateless and every session drops.

Configuration

! Primary unit
failover lan unit primary
failover lan interface FOLINK GigabitEthernet0/3
failover interface ip FOLINK 10.255.0.1 255.255.255.252 standby 10.255.0.2
failover link FOSTATE GigabitEthernet0/4
failover interface ip FOSTATE 10.255.0.5 255.255.255.252 standby 10.255.0.6
failover key <shared-key>
failover

! On each data interface
interface GigabitEthernet0/0
 ip address 203.0.113.2 255.255.255.0 standby 203.0.113.3

monitor-interface inside
monitor-interface outside
failover polltime unit 1 holdtime 3
failover polltime interface 5 holdtime 25

The failover link carries hellos and config replication; the state link carries session state. They can share an interface on low-throughput deployments, but separate them where you can — state replication can be heavy.

What must match between peers

Failover will not form, or will fall out, if these differ: software version (within the allowed combinations for a zero-downtime upgrade), hardware model, number and type of interfaces, operating mode (routed/transparent, single/multiple), and licensing of the relevant features.

show failover
show failover history
show failover state
failover active                           ! force this unit active
no failover active                        ! force it standby
failover exec mate show version           ! run a command on the peer
failover reload-standby
Always check historyshow failover history records every state change with a reason. “Interface check”, “Failover state check” and “HELLO not heard” each point somewhere different. Start here, not with show failover alone.

Interface monitoring and split brain

Monitored interfaces are tested with hellos and, if those fail, with ARP and broadcast ping tests. If more monitored interfaces fail on the active than on the standby, failover occurs. Unmonitored interfaces never trigger failover — a common oversight on newly added interfaces.

Split brain (both units active) usually means the failover link is down while data interfaces are up. The units cannot hear each other, so both assume the peer is dead. This is why the failover link should be a direct cable or a dedicated, highly reliable path.

Zero-downtime upgrade

  1. Copy the image to both units and set boot system on both.
  2. failover reload-standby — the standby reloads on the new image.
  3. Wait for it to come back and sync (show failover shows standby ready).
  4. no failover active on the primary — traffic moves to the upgraded unit.
  5. Reload the now-standby original primary.
  6. Optionally make it active again.

Only certain version combinations are supported as a mixed pair. Check the upgrade path in the release notes before starting.

10Clustering

Several ASAs acting as one logical firewall, for throughput beyond a single box. Distinct from failover, and with its own vocabulary.

Roles per flow

RoleDoes what
OwnerThe unit that received the first packet and holds the connection state. Processes the flow
DirectorChosen by hash of the flow. Keeps a backup of the state and answers “who owns this flow?” queries
ForwarderA unit that receives a packet for a flow it does not own; asks the director and forwards to the owner over the CCL
Backup ownerHolds a copy of the state so the flow survives the owner failing

This design is what makes clustering tolerate asymmetric traffic: any unit can receive a packet and get it to the owner.

Key components

  • CCL (Cluster Control Link) — the dedicated backplane between units, carrying state, director queries and forwarded data. Size it generously; a congested CCL degrades everything. Usually a port-channel on a dedicated switch pair.
  • Control unit — elected; owns configuration, which replicates to data units. Replaces the idea of a primary.
  • Spanned EtherChannel mode — all units share one port-channel to the switch, which load-balances by hash. The usual choice.
  • Individual interface mode — each unit has its own IP, with an upstream router load-balancing. Routed mode only.
show cluster info
show cluster info health
show cluster conn count
show conn detail | include Cluster
cluster exec show conn count              ! run across every unit
cluster exec is the one to rememberAny show command prefixed with cluster exec runs on every member and labels the output. Without it you are troubleshooting one unit of a system that spreads flows across all of them.

11Site-to-site VPN

The two phases

Phase 1 (IKE / ISAKMP) authenticates the peers and builds a secure management channel. Negotiates encryption, hash, authentication method, DH group and lifetime.

Phase 2 (IPsec) builds the actual data SAs inside that channel, one pair per traffic selector. Negotiates the transform set / proposal, the proxy IDs (interesting traffic), PFS and lifetime.

Mismatches in phase 1 mean the tunnel never comes up at all. Mismatches in phase 2 mean phase 1 completes and then fails — which is a useful diagnostic split in itself.

IKEv2 configuration

crypto ikev2 policy 10
 encryption aes-256
 integrity sha256
 group 14
 prf sha256
 lifetime seconds 86400
crypto ikev2 enable outside

crypto ipsec ikev2 ipsec-proposal PROP-AES256
 protocol esp encryption aes-256
 protocol esp integrity sha-256

tunnel-group 198.51.100.1 type ipsec-l2l
tunnel-group 198.51.100.1 ipsec-attributes
 ikev2 remote-authentication pre-shared-key <key>
 ikev2 local-authentication pre-shared-key <key>

access-list VPN-PARTNER extended permit ip 10.1.0.0 255.255.0.0 172.16.0.0 255.255.0.0

crypto map OUTSIDE-MAP 10 match address VPN-PARTNER
crypto map OUTSIDE-MAP 10 set peer 198.51.100.1
crypto map OUTSIDE-MAP 10 set ikev2 ipsec-proposal PROP-AES256
crypto map OUTSIDE-MAP 10 set pfs group14
crypto map OUTSIDE-MAP interface outside

The crypto map is processed in sequence order; a lower-numbered entry with a broad ACL will capture traffic intended for a later peer.

The three things that break site-to-site tunnels

  1. Mismatched proxy IDs. The crypto ACL must mirror the peer's exactly. Syslog 402116 tells you a packet did not match the SA's proxy ID. Non-Cisco peers often want specific (not aggregate) selectors.
  2. Missing NAT exemption. Traffic gets PATed to the outside interface instead of entering the tunnel. Covered in the NAT section — this is the most common fault of all.
  3. Mismatched phase 1 or 2 parameters. DH group, lifetime, PFS, integrity. Debugs name the attribute that failed.
show crypto ikev2 sa
show crypto ipsec sa peer 198.51.100.1
show vpn-sessiondb l2l
show crypto ipsec sa | include ident|encaps|decaps

debug crypto ikev2 protocol 127
debug crypto ipsec 127
debug crypto condition peer 198.51.100.1  ! scope the debug first
Encaps vs decapsIn show crypto ipsec sa, if encaps is incrementing but decaps is not, you are sending and they are not replying — look at their side, their NAT exemption, or a firewall in between. Both at zero means traffic is not reaching the crypto map at all, which is usually NAT or routing.

VTI, the modern alternative

From 9.7, the ASA supports Virtual Tunnel Interfaces — a routable tunnel interface instead of a crypto map and ACL. Traffic enters the tunnel because of the routing table, not a crypto ACL, which removes the proxy-ID class of problems entirely and lets you run dynamic routing over the tunnel.

crypto ipsec profile PROF-VTI
 set ikev2 ipsec-proposal PROP-AES256

interface Tunnel1
 nameif vti-partner
 ip address 169.254.1.1 255.255.255.252
 tunnel source interface outside
 tunnel destination 198.51.100.1
 tunnel mode ipsec ipv4
 tunnel protection ipsec profile PROF-VTI

route vti-partner 172.16.0.0 255.255.0.0 169.254.1.2

sysopt and tunnel traffic

sysopt connection permit-vpn (on by default) lets decrypted VPN traffic bypass the interface ACL. If you need to filter inside the tunnel, either disable it and write ACLs, or apply a vpn-filter in the group policy. Knowing it is on by default explains why tunnel traffic flows despite a restrictive outside ACL.

Split tunnelling

  • tunnelall — everything goes through the VPN. Most secure, highest load on the ASA and the internet link.
  • tunnelspecified — only networks in the ACL are tunnelled.
  • excludespecified — everything is tunnelled except the listed networks.

Use a standard ACL for the split-tunnel list. Dynamic split tunnelling by FQDN is available in newer client and ASA versions and is the usual way to exclude SaaS traffic.

Hairpinning

If VPN clients need to reach the internet through the ASA, traffic enters and leaves the same interface. That requires:

same-security-traffic permit intra-interface

nat (outside,outside) source dynamic VPN-POOL interface

Both pieces are needed. The missing intra-interface permit is a very common cause of “VPN connects but no internet”.

13Multiple context mode

The three spaces

  • System execution space — no interfaces or routing of its own. Defines contexts, allocates interfaces, configures failover and resource classes.
  • Admin context — a normal context that the system uses for things needing network access, such as TFTP and AAA for management.
  • User contexts — independent virtual firewalls, each with its own config file, interfaces, policy, NAT and routing table.
mode multiple                             ! reboots the box
changeto system
changeto context CTX-A
show context
show mode

Interface allocation and the classifier

context CTX-A
 allocate-interface GigabitEthernet0/0.10
 allocate-interface GigabitEthernet0/1.10 inside visible
 config-url disk0:/ctx-a.cfg

When an interface is shared between contexts, the ASA must decide which context a packet belongs to. The classifier uses, in order: unique interfaces (simplest and preferred), then unique MAC addresses, then the NAT configuration. Enable mac-address auto in the system space so shared interfaces get distinct MACs — without it, classification on shared interfaces is fragile.

Resource management

class GOLD
 limit-resource conns 20%
 limit-resource xlates 20%
 limit-resource rate conns 5000
context CTX-A
 member GOLD

show resource usage context CTX-A
show resource allocation

Without resource classes, one context can exhaust the box for everyone. The default class is unlimited, which is rarely what you want in a shared deployment.

What you give up

Historically multiple context mode excluded VPN, dynamic routing and multicast. Much of that has been relaxed — dynamic routing from 9.0, site-to-site VPN in contexts from 9.0, and remote access VPN in contexts from 9.5 with licensing caveats. Check the feature matrix for your exact release rather than quoting the old limitations.

14Transparent mode

What it is

A layer 2 firewall: a "bump in the wire" that bridges two segments of the same subnet while still performing full stateful inspection. The ASA is not a routing hop, so you can insert it without re-addressing anything — the main reason to choose it.

firewall transparent                      ! clears the config
show firewall

interface BVI1
 ip address 10.1.1.4 255.255.255.0        ! management IP only

interface GigabitEthernet0/0
 nameif outside
 security-level 0
 bridge-group 1

interface GigabitEthernet0/1
 nameif inside
 security-level 100
 bridge-group 1

The BVI address is for management and for traffic the ASA originates; it is not a gateway for hosts. Hosts keep their original default gateway on the other side of the firewall.

EtherType ACLs

Transparent mode passes IP traffic subject to normal ACLs, but non-IP traffic needs an EtherType ACL. Most commonly for BPDUs — which are not forwarded by default, and whose absence can cause a loop if the ASA bridges two paths.

access-list ETHER ethertype permit bpdu
access-list ETHER ethertype permit mpls-unicast
access-group ETHER in interface outside

Limitations

  • No dynamic routing protocol participation through the ASA (it can still pass the traffic).
  • DHCP traffic passes, but the ASA cannot be the DHCP relay in the usual sense.
  • Each bridge group is limited in the number of interfaces, and the number of bridge groups is capped per release.
  • NAT is supported in transparent mode from 8.4, which surprises people who learned the older restriction.

show bridge-group

Cut-through proxy and identity

The ASA can authenticate users for through traffic (aaa authentication match), intercepting HTTP/FTP/Telnet to prompt for credentials — the classic cut-through proxy. More modern deployments use the Identity Firewall with the AD agent, or TrustSec SGTs learned over SXP from ISE, so that ACLs can reference users and groups rather than addresses.

17Troubleshooting

Three tools do ninety percent of the work: packet-tracer, capture with trace, and show asp drop. Learn those properly before reaching for debugs.

packet-tracer — simulate a flow

packet-tracer input inside tcp 10.1.1.50 12345 8.8.8.8 443 detailed
packet-tracer input outside tcp 198.51.100.5 12345 203.0.113.10 443 detailed

! newer syntax with full 6-tuple and persistence
packet-tracer input outside tcp 198.51.100.5 12345 203.0.113.10 443 \
  detailed xml
packet-tracer input inside icmp 10.1.1.50 8 0 8.8.8.8

It walks the real configuration through the real order of operations and tells you which phase dropped the packet and why. It does not test whether the far end responds, and it uses a synthetic packet, so a clean packet-tracer with a broken application means the problem is beyond the ASA's policy.

Habit worth formingRun packet-tracer in both directions before escalating anything. Half of “the firewall is blocking it” tickets are answered in thirty seconds this way, and the output is evidence you can paste into the ticket.

capture — see the real packets

! standard data capture
access-list CAPACL extended permit ip host 10.1.1.50 host 8.8.8.8
access-list CAPACL extended permit ip host 8.8.8.8 host 10.1.1.50
capture CAP interface inside access-list CAPACL buffer 10000000

! or match syntax, quicker to type
capture CAP interface inside match tcp host 10.1.1.50 host 8.8.8.8 eq 443

! capture what the ASP is dropping
capture ASPDROP type asp-drop all buffer 10000000
capture ASPDROP type asp-drop acl-drop

! trace each captured packet through the phases
capture CAP interface inside trace trace-count 50 match ip host 10.1.1.50 any
show capture CAP
show capture CAP trace detail
show capture CAP packet-number 3 trace

copy /pcap capture:CAP tftp://10.1.1.50/cap.pcap
no capture CAP                            ! always clean up

capture ... trace is the strongest tool on the box: it takes a real packet and shows you the same phase-by-phase walk as packet-tracer. When packet-tracer says allow but traffic still fails, this is the next step.

Remember to remove capturesThey consume memory and, with large buffers on a busy box, can affect performance. clear capture /all and no capture NAME.

show asp drop — why packets died

clear asp drop
! reproduce the problem, then:
show asp drop
show asp drop frame acl-drop

Performance triage

show cpu usage
show processes cpu-usage sorted non-zero
show cpu detailed                         ! dataplane vs control plane split
show memory
show memory detail
show blocks
show conn count
show perfmon
show traffic
show resource usage                       ! multi-context

High CPU in the data plane points at traffic volume, inspection load or an attack. High CPU in a single named process points at that process — Dispatch Unit is dataplane, Logger means you are logging too much, snmp means a polling problem. Correlate with show conn count and show local-host to find a source.

First ten minutes on an unknown problem

  1. show version and show failover — what am I on, and is this the active unit?
  2. packet-tracer for the reported flow, both directions.
  3. show conn address <host> — does the flow exist, and what are its flags?
  4. show xlate local <host> — is NAT doing what you expect?
  5. clear asp drop, reproduce, show asp drop.
  6. show logging | include <host> for the syslog story.
  7. Only then: capture with trace, and only then debugs.
Debugs last, and scopedDebugs on a production ASA can wedge the box. Always scope first — debug crypto condition peer x.x.x.x — set logging buffered debugging rather than printing to console, and have undebug all ready.

18ASA vs FTD

Most ASA work now happens alongside a migration conversation, so be able to speak to both.

DimensionASAFTD (Secure Firewall Threat Defense)
ManagementCLI and ASDM, or CSMFMC (Secure Firewall Management Center) or FDM; CLI is diagnostic, not configuration
Policy modelACL plus MPF inspectionAccess Control Policy with rules referencing applications, URLs, users and intrusion policies
IPSSeparate module (legacy)Snort, integrated
Application awarenessLimitedOpenAppID application visibility and control
Config changesImmediate on commitStaged, then deployed from FMC
Packet pathLINA onlyLINA (the ASA data plane) then Snort, for traffic that needs it

What carries over

FTD still contains LINA — essentially the ASA data plane. So the packet-flow order of operations, NAT model, conn and xlate tables, ASP drop reasons and many show commands are the same. From the FTD CLI, system support diagnostic-cli drops you into a familiar ASA prompt where packet-tracer, show conn and show asp drop all work.

That is the reason ASA knowledge remains directly useful: the inspection layer above changed, the forwarding engine underneath did not.

Migration

Cisco's Secure Firewall Migration Tool converts an ASA configuration into an FTD policy, handling objects, ACLs, NAT and interfaces, with a report of what it could not translate. Expect manual work on: VPN configuration, anything using MPF features without an FTD equivalent, and rules that relied on ASA-specific NAT ordering.

Worth saying in an interviewThe migration tool gets you a starting policy, not a finished one. The value of understanding ASA packet flow is that you can tell whether the converted policy actually behaves the same way.
