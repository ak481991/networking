01How the ASA picks a NAT rule

Before any syntax, understand the evaluation order. Most NAT faults are not a wrong rule — they are the right rule sitting below a broader one that matched first.

The three sections

SectionRule typeOrder inside the section
1Manual NAT (twice NAT)Exactly as configured, top to bottom
2Auto NAT (object NAT)Automatic — see the ordering rules below
3Manual NAT after-autoAs configured, evaluated last of all

The ASA walks section 1 top to bottom, then section 2, then section 3. First match wins and evaluation stops. Nothing below it is ever considered for that packet.

The single most common NAT faultA broad manual NAT rule configured early in section 1 shadowing every specific rule written later. show nat prints rules in true evaluation order with hit counts — if your rule has zero hits and traffic is being translated anyway, something above it matched.

Auto NAT ordering inside section 2

You do not control this order directly. The ASA sorts auto NAT rules by:

  1. Static before dynamic. Every static rule is considered before any dynamic rule.
  2. Fewest real IP addresses first. A host object beats a /24 object, which beats a /16.
  3. Lowest real IP address first, where the counts tie.
  4. Alphabetically by object name, as the final tie-break.

This is usually what you want — most specific first. When it is not, that is the reason manual NAT exists: it gives you explicit placement.

Controlling placement explicitly

! line 1 of section 1 — evaluated before everything
nat (inside,outside) 1 source static NET-A NET-A destination static NET-B NET-B

! insert at a specific line in section 1
nat (inside,outside) 3 source dynamic NET-C POOL-C

! section 3 — a catch-all that can never shadow anything
nat (inside,outside) after-auto source dynamic any interface

The numeric argument is the line number within section 1. after-auto places the rule in section 3. A catch-all PAT written after-auto is the clean pattern: it still works, but it can never accidentally pre-empt a specific rule.

Proxy ARP

When a mapped address lives in the same subnet as the mapped interface, the ASA answers ARP requests for it so the upstream router can deliver the traffic. That is correct for static NAT publishing a server.

It is wrong for identity NAT, where the mapped address is a real network that exists elsewhere — the ASA would answer ARP for addresses it does not own and black-hole the traffic. Hence no-proxy-arp on exemption rules.

show arp
show running-config nat | include proxy
debug arp                                 ! scope it, this is noisy

route-lookup and NAT divert

For manual NAT with a static source translation, the egress interface normally comes from the NAT rule's interface pair rather than the routing table. This is NAT divert, and it can pull traffic out of an interface the routing table never chose.

route-lookup suppresses that and forces a normal routing decision. Add it to identity and exemption rules unless you specifically want the divert behaviour.

Rule of thumbOn an exemption rule, write both keywords: no-proxy-arp route-lookup. It is the safe default and avoids two whole classes of problem.

Bidirectional vs unidirectional

Static rules are bidirectional: they translate outbound and un-translate inbound, so the mapped address becomes reachable from the mapped side. Dynamic rules are unidirectional — they only create a translation when traffic originates from the real side.

That is why you cannot reach a host that is only covered by dynamic PAT. If inbound access is needed, you need a static rule or static PAT.

object network SRV
 host 10.10.10.10
 nat (dmz,outside) static 203.0.113.10 unidirectional   ! outbound only

The unidirectional keyword on a static rule suppresses the inbound half, which is occasionally useful for a server that must present a fixed source address outbound but must never be reachable inbound.

03Dynamic PAT

Many real addresses share one mapped address, distinguished by port. The default for internet access, and the most-deployed NAT type anywhere.

Interface PAT

Everything behind the ASA shares the outside interface address. No extra public addresses needed.

object network INSIDE-NET
 subnet 10.1.1.0 255.255.255.0
 nat (inside,outside) dynamic interface
Packet transformation — 10.1.1.50 browsing 8.8.8.8
StageSourceDestination
Inside → ASA10.1.1.50:510008.8.8.8:443
ASA → Outside203.0.113.2:123458.8.8.8:443
Reply in8.8.8.8:443203.0.113.2:12345
ASA → Inside8.8.8.8:44310.1.1.50:51000

PAT to a pool

Spreads translations across several addresses. Needed past roughly 65,000 concurrent translations per mapped address, and useful when an upstream system needs to distinguish groups of users.

object network INSIDE-NET
 subnet 10.1.1.0 255.255.255.0
 nat (inside,outside) dynamic pat-pool PAT-POOL round-robin
  • round-robin — cycle through pool addresses rather than filling one before moving on. Spreads load, but a single host's connections then come from varying addresses, which breaks some session-affinity applications.
  • Without round-robin the ASA exhausts one address before using the next, keeping a host's translations consistent for longer.

Fallback to interface

object network INSIDE-NET
 subnet 10.1.1.0 255.255.255.0
 nat (inside,outside) dynamic pat-pool PAT-POOL interface

The trailing interface makes the interface address a fallback when the pool is exhausted. Cheap insurance against an outage caused by pool exhaustion, and worth adding by default.

Verification

show xlate local 10.1.1.50
show nat pool                             ! utilisation per mapped address
show nat detail | include PAT

! typical xlate output
TCP PAT from inside:10.1.1.50/51000 to outside:203.0.113.2/12345 flags ri idle 0:00:04
Pool exhaustionSymptom: intermittent connection failures for some users, syslog 305006, ASP drop nat-no-xlate-to-pat-pool. Check show nat pool. Fix with a larger pool, extended PAT, or per-session PAT — see the PAT scaling section.

04Dynamic NAT

One-to-one from a pool, with no port translation, for as long as the translation lives. Uncommon today, but it still appears where an application cannot tolerate PAT.

Configuration

object network NAT-POOL
 range 203.0.113.40 203.0.113.60

object network INSIDE-NET
 subnet 10.1.1.0 255.255.255.0
 nat (inside,outside) dynamic NAT-POOL
Packet transformation — ports preserved
StageSourceDestination
Inside → ASA10.1.1.50:510008.8.8.8:443
ASA → Outside203.0.113.408.8.8.8:443

Note the port is unchanged. That is the whole point: protocols that embed or depend on the source port survive, where PAT would break them.

When to use it, and why rarely

  • Use it for legacy applications that cannot cope with port rewriting, or where a downstream system must see one address per host.
  • Avoid it otherwise — the pool is consumed one address per host, so twenty-one addresses serve twenty-one concurrent hosts and no more. When the pool is empty, further hosts simply fail.

Add a PAT fallback so exhaustion degrades instead of failing:

object network INSIDE-NET
 nat (inside,outside) dynamic NAT-POOL interface
Watch the xlate timeoutA dynamic NAT translation holds its pool address until the xlate times out (timeout xlate, default three hours), not until the connection closes. A short burst of hosts can hold the pool empty for a long time afterwards.

05Static NAT

A permanent one-to-one mapping, bidirectional, created at configuration time rather than on first packet. This is how you publish a server.

Publishing a server

object network SRV-WEB
 host 10.10.10.10
 nat (dmz,outside) static 203.0.113.10

! the ACL permits the REAL address, not the mapped one
access-list OUTSIDE_IN extended permit tcp any4 object SRV-WEB eq 443
access-group OUTSIDE_IN in interface outside
Inbound: 198.51.100.5 reaching the published server
StageSourceDestination
Outside → ASA198.51.100.5:49152203.0.113.10:443
After un-NAT198.51.100.5:4915210.10.10.10:443
ACL evaluated against198.51.100.510.10.10.10:443
ASA → DMZ198.51.100.5:4915210.10.10.10:443
The post-8.3 trapUn-NAT happens before the ACL check. Permitting 203.0.113.10 in the outside ACL does nothing — by the time the ACL runs, the destination is already 10.10.10.10. Engineers migrating from 8.2 get this wrong almost every time.

Net-to-net static

Map a whole subnet one-to-one, preserving the host portion.

object network DMZ-NET
 subnet 10.10.10.0 255.255.255.0
 nat (dmz,outside) static 203.0.113.0

10.10.10.10 becomes 203.0.113.10, 10.10.10.25 becomes 203.0.113.25, and so on. Compact, and the usual approach where a provider has given you a matching public block.

Static with an interface mapped address

object network SRV-WEB
 host 10.10.10.10
 nat (dmz,outside) static interface

Maps the server to the outside interface address itself. This consumes the entire address for that one host, so it is almost always wrong — what people usually want here is static PAT, in the next section.

Verification

show xlate | include 203.0.113.10
show nat detail | include SRV-WEB

! static xlates exist before any traffic
NAT from dmz:10.10.10.10 to outside:203.0.113.10 flags sI idle 0:00:00

packet-tracer input outside tcp 198.51.100.5 12345 203.0.113.10 443 detailed

Flag s means static, I identity-free inbound. A static translation appears in show xlate immediately on configuration, unlike a dynamic one — a quick way to confirm the rule parsed as you intended.

06Static PAT — port forwarding

Publish a single service rather than a whole host, so several internal servers can share one public address on different ports.

Forwarding one port

object network SRV-WEB-443
 host 10.10.10.10
 nat (dmz,outside) static interface service tcp 443 443

object network SRV-MAIL-25
 host 10.10.10.20
 nat (dmz,outside) static interface service tcp 25 25

Both servers share the outside interface address, separated by port. Read the service clause as service <protocol> <real-port> <mapped-port>.

Port redirection

Real and mapped ports need not match — publish an internal service on a different external port.

object network SRV-SSH
 host 10.1.1.60
 nat (inside,outside) static interface service tcp 22 2222
Inbound to port 2222, redirected to 22
StageSourceDestination
Outside → ASA198.51.100.5:40000203.0.113.2:2222
After un-NAT198.51.100.5:4000010.1.1.60:22

The ACL permits tcp any4 host 10.1.1.60 eq 22 — the real address and the real port.

Do not forward management to the internetA static PAT of SSH or RDP straight to the internet is a standing invitation. If it must exist, restrict the ACL to known source addresses and put it behind MFA — or use remote access VPN instead, which is what it is for.

Using a service object

object service SVC-HTTPS
 service tcp source eq 443

object network SRV-WEB
 host 10.10.10.10

nat (dmz,outside) source static SRV-WEB SRV-WEB-PUBLIC service SVC-HTTPS SVC-HTTPS

The manual-NAT form, useful when the port mapping must also depend on the destination. Note that in a source static translation the service object describes the source port, which is a frequent source of confusion — for inbound publishing you normally want the auto NAT form above.

Conflicts with ASA services

If the ASA itself listens on a port on that interface, static PAT for the same port collides. The common case is TCP 443 when ASDM or AnyConnect is enabled on the outside interface. Move the ASA's service:

http server enable 8443
ssh version 2
webvpn
 port 4443

Or publish the server on a different public address instead of the interface address.

07Identity NAT and NAT exemption

Translate an address to itself. Sounds pointless until you remember that a matching NAT rule stops evaluation — identity NAT is how you protect traffic from a broader rule further down.

Why it exists

Traffic between two internal networks across the ASA should not be translated. But a catch-all PAT rule would match it and translate it anyway. Identity NAT, placed above that rule, matches first and translates the address to itself — so nothing changes, and evaluation stops before the PAT rule is reached.

Simple identity NAT

object network INSIDE-NET
 subnet 10.1.1.0 255.255.255.0
 nat (inside,dmz) static INSIDE-NET

The auto NAT form. Adequate where the exemption applies to all traffic between that interface pair.

NAT exemption — the form you will actually use

Manual NAT, matching source and destination, placed explicitly at the top of section 1.

nat (inside,outside) 1 source static INSIDE-NET INSIDE-NET \
    destination static REMOTE-NET REMOTE-NET no-proxy-arp route-lookup
Nothing changes — which is the point
StageSourceDestination
Inside → ASA10.1.1.50:51000172.16.5.10:445
ASA → tunnel10.1.1.50:51000172.16.5.10:445

The two keywords matter:

  • no-proxy-arp — the ASA must not answer ARP for 10.1.1.0/24 addresses on the outside, because it does not own them there.
  • route-lookup — use the routing table to pick the egress interface, rather than letting the NAT rule's interface pair divert the traffic.
Placement is the whole gameWrite it as line 1 of section 1. An exemption rule below a catch-all PAT does nothing at all, and this is the single most common reason a site-to-site VPN carries no traffic.

Verifying an exemption

show nat | include 10.1.1.0
packet-tracer input inside tcp 10.1.1.50 51000 172.16.5.10 445 detailed

In the packet-tracer output, the NAT phase should show your exemption rule and an unchanged address. If it shows the PAT rule and a 203.0.113.2 source, the exemption is below it or does not match.

08Twice NAT and policy NAT

Matching source and destination together, so the same source can be translated differently depending on where it is going.

The shape of a manual NAT rule

nat (real-intf,mapped-intf) [line | after-auto] \
    source  static|dynamic  REAL-SRC  MAPPED-SRC \
    destination static MAPPED-DST REAL-DST \
    [service REAL-SVC MAPPED-SVC] \
    [no-proxy-arp] [route-lookup] [unidirectional]
The destination operands are reversedIn the destination static clause the first object is the mapped (what you see on the wire) and the second is the real. This is the opposite order to the source clause, and it catches everyone. Read it as "translate this destination into that one".

Policy NAT: different translation per destination

Internet traffic PATs to the interface, but traffic to a partner must appear as a specific address the partner has whitelisted.

object network PARTNER-NET
 subnet 192.0.2.0 255.255.255.0
object network OUR-PARTNER-IP
 host 203.0.113.50

! specific: to the partner, use the dedicated address
nat (inside,outside) 1 source dynamic INSIDE-NET OUR-PARTNER-IP \
    destination static PARTNER-NET PARTNER-NET

! general: everything else, interface PAT
object network INSIDE-NET
 nat (inside,outside) dynamic interface
Same source, two destinations, two translations
DestinationRule matchedMapped source
192.0.2.10 (partner)Section 1, line 1203.0.113.50
8.8.8.8 (internet)Section 2, auto NAT203.0.113.2

Section 1 is evaluated first, so the specific partner rule wins for partner traffic and everything else falls through to the auto NAT rule. This ordering is precisely why the feature is split into sections.

Dual NAT — translating both ends

Two networks with overlapping address space need to reach each other. Translate both sides so neither sees a conflict.

object network OUR-10NET
 subnet 10.1.1.0 255.255.255.0
object network OUR-10NET-MAPPED
 subnet 192.168.1.0 255.255.255.0
object network THEIR-10NET
 subnet 10.1.1.0 255.255.255.0
object network THEIR-10NET-MAPPED
 subnet 192.168.2.0 255.255.255.0

nat (inside,outside) 1 source static OUR-10NET OUR-10NET-MAPPED \
    destination static THEIR-10NET-MAPPED THEIR-10NET

Our hosts reach theirs by dialling 192.168.2.x; the ASA rewrites that to 10.1.1.x on the way out and our source to 192.168.1.x. Both sides see unique space. This is the standard answer to the overlapping-subnet merger problem, and a classic interview question.

Do not forget DNSDual NAT works at the IP layer only. If hosts resolve names, the DNS answers still contain the untranslated addresses. Either run split DNS or use DNS doctoring.

09Hairpin and U-turn NAT

An internal client reaching an internal server by its public address. Conceptually simple, reliably confusing, and a frequent ticket.

U-turn NAT · 4 stages. Step 3 is what makes the return traffic come back through the ASA.

Why the source must also be translated

If you only un-NAT the destination, the server at 10.10.10.10 receives a packet from 10.1.1.50 — and replies directly to it using its own default gateway, bypassing the ASA. The client then receives a reply from 10.10.10.10 when it was talking to 203.0.113.10, and discards it.

Translating the source to the ASA's interface address forces the reply back through the firewall, which then reverses both translations. This is the whole trick, and the reason a "just un-NAT the destination" configuration half-works in a way that is maddening to diagnose.

U-turn across interfaces: inside client to DMZ server

nat (inside,dmz) 1 source dynamic INSIDE-NET interface \
    destination static SRV-WEB-PUBLIC SRV-WEB

Reads as: for inside traffic heading to 203.0.113.10, rewrite the destination to 10.10.10.10 and the source to the ASA's DMZ interface address.

True hairpin: in and out of the same interface

When client and server are on the same interface, traffic must enter and leave through it. That is blocked by default.

same-security-traffic permit intra-interface

nat (inside,inside) 1 source dynamic INSIDE-NET interface \
    destination static SRV-PUBLIC SRV-REAL
Missing intra-interface permitWithout same-security-traffic permit intra-interface the hairpin silently fails even with a perfect NAT rule. Same applies to VPN clients reaching the internet back out the outside interface.

The better answer, where you can take it

Hairpinning makes the firewall carry traffic that never needed to cross it, and it hides the real client address from the server — which ruins the server's access logs. The cleaner fixes:

  • Split DNS — internal resolvers return 10.10.10.10 for the server's name, so clients go direct and the ASA is never involved.
  • DNS doctoring — the ASA rewrites DNS replies as they pass. See the next section.

Reach for the NAT solution when you do not control DNS, which is most often the case with partner or third-party resolvers.

10DNS doctoring

What it does

The dns keyword on a static NAT rule makes the ASA rewrite the A record inside DNS replies that cross it. An inside client asking a public resolver for www.example.com gets back 10.10.10.10 instead of 203.0.113.10, and connects directly — no hairpin needed.

object network SRV-WEB
 host 10.10.10.10
 nat (dmz,outside) static 203.0.113.10 dns

! DNS inspection must be enabled, which it is by default
policy-map global_policy
 class inspection_default
  inspect dns preset_dns_map
The DNS reply, rewritten in flight
StageA record in the reply
Resolver → ASAwww.example.com → 203.0.113.10
ASA → inside clientwww.example.com → 10.10.10.10

Limits worth knowing

  • DNSSEC breaks it. Rewriting the record invalidates the signature, so a validating resolver rejects the answer. This is increasingly a reason not to use doctoring at all.
  • Encrypted DNS bypasses it. DoH and DoT traffic is opaque to the ASA, and modern clients increasingly default to it.
  • The DNS reply must traverse the ASA for the rewrite to happen — an internal resolver with its own upstream path is untouched.
  • Only A and AAAA records in replies are rewritten, not records inside other message types.
Where this is goingSplit DNS is the durable answer and DNS doctoring is the legacy workaround. Know it because you will meet it in existing configurations, but prefer split DNS in anything you design now.

11NAT with VPN

The interaction that generates more tickets than any other. Worth understanding as a picture before as a configuration.

VPN NAT exemption · the same traffic, two outcomes decided by rule order.

Why it happens

The crypto ACL selects interesting traffic by its post-NAT addresses. If the catch-all PAT rule matched first, the packet's source is now 203.0.113.2 — which does not match a crypto ACL written for 10.1.1.0/24. The packet misses the tunnel and leaves in clear text.

Order of operations explains it exactly: NAT is applied before the crypto map is consulted.

The fix

object network REMOTE-NET
 subnet 172.16.0.0 255.255.0.0

nat (inside,outside) 1 source static INSIDE-NET INSIDE-NET \
    destination static REMOTE-NET REMOTE-NET no-proxy-arp route-lookup

! the crypto ACL then matches
access-list VPN-PARTNER extended permit ip 10.1.1.0 255.255.255.0 172.16.0.0 255.255.0.0

Line 1 places it at the top of section 1, above anything else. Confirm with show nat that it really is first and that it is taking hits.

Deliberate NAT into a tunnel

Sometimes you want translation — the peer has dictated the source range, or your real addresses overlap theirs.

object network OUR-VPN-SOURCE
 subnet 192.168.99.0 255.255.255.0

nat (inside,outside) 1 source dynamic INSIDE-NET OUR-VPN-SOURCE \
    destination static REMOTE-NET REMOTE-NET

! the crypto ACL must use the TRANSLATED source
access-list VPN-PARTNER extended permit ip 192.168.99.0 255.255.255.0 172.16.0.0 255.255.0.0
Crypto ACL follows NATWhen you deliberately NAT into a tunnel, the crypto ACL must describe the post-NAT source. Writing it with the real addresses produces a tunnel that builds phase 1, fails phase 2, and logs 402116.

Remote access VPN

! exempt pool-to-inside traffic from PAT
object network VPN-POOL
 subnet 10.9.0.0 255.255.255.0

nat (outside,inside) 1 source static VPN-POOL VPN-POOL \
    destination static INSIDE-NET INSIDE-NET no-proxy-arp route-lookup

! and if clients browse the internet through the ASA
same-security-traffic permit intra-interface
nat (outside,outside) source dynamic VPN-POOL interface

Two separate needs: exemption so clients reach internal resources untranslated, and a hairpin PAT so their internet traffic can leave. Missing the second is the classic "VPN connects but no internet" fault.

12PAT scaling and tuning

Each mapped address offers roughly 65,000 ports. On a large network that runs out, and the symptoms are intermittent rather than obvious.

Per-session PAT

By default the ASA holds a PAT translation for a short period after the connection closes, in case of late packets. Per-session PAT tears the xlate down immediately with the connection, which hugely increases the achievable connection rate.

show run all xlate                         ! see the defaults

xlate per-session permit tcp any4 any4
xlate per-session permit udp any4 any4 eq domain

TCP and DNS over UDP are per-session by default on modern releases. Other UDP traffic is multi-session, because many UDP applications expect the mapping to persist — so be careful about blanket per-session UDP rules.

First thing to check on PAT exhaustionIf connection rate is high but concurrent connections are modest, a multi-session default is probably holding xlates after teardown. show xlate count against show conn count tells you — far more xlates than conns is the signature.

Extended PAT

object network INSIDE-NET
 nat (inside,outside) dynamic pat-pool PAT-POOL extended

Normally a mapped address and port pair must be unique. Extended PAT makes the translation unique per destination, so the same mapped port can be reused for different destinations — multiplying capacity substantially.

The cost is memory and the fact that some stateful upstream devices dislike it. It also cannot be combined with certain other options; check the release notes for your version.

Port range options

KeywordEffect
flatUse 1024–65535 as one flat range instead of the three-tier allocation. More usable ports per address
include-reserveAlso use 1–1023. Use with flat, and only where nothing upstream objects to low source ports
round-robinCycle through pool addresses rather than filling each in turn
extendedPer-destination uniqueness, as above
 
object network INSIDE-NET
 nat (inside,outside) dynamic pat-pool PAT-POOL flat include-reserve round-robin

Monitoring

show nat pool
show xlate count
show conn count
show local-host | include host|conns
show perfmon | include xlate

Build a baseline before you need it. show nat pool gives per-address port allocation, and a single address climbing toward its ceiling while the others sit idle usually means round-robin is off and the pool is being filled sequentially — which is fine, until it is not.

The three flavours

NAT64 outline

object network IPV6-CLIENTS
 subnet 2001:db8:1::/64

object network PAT-POOL-V4
 range 203.0.113.70 203.0.113.79

! source: IPv6 clients PAT to an IPv4 pool
nat (inside,outside) source dynamic IPV6-CLIENTS pat-pool PAT-POOL-V4

! destination: the well-known NAT64 prefix maps to real IPv4
object network NAT64-PREFIX
 subnet 64:ff9b::/96

nat (inside,outside) source dynamic IPV6-CLIENTS pat-pool PAT-POOL-V4 \

DNS64 is the other half: a resolver that synthesises a AAAA record inside 64:ff9b::/96 when a name has only an A record, so the client sends IPv6 traffic that the ASA can translate. The ASA does not provide DNS64 itself — that is your resolver's job.

Check the versionIPv6 NAT syntax and capability changed across releases, and some forms are not supported in every mode. Validate against the configuration guide for your exact version before building this in production rather than copying any example, including this one.

14Troubleshooting NAT

The workflow

  1. packet-tracer the flow and read the UN-NAT and NAT phases. They name the exact rule that matched.
  2. show nat — is that the rule you expected, and where does yours sit relative to it?
  3. show nat detail — confirm the objects expanded to the addresses you think they did.
  4. show xlate local <host> — what translation actually exists right now?
  5. clear asp drop, reproduce, show asp drop — any NAT-related drops?
  6. show logging | include 305 — the 305xxx family is all translation messages.

Reading packet-tracer for NAT

packet-tracer input inside tcp 10.1.1.50 51000 172.16.5.10 445 detailed

Phase: 2
Type: UN-NAT
Subtype: static
Result: ALLOW
Config:
nat (inside,outside) source static INSIDE-NET INSIDE-NET destination static REMOTE-NET REMOTE-NET
Additional Information:

The Config: block is the authoritative answer to "which rule matched". If it shows a rule you did not expect, you have a shadowing problem, not a syntax problem.
