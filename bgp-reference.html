01Fundamentals

BGP is not an IGP with more knobs. It is a policy engine that happens to carry routes, and almost every design decision follows from that.

Path-vector protocol

BGP does not compute a shortest path from a link-state database or exchange distance vectors with metrics. Each route carries the explicit list of autonomous systems it has traversed. That list serves two purposes: loop detection (an AS rejects a route containing its own ASN) and a crude distance measure.

Because the path is explicit rather than computed, BGP can be steered. That is why it is the inter-domain protocol: AS 65001 can decide, for business rather than topological reasons, that traffic should leave via one provider rather than another.

The mental modelAn IGP answers "what is the shortest way there?" BGP answers "whose network am I willing to use to get there, and who am I willing to carry traffic for?" Those are policy questions.

The iBGP split-horizon ruleThis single rule is behind the full-mesh requirement, route reflectors and confederations. A route learned from one iBGP peer is not passed to another iBGP peer — because there is no AS_PATH change inside an AS, so there would be no loop protection. Every iBGP design question is a consequence of this.

The three tables

  • Adj-RIB-In — everything received from a peer, before inbound policy. Only kept if soft-reconfiguration inbound is configured, or reconstructed via route refresh.
  • Loc-RIB — what survived inbound policy; the BGP table proper, where best-path runs. This is what show bgp displays.
  • Adj-RIB-Out — per-peer, what is advertised after outbound policy.

Only the best path for a prefix is installed in the routing table and advertised onward. BGP holds all the alternatives but shows the world one answer per prefix, which is why show bgp <prefix> often reveals several paths where show ip route shows one.

Transport

BGP runs over TCP port 179. The speaker with the higher IP address usually ends up as the TCP client in a collision, though either side may initiate. TCP gives reliable, ordered delivery, so BGP has no retransmission logic of its own — and inherits TCP's behaviour, including the need for MSS and path MTU to work correctly.

Peers are statically configured, never discovered. That is deliberate: you should know exactly who you are exchanging routing information with. (BGP dynamic neighbors exist for listen ranges, but the range is still explicitly configured.)

03Messages and the finite state machine

Message types

2UPDATEWithdrawn routes, path attributes, and NLRI. One UPDATE can withdraw many prefixes and advertise many that share one attribute set

4KEEPALIVENothing but the 19-byte header. Sent at one third of the hold time
5ROUTE-REFRESH"Resend me everything" — the modern alternative to storing an Adj-RIB-In

Every message starts with a 19-byte header: a 16-byte marker (all ones), a 2-byte length, and a 1-byte type. Maximum message size is 4096 bytes, extended to 65535 by RFC 8654 where both peers support it.

Capabilities

Negotiated in the OPEN message. If a peer advertises a capability you do not support, you ignore it; if you require one it does not have, the session may fail. Common ones:

  • Multiprotocol (MP-BGP) — which AFI/SAFI pairs this session will carry.
  • Route refresh — allows soft reconfiguration without storing the inbound RIB.
  • 4-byte ASN — without it, AS_TRANS (23456) substitution happens.
  • Graceful restart — forwarding continues while the control plane restarts.
  • Add-path — advertise more than one path per prefix.

A number in the last column means Established, and the number is prefixes received. A word means it is not up, and the word tells you where to look. Idle (Admin) means someone shut it down.

The quickest diagnostic in BGPActive means "TCP will not come up". Check reachability, the ACL, the source address and the TTL. OpenSent means "TCP is fine but we disagree about something in OPEN" — almost always the remote ASN. That one distinction saves enormous amounts of time.

Timers

router bgp 65001
 timers bgp 60 180                        ! keepalive, holdtime — global default
 neighbor 203.0.113.1 timers 10 30        ! per-neighbor override
 neighbor 203.0.113.1 fall-over bfd       ! sub-second via BFD instead

The hold time is negotiated down to the lower of the two peers' values. A hold time of 0 disables the timer entirely. Keepalive is sent at one third of the agreed hold time.

Aggressive timers detect failure faster but cost CPU and risk flapping on a loaded router. The better answer is BFD: it detects loss in milliseconds in a dedicated, lightweight process, and BGP simply subscribes to it. For a directly connected eBGP peer, fall-over bfd plus default BGP timers beats tuning the BGP timers down.

04Neighbor establishment

eBGP: the TTL rule

eBGP sends packets with TTL 1 by default, expecting a directly connected peer. A multihop session fails silently unless you say otherwise.

! peer two hops away
neighbor 203.0.113.9 ebgp-multihop 2

! better: GTSM — accept only packets that arrived with TTL >= 254
neighbor 203.0.113.9 ttl-security hops 2

ttl-security is strictly better than ebgp-multihop where both ends support it. Multihop raises the outgoing TTL; TTL security requires a high incoming TTL, so a spoofed packet from further away is dropped in hardware before BGP sees it. The two are mutually exclusive on the same neighbor.

iBGP: peer with loopbacks

neighbor 10.0.0.3 remote-as 65001
neighbor 10.0.0.3 update-source Loopback0

Always peer iBGP loopback to loopback, and carry the loopbacks in the IGP. The session then survives any single link failure as long as the IGP can find another path. Peering on physical interfaces means the BGP session dies whenever that interface does, even when connectivity still exists.

update-source must be symmetricIf R1 peers to 10.0.0.3 but sources from its physical interface, R3 sees an incoming connection from an address it has no neighbor statement for, and refuses it. The session sits in Active or Idle. Both ends must agree on the addresses.

Authentication

neighbor 203.0.113.1 password MySecret      ! TCP MD5, RFC 2385

TCP MD5 is still the near-universal mechanism for eBGP sessions with providers. TCP-AO (RFC 5925) is the modern replacement with better algorithm agility, but deployment remains thin.

A password mismatch produces a distinctive symptom: the session never establishes, and the log shows repeated MD5 failures rather than a BGP NOTIFICATION — because the failure is below BGP, in TCP.

%TCP-6-BADAUTH: Invalid MD5 digest from 203.0.113.1:179 to 203.0.113.2:179

How an attribute is encoded

Each attribute in an UPDATE is a TLV: a flags octet, a type code octet, a length (one or two octets), and the value. The flags are what determine how a router that does not understand the attribute must behave.

Attribute flags — the first octet
BitMaskNameMeaning
00x80Optional0 = well-known (every implementation must support it), 1 = optional
10x40Transitive0 = non-transitive, 1 = transitive. Well-known attributes are always transitive
20x20PartialSet by a router that passed on an optional transitive attribute it did not recognise
30x10Extended length0 = 1-octet length field, 1 = 2-octet. Needed once the value exceeds 255 bytes
4–7—UnusedMust be zero

So the two flag bits give four classes, and each has a defined handling rule when the receiving router does not recognise the type code:

  • Well-known mandatory and discretionary — must be recognised. An unrecognised well-known attribute is an error and triggers a NOTIFICATION, dropping the session.
  • Optional transitive — keep it, set the Partial bit, pass it on unchanged. This is how new attributes propagate across routers that predate them.
  • Optional non-transitive — silently discard. The attribute never leaves the AS boundary it arrived at.
Why this matters in practiceOptional transitive is why COMMUNITY survives transit through networks that ignore it, and why MED (optional non-transitive) stops at the first AS. It also explains a real failure class: a malformed optional transitive attribute propagated by routers that did not parse it, reaching one that did and resetting its sessions. RFC 7606 added "treat as withdraw" handling precisely so a bad attribute no longer drops the session.

AS_PATH

An ordered list of the ASes traversed, prepended on every eBGP advertisement. Segment types: AS_SEQUENCE (ordered, the normal case), AS_SET (unordered, produced by aggregation with as-set), and the confederation variants AS_CONFED_SEQUENCE and AS_CONFED_SET.

Loop prevention: if a router sees its own ASN in the received AS_PATH, it discards the route. Two commands override this, both of which should make you nervous:

neighbor X allowas-in 2            ! accept my own ASN up to N times
neighbor X as-override             ! replace customer ASN with mine (MPLS VPN)
allowas-in disables loop preventionIt is legitimate in MPLS L3VPN hub-and-spoke designs where the same ASN genuinely appears twice. Anywhere else it is a workaround for a design problem, and it can create a real routing loop. Document why it is there.

NEXT_HOP — the attribute that causes the most confusion

The rules:

  • eBGP — the advertising router sets NEXT_HOP to itself.
  • iBGP — NEXT_HOP is passed along unchanged. A route R1 learned from ISP-A keeps 203.0.113.1 as its next hop when R1 tells R3 about it.
  • On a shared multi-access segment, a router may advertise a third party's address as next hop if that is a better path. This is "third-party next hop".

That second rule is why next-hop-self exists. R3 has no route to 203.0.113.1 unless you carry the provider link in the IGP — which you should not. So the route is received, held in the BGP table, and marked inaccessible.

LOCAL_PREF — outbound policy

Default 100. Highest wins. Sent to iBGP peers, never to eBGP peers, so it is the tool for telling your own AS which exit to use.

route-map PREFER-ISP-A permit 10
 set local-preference 200
!
router bgp 65001
 address-family ipv4 unicast
  neighbor 203.0.113.1 route-map PREFER-ISP-A in

Now every router in AS 65001 prefers routes learned via ISP-A, because R1 raises the LOCAL_PREF on ingress and floods that to the iBGP mesh. This controls outbound traffic.

MED — inbound hint

Also called the external metric. Lowest wins. Sent to an eBGP peer to say "if you have two ways into my AS, prefer this one". It is non-transitive: the neighbouring AS may use it, but does not pass it on.

route-map SET-MED permit 10
 set metric 50
!
neighbor 203.0.113.1 route-map SET-MED out

By default MED is only compared between paths from the same neighbouring AS. Two modifiers change that:

bgp always-compare-med          ! compare across different ASes — use with care
bgp deterministic-med           ! group paths by AS before comparing — always set this
bgp bestpath med missing-as-worst
MED is advisoryYour provider is under no obligation to honour it, and many strip or ignore it. Before building an inbound traffic-engineering design on MED, confirm with the provider that they accept it. AS prepending and communities are usually more reliable levers.

WEIGHT — Cisco only, this router only

Default 0 for learned routes, 32768 for locally originated. Highest wins, and it is checked first in best-path. It is never advertised anywhere.

neighbor 203.0.113.1 weight 100

Because it is purely local, weight is excellent for a quick fix on one router and dangerous as a design tool — it creates an inconsistency the rest of the AS cannot see. Prefer LOCAL_PREF for anything intended to be a policy.

ORIGIN

Three values, preferred in this order at step 5: IGP (i) < EGP (e) < Incomplete (?). Set automatically by how the route entered BGP — network gives IGP, redistribution gives Incomplete, and EGP is a historical artefact you will essentially never see.

It can be set explicitly, which is occasionally the cleanest tie-breaker when you want to de-preference a path without touching AS_PATH or LOCAL_PREF:

route-map DEPREF permit 10
 set origin incomplete
A quiet cause of surpriseRoutes you redistribute carry Incomplete and lose at step 5 against an otherwise identical route someone else originated with network. If your own prefix is being reached via a longer path, check the origin codes on both.

ATOMIC_AGGREGATE and AGGREGATOR

ATOMIC_AGGREGATE is a zero-length flag meaning "a less specific route was selected over more specific ones, and some path information was lost". It warns downstream routers that the AS_PATH may not list every AS actually traversed.

AGGREGATOR carries the ASN and router ID of whoever performed the aggregation — useful for tracing where a summary was created.

Using as-set on your aggregate avoids setting ATOMIC_AGGREGATE, because the AS_SET preserves the path information instead of discarding it.

AIGP Accumulated IGP metric, RFC 7311

Carries an accumulated IGP cost across BGP, so that a path's true end-to-end metric can be compared rather than only the local IGP distance to the next hop. It inserts into best-path between steps 3 and 4 — after locally originated, before AS_PATH.

The use case is a single administrative domain split into multiple ASes or regions, where you want BGP to behave like one large IGP. Seamless MPLS designs and some SR deployments depend on it.

router bgp 65001
 address-family ipv4 unicast
  bgp bestpath aigp ignore          ! opt out of AIGP comparison
 !
 neighbor 10.0.0.2 aigp
 neighbor 10.0.0.2 aigp send-cost-community 100 poi igp-cost
!
route-map SET-AIGP permit 10
 set aigp-metric 500
 set aigp-metric igp-cost          ! derive from the IGP metric
AIGP is domain-scopedIt is optional non-transitive and must only be used within a trusted domain. Accepting AIGP from an external peer would let them manipulate your path selection at a step above AS_PATH. Never enable it on an internet-facing eBGP session.

06Best path selection

The algorithm is a sequence of tie-breakers. It stops at the first step that distinguishes the candidates, which is why a change at step 2 makes everything below it irrelevant.

Troubleshooting habitWhen asked "why did BGP pick that path?", walk the list from the top and stop at the first difference. Do not start from AS_PATH just because it is the famous one.

Multipath

router bgp 65001
 address-family ipv4 unicast
  maximum-paths 4                    ! eBGP
  maximum-paths ibgp 4               ! iBGP
  maximum-paths eibgp 4              ! MPLS VPN only
  bgp bestpath as-path multipath-relax

For paths to be bundled they must be equal through every step up to the multipath check — same weight, local-pref, AS_PATH length, origin and MED. By default they must also come from the same neighbouring AS; multipath-relax drops that requirement so you can load-share across two different providers.

Only one path is still the best path and only that one is advertised onward. Multipath affects forwarding, not advertisement.

bgp bestpath as-path ignoreSkip step 4 entirely. Very rarely appropriate
bgp bestpath med missing-as-worstTreat a missing MED as infinity rather than 0
Consistency matters more than the settingBest-path modifiers must be identical on every router in the AS. A mix of always-compare-med on some routers and not others can produce a persistent forwarding loop, because two routers reach different conclusions about the same prefix.

07iBGP, route reflectors and confederations

The full-mesh problem

Because iBGP never re-advertises between iBGP peers, every iBGP speaker must hear every route directly. That means a full mesh of n(n−1)/2 sessions. Ten routers is 45 sessions; fifty routers is 1,225. Adding one router means touching every other router.

Two solutions exist, and in practice everyone uses the first.

iBGP scaling · full mesh against a single reflector, six routers.

Route reflectors

A route reflector is permitted to break the split-horizon rule. Its peers are either clients or non-clients, and the reflection rules are:

  • Route learned from a client → reflect to all clients and all non-clients.
  • Route learned from a non-client → reflect to clients only.
  • Route learned from an eBGP peer → send to everyone, as normal.

Non-clients must still be fully meshed among themselves.

router bgp 65001
 bgp cluster-id 10.0.0.3
 address-family ipv4 unicast
  neighbor 10.0.0.1 route-reflector-client
  neighbor 10.0.0.2 route-reflector-client

Only the reflector is configured. Clients are ordinary iBGP speakers and need no special configuration — a frequent exam question.

Reflector loop prevention

Since reflection breaks split horizon, two attributes replace it:

  • ORIGINATOR_ID — the router ID of the speaker that first injected the route into the AS. A router receiving a route with its own ORIGINATOR_ID discards it.
  • CLUSTER_LIST — each reflector prepends its cluster ID. A reflector seeing its own cluster ID discards the route.
Cluster-id and redundant reflectorsTwo reflectors serving the same clients should normally have different cluster IDs. Giving them the same cluster ID suppresses the second copy of each route (by cluster-list loop detection), which saves memory but removes the path diversity that the redundancy was for. Unless you are deliberately optimising memory, leave them distinct — the default is each router's own BGP router ID.

Reflector placement

The reflector chooses one best path and reflects only that. If the reflector's view of the topology differs from a client's, the client can be sent a path that is not optimal from its own position — or, worse, a persistent loop in pathological designs.

Mitigations: place reflectors so their IGP view resembles their clients', use add-path to advertise more than one path per prefix, or deploy BGP ORR (Optimal Route Reflection) where supported, which lets the reflector compute best paths from the client's perspective.

Confederations

Split the AS into sub-ASes. Within a sub-AS, normal iBGP rules apply; between sub-ASes you run confederation eBGP, which prepends to AS_CONFED_SEQUENCE. The outside world sees only the confederation ID.

router bgp 65501
 bgp confederation identifier 65001
 bgp confederation peers 65502 65503
 neighbor 10.1.0.2 remote-as 65502

Confederation eBGP preserves LOCAL_PREF and does not change NEXT_HOP by default, so it behaves more like iBGP than true eBGP.

In practice confederations are rare. They are harder to operate, harder to troubleshoot, and route reflectors solve the same problem with less ceremony. Know them for interviews and for the handful of large networks that adopted them early and never migrated.

08Originating and aggregating routes

The network command

router bgp 65001
 address-family ipv4 unicast
  network 192.0.2.0 mask 255.255.255.0

This does not "advertise an interface". It says: if an exactly matching prefix exists in the routing table, inject it into BGP. The mask must match exactly. network 192.0.2.0 mask 255.255.255.0 does nothing if the RIB only holds 192.0.2.0/25 and 192.0.2.128/25.

The usual fix is a pull-up static route to Null0, which guarantees the prefix exists:

ip route 192.0.2.0 255.255.255.0 Null0 250

Origin code is set to IGP (i). The high administrative distance keeps it out of the way of real routes.

Why network is preferred over redistributeIt is explicit. Every prefix you originate is one line you wrote deliberately. Redistribution injects whatever happens to be in the IGP, which is how organisations accidentally announce internal space to the internet.

Redistribution

router bgp 65001
 address-family ipv4 unicast
  redistribute ospf 1 route-map OSPF-TO-BGP

Origin becomes Incomplete (?), which loses at step 5 of best-path against an otherwise identical IGP-origin route. Always attach a route-map that explicitly permits only what you intend.

Never redistribute BGP into your IGPThe full table is close to a million prefixes. Redistributing it into OSPF or EIGRP will take the network down, and it is a mistake that has caused real outages. If internal routers need internet reachability, give them a default route.

Conditional advertisement

Advertise a prefix only when some other prefix is absent — the primary/backup pattern that does not depend on the other provider withdrawing anything.

router bgp 65001
 address-family ipv4 unicast
  neighbor 198.51.100.1 advertise-map ADVERTISE-BACKUP non-exist-map CHECK-PRIMARY
!
! WHAT to advertise when the condition fires
ip prefix-list OUR-PREFIX seq 5 permit 192.0.2.0/24
route-map ADVERTISE-BACKUP permit 10
 match ip address prefix-list OUR-PREFIX
!
! WHAT to watch for. While this is present, stay silent.
ip prefix-list PRIMARY-LEARNED seq 5 permit 10.99.99.0/24
route-map CHECK-PRIMARY permit 10
 match ip address prefix-list PRIMARY-LEARNED

While a prefix matching CHECK-PRIMARY exists in the BGP table, nothing is advertised to ISP-B. When it disappears — because the primary path is gone — the backup advertisement starts.

R1# show bgp ipv4 unicast neighbors 198.51.100.1 | include Condition
  Condition-map CHECK-PRIMARY, Advertise-map ADVERTISE-BACKUP, status: Withdraw
! status Withdraw = condition present, not advertising
! status Advertise = condition gone, advertising the backup
Pick a sentinel you trustThe watched prefix should be something that genuinely disappears when the primary path fails — a prefix originated only by the primary provider, or a loopback behind the primary link. Watching a prefix that is reachable via both providers means the condition never fires.

There is also an exist-map variant: advertise while the watched prefix is present, rather than while it is absent. Same syntax, inverted logic.

Distribute-list

The original filtering mechanism, using an ACL instead of a prefix-list. Still appears in older configurations, and worth understanding because its extended ACL form behaves in a way nobody guesses correctly.

! Standard ACL form — matches the NETWORK ADDRESS only.
! Cannot distinguish 192.0.2.0/24 from 192.0.2.0/26.

!
router bgp 65001
 address-family ipv4 unicast
  neighbor 203.0.113.1 distribute-list 10 out
The extended ACL form is not what it looks likeIn a BGP distribute-list, an extended ACL does not mean "source and destination". The source fields match the network address, and the destination fields match the subnet mask. It is a two-part prefix matcher wearing an ACL's clothes.
! Read this as: network 192.0.2.0 exactly, mask 255.255.255.0 exactly
!              ^^^^ source ^^^^        ^^^^ destination ^^^^
access-list 100 permit ip host 192.0.2.0 host 255.255.255.0

! Any prefix in 192.0.0.0/16 with a /24 mask
access-list 101 permit ip 192.0.0.0 0.0.255.255 host 255.255.255.0

! Any prefix in 10.0.0.0/8 with a mask from /24 to /32
! (the destination wildcard 0.0.0.255 lets the last octet vary)
access-list 102 permit ip 10.0.0.0 0.255.255.255 255.255.255.0 0.0.0.255

!
 neighbor 203.0.113.1 distribute-list 100 out

The prefix-list equivalents are permit 192.0.2.0/24, permit 192.0.0.0/16 ge 24 le 24 and permit 10.0.0.0/8 ge 24 — obviously clearer, which is why prefix-lists won.

When you still meet itMigrating an old configuration, or on a platform where someone built the policy years ago. Translate to prefix-lists when you touch it, and verify the translation with show bgp ipv4 unicast neighbors X advertised-routes before and after — mis-translating the mask semantics is an easy way to leak.

Prefix lists

ip prefix-list OUR-PREFIXES seq 5 permit 192.0.2.0/24
ip prefix-list OUR-PREFIXES seq 10 deny 0.0.0.0/0 le 32

ip prefix-list FROM-ISP seq 5 deny 0.0.0.0/0
ip prefix-list FROM-ISP seq 10 deny 10.0.0.0/8 le 32
ip prefix-list FROM-ISP seq 15 deny 172.16.0.0/12 le 32
ip prefix-list FROM-ISP seq 20 deny 192.168.0.0/16 le 32
ip prefix-list FROM-ISP seq 25 deny 0.0.0.0/0 ge 25     ! no /25 or longer
ip prefix-list FROM-ISP seq 30 permit 0.0.0.0/0 le 24

ge and le operate on the prefix length, not the address. 0.0.0.0/0 le 24 means "any prefix with a mask of /24 or shorter". There is an implicit deny at the end.

Minimum safe eBGP hygieneOutbound: permit only your own prefixes, explicitly listed. Inbound: deny RFC 1918, deny your own prefixes coming back, deny the default unless you asked for it, deny anything longer than /24. These four lines prevent most self-inflicted incidents.

Route maps

route-map continue

Normally processing stops at the first matching clause. continue carries on to a later clause, so several sets can be applied to one route without duplicating match logic.

route-map LAYERED permit 10
 match ip address prefix-list CUSTOMER
 set community 65001:2000 additive
 continue 30
!
route-map LAYERED permit 20
 match ip address prefix-list PEER
 set community 65001:3000 additive
 continue 30
!
route-map LAYERED permit 30
 set local-preference 150
 set origin igp

Both customer and peer routes get their own community and the common local-preference, without repeating the local-preference in every clause. continue with no argument moves to the next clause in sequence.

continue makes route-maps harder to readIt is genuinely useful for layered policy, but a route-map with several continue statements is difficult for the next engineer to trace. Comment every one, and prefer a flatter structure where the duplication is small.

Policy lists

A reusable bundle of match clauses. Define a common matching condition once and reference it from several route-maps.

Matches inside a policy list are ANDed, as they would be inside a route-map clause. Referencing several policy lists in one clause ORs them.

table-map

Applied between the BGP table and the RIB. It can modify attributes as routes are installed, or — with the filter keyword — prevent installation entirely while keeping the route in BGP for onward advertisement.

router bgp 65001
 address-family ipv4 unicast
  table-map SET-INDEX
  table-map FILTER-RIB filter        ! keep in BGP, do not install in RIB
!
route-map FILTER-RIB deny 10
 match ip address prefix-list DO-NOT-INSTALL
route-map FILTER-RIB permit 20

The filter form matters on a route server or a route reflector that should propagate routes without forwarding along them itself. It is also used to keep a large table out of a FIB that cannot hold it, while still reflecting to clients.

ORF — outbound route filtering

Push your inbound prefix-list to the peer, so they filter before transmitting. Saves bandwidth, memory and convergence time — you never receive the routes at all.

router bgp 65001
 neighbor 203.0.113.1 capability orf prefix-list both
 address-family ipv4 unicast
  neighbor 203.0.113.1 prefix-list ONLY-WHAT-I-NEED in
!
! push the current filter to the peer
clear bgp ipv4 unicast 203.0.113.1 in prefix-filter

show bgp ipv4 unicast neighbors 203.0.113.1 | include ORF
show bgp ipv4 unicast neighbors 203.0.113.1 received prefix-filter

both means send and receive. The capability must be supported on both sides; many providers do not offer it, so treat it as an optimisation to ask about rather than to depend on.

Where each filter applies, and in what order

All configured filters must pass — it is an AND, not a first-match. So the order rarely changes whether a route survives. It matters only when a route-map sets an attribute and another filter matches on that attribute.

DirectionCommonly documented order
Inboundroute-map → filter-list → prefix-list / distribute-list
Outboundprefix-list / distribute-list → filter-list → route-map
Do not build a design on this orderThe documented sequence has varied between releases and platforms, and it is widely misquoted. If your policy depends on one filter seeing the output of another, restructure it into a single route-map instead — where the order is explicit and visible. Verify any assumption with show bgp ipv4 unicast neighbors X advertised-routes on your actual code.

A practical rule: use one route-map per neighbour per direction, with prefix-lists and AS-path lists referenced from inside it. You then have a single ordered document describing the policy, rather than three independent filters whose interaction you have to reason about.

Applying policy without dropping the session

! modern: uses the route-refresh capability, no extra memory
clear bgp ipv4 unicast 203.0.113.1 soft in
clear bgp ipv4 unicast 203.0.113.1 soft out
clear bgp ipv4 unicast * soft

! legacy: stores the unfiltered Adj-RIB-In locally
neighbor 203.0.113.1 soft-reconfiguration inbound

If both peers support route refresh — essentially all modern code — you never need soft-reconfiguration inbound, and storing the full table twice on a router carrying several full feeds is a real memory cost.

The one thing it still gives you is show bgp neighbors X received-routes, which shows what arrived before inbound policy. Without it you only get routes, which is post-policy. On a lab or a troubleshooting-heavy edge router that visibility can be worth the memory.

Never use a hard clear in productionclear ip bgp * tears every session down and reconverges the whole table. On a router with full feeds that is minutes of outage. Always soft.

10Communities

A 32-bit tag you attach to a route so that some other router — often in someone else's AS — can act on it without having to match prefixes.

Formats

  • Extended — 64 bits, used for route targets in MPLS VPN and similar.
  • Large (RFC 8092) — three 32-bit fields, ASN:function:parameter. Designed for 4-byte ASNs, which do not fit in the standard format.

Most transit providers publish a community list letting you control their behaviour. Typical offerings:

neighbor 203.0.113.1 route-map FROM-ISP-A-IN in
! on R2
neighbor 198.51.100.1 route-map FROM-ISP-B-IN in

Refinements: prefer whichever provider originates or is closest to a given destination by matching AS_PATH; accept a default from the cheaper provider and full routes from the better-connected one; or use per-prefix policy for the handful of destinations that actually matter.

How much table do you need?

OptionMemoryGives you
Default route only from bothMinimalFailover, no path selection. Fine for most enterprises
Default + customer routesModestDirect path to each provider's own customers, default for the rest

The IPv4 table passed 900,000 prefixes and continues to grow, so "full tables" is a hardware commitment that must be reviewed against the platform's FIB scale, not just its RAM. For an enterprise whose goal is resilience rather than optimality, taking defaults from both providers is usually the right engineering answer and is often dismissed too quickly.

Controlling inbound traffic

In rough order of reliability:

  1. Provider communities — the most precise, because they act inside the provider's network. Always the first choice where offered.
  2. More-specific advertisements — the most forceful. A /24 always beats a /23 regardless of AS_PATH, because longest-prefix match happens before any BGP policy. Also the most antisocial: it adds entries to every table on the internet.
  3. AS prepending — blunt but universally supported. Only influences networks for which AS_PATH length is the deciding step.
  4. MED — only works between two links to the same provider, and only if they honour it.
route-map PREPEND-TO-B permit 10
 set as-path prepend 65001 65001 65001
!
neighbor 198.51.100.1 route-map PREPEND-TO-B out
Prepending has diminishing returnsThree prepends is usually enough. Beyond that you are only affecting networks whose decision reaches step 4 — and many large networks set LOCAL_PREF at step 2 based on their own commercial relationships, so your prepends never get evaluated. If ten prepends "do not work", that is why, and adding more will not help.

A worked split: primary and backup

Goal: all traffic via ISP-A, ISP-B only on failure.

! OUTBOUND — prefer ISP-A
! R1
route-map ISP-A-IN permit 10

! R2
route-map ISP-B-IN permit 10

neighbor 198.51.100.1 route-map ISP-B-IN in

12Scaling and stability

Maximum prefix

neighbor 203.0.113.1 maximum-prefix 1000000 90 restart 15
neighbor 10.0.0.5 maximum-prefix 100 80 warning-only

Protects you from a peer leaking the full table. The threshold percentage triggers a warning log; exceeding the limit tears the session down. restart N brings it back automatically after N minutes; warning-only never drops it.

Set it on every eBGP peer. For a customer or partner expected to send a handful of prefixes, set it tight — a limit of 100 on a peer that should send five will catch a leak before it propagates.

Route dampening

bgp dampening 15 750 2000 60
!            |   |    |    +-- max suppress time, minutes
!            |   |    +------- suppress threshold
!            |   +------------ reuse threshold
!            +---------------- half-life, minutes

show bgp ipv4 unicast dampening dampened-paths
show bgp ipv4 unicast dampening flap-statistics
clear bgp ipv4 unicast dampening 192.0.2.0 255.255.255.0

Each flap adds a penalty of 1000. Above the suppress threshold the route is withheld; the penalty decays exponentially and the route returns below the reuse threshold.

Dampening is largely deprecatedRIPE recommended against the original aggressive parameters because they suppressed stable prefixes for far too long after brief flaps — sometimes an hour for a few seconds of instability. If you must use it, use the far gentler RIPE-recommended values, and apply it only to longer prefixes. Most networks simply do not run it any more.

Graceful restart and NSR

  • Graceful restart — the restarting router asks peers to keep forwarding using the stale routes while its control plane recovers. Requires both ends to support it, and depends on the forwarding plane surviving the restart.
  • NSR (Non-Stop Routing) — BGP state is replicated to a standby route processor, so a switchover is invisible to peers. No peer cooperation needed, but it requires dual-RP hardware.
bgp graceful-restart
bgp graceful-restart restart-time 120
bgp graceful-restart stalepath-time 360

There is a trade-off: graceful restart keeps traffic flowing through a router whose control plane has failed, which is right if the failure is transient and wrong if the router is genuinely broken.

Convergence: PIC and add-path

  • BGP PIC (Prefix Independent Convergence) — pre-installs a backup next hop in the FIB so failover does not require reconverging each prefix individually. Convergence time stops scaling with prefix count, which matters enormously with a full table.
  • Add-path — lets a speaker advertise several paths for the same prefix instead of only the best. Essential for making PIC effective behind a route reflector, which would otherwise hide the alternatives.
address-family ipv4 unicast
 bgp additional-paths select best 2
 bgp additional-paths send receive
 neighbor 10.0.0.1 additional-paths send
 bgp recursion host

Update groups

show bgp ipv4 unicast update-group
show bgp ipv4 unicast update-group summary

IOS automatically groups neighbors with identical outbound policy and computes one update per group. Giving peers different outbound route-maps splits them into separate groups and multiplies CPU work at convergence. If you have hundreds of peers, check the group count — many groups with one member each means your policy is less uniform than it could be.

IPv6

MPLS L3VPN in brief

  • RD (Route Distinguisher) — 64 bits prepended to an IPv4 prefix to make it unique across VRFs. Purely about uniqueness; it carries no policy meaning.
  • RT (Route Target) — an extended community controlling which VRFs import and export the route. This is where the policy lives.
vrf definition CUSTOMER-A

  route-target export 65001:100
  route-target import 65001:100

  neighbor 10.0.0.3 activate
  neighbor 10.0.0.3 send-community extended

RD unique per VRF per PE, RT shared to define the VPN topology. Hub-and-spoke VPNs are built by asymmetric RT import and export, which is a common interview question.

14Security

The threat model

BGP has no built-in way to verify that an AS is entitled to originate a prefix, or that an advertised path was really traversed. Three consequences:

  • Prefix hijack — an AS announces someone else's space, usually by accident, occasionally not. A more specific announcement wins everywhere.
  • Route leak — an AS re-advertises routes it should not, typically announcing one provider's routes to another and becoming unintended transit. Overwhelmingly the most common incident.
  • Session attacks — spoofed packets against the TCP session, mitigated by MD5 and TTL security.

What you configure

! 1. Session protection
neighbor 203.0.113.1 password <key>
neighbor 203.0.113.1 ttl-security hops 1

! 2. Never become transit — the single most valuable line
ip as-path access-list 1 permit ^$
neighbor 203.0.113.1 filter-list 1 out

! 3. Explicit outbound prefix list
neighbor 203.0.113.1 prefix-list OUR-PREFIXES out

! 4. Inbound sanity filter
neighbor 203.0.113.1 prefix-list FROM-ISP in

! 5. Cap the damage
neighbor 203.0.113.1 maximum-prefix 1000000 90 restart 15

! 6. Control plane protection
ip access-list extended BGP-PEERS
 permit tcp host 203.0.113.1 host 203.0.113.2 eq bgp
 deny   tcp any any eq bgp
If you do only one thingApply ^$ outbound on every eBGP session. It makes accidental transit impossible, which is the failure mode most likely to take you — and possibly other people — off the air.

RPKI and origin validation

RPKI lets a prefix holder publish a signed ROA (Route Origin Authorisation) stating which ASN may originate their prefix and at what maximum length. Routers fetch validated data from an RPKI cache over RTR and mark each received route:

StateMeaning
ValidA ROA covers this prefix and the origin AS matches
InvalidA ROA covers it but the origin AS or prefix length is wrong
NotFoundNo ROA exists. Still a large share of the table
 
router bgp 65001
 bgp rpki server tcp 10.1.1.100 port 3323 refresh 600
 address-family ipv4 unicast
  bgp bestpath prefix-validate allow-invalid
!
route-map RPKI-IN permit 10
 match rpki invalid
 set local-preference 50
route-map RPKI-IN permit 20

show bgp ipv4 unicast rpki table
show bgp ipv4 unicast rpki servers

Two things to do regardless of whether you validate: publish ROAs for your own prefixes, and register your routing policy in an IRR so providers can build filters. Both are quick, both protect you, and neither requires any change on your routers.

RPKI validates the origin only. It does not prevent a route leak where the origin is correct but the path is not — that is what ASPA and BGPsec aim at, with ASPA the more likely to see real deployment.

15Troubleshooting

The three questions

Almost every BGP problem is one of these. Identify which before touching anything:

  1. Is the session up? → FSM state, TCP, ASN, authentication.

  3. Is the right path chosen? → best-path algorithm, attributes, next-hop reachability.

16Real-world scenarios

Ten incidents, each worked from the reported symptom through the diagnosis to the fix. Output is from the lab topology above. Try to reach the conclusion yourself before expanding the diagnosis.

Session stuck in Active, and the link is fine
Reported

New eBGP session to ISP-B on R2 will not come up. The circuit tests clean, the interface is up, and the provider says their side is configured.

What you see 
R2# show bgp ipv4 unicast summary | include 198.51.100.1
198.51.100.1  4 65200   0   0   0  0  0 never   Active

R2# ping 198.51.100.1
!!!!! Success rate is 100 percent (5/5)

Ping works, so IP reachability is fine. Active means TCP 179 is not establishing — a different question entirely.

Diagnosis 
R2# show bgp neighbors 198.51.100.1 | include Last reset|state
  BGP state = Active
  Last reset never, no connection

R2# debug ip tcp transactions
TCP: sending SYN, seq 1234567, ack 0
TCP: connection attempt to 198.51.100.1:179 timed out

SYNs leave, nothing returns. Ping succeeding while TCP 179 fails points at something filtering the port rather than a routing problem. Check, in order: an ACL on your own interface or control plane, an ACL on theirs, a firewall in the path, and — the one people forget — whether they have actually configured the neighbor. A router with no matching neighbor statement sends a TCP RST or simply drops the SYN.

R2# show access-lists | include 179|bgp
    10 permit tcp host 203.0.113.1 any eq bgp
    20 deny tcp any any eq bgp
Root cause

The control-plane ACL was written for the existing ISP-A peer and never updated when ISP-B was added. The new peer's SYNs were being denied at line 20.

Fix 
ip access-list extended BGP-PEERS
 15 permit tcp host 198.51.100.1 host 198.51.100.2 eq bgp
TakeawayActive plus successful ping equals "something is blocking TCP 179", not "the link is broken". Ping and BGP test different things, and conflating them wastes hours. Build peer ACLs from a template that is updated whenever a peer is added.
Session flaps every 90 seconds, carrying a full table
Reported

After enabling full routes from ISP-A, the session comes up, starts sending, then drops. It repeats roughly every 90 seconds and never finishes converging.

What you see 
R1# show log | include BGP
%BGP-5-ADJCHANGE: neighbor 203.0.113.1 Up
%BGP-5-NBR_RESET: Neighbor 203.0.113.1 reset (BGP Notification sent)
%BGP-3-NOTIFICATION: sent to neighbor 203.0.113.1 4/0 (hold time expired)

R1# show bgp ipv4 unicast summary | include 203.0.113.1
203.0.113.1   4 65100  412   18   0  0  0 00:01:12  Idle

Hold time expired, and it happens only once a large volume of updates starts. That combination is the signature of an MTU problem.

Diagnosis 
R1# ping 203.0.113.1 size 1500 df-bit
Packet sent with the DF bit set
.....
Success rate is 0 percent (0/5)

R1# ping 203.0.113.1 size 1476 df-bit
!!!!!
Success rate is 100 percent (5/5)

Small packets pass, large ones do not. KEEPALIVEs are 19 bytes and always get through; UPDATE messages full of NLRI are large and get silently dropped. The session stays up until the hold timer expires with no keepalive — because the keepalives are stuck behind a blocked large segment in the TCP stream.

Root cause

A carrier Ethernet segment in the path with a 1492-byte MTU, and path MTU discovery failing because ICMP fragmentation-needed messages were being filtered somewhere upstream.

Fix 
interface GigabitEthernet0/0
 ip tcp adjust-mss 1400
!
router bgp 65001
 neighbor 203.0.113.1 transport path-mtu-discovery disable

Permanent fix is raising the MTU across the path or unblocking PMTUD. The MSS clamp is the immediate mitigation.

TakeawayA BGP session that establishes and then dies while exchanging a lot of prefixes is an MTU problem until proven otherwise. Test with ping size 1500 df-bit before anything else. Sessions carrying few prefixes can hide this fault for months.

Reported

R3 shows thousands of prefixes in its BGP table but cannot reach any of them. R1 and R2, which hold the eBGP sessions, work fine.

Prepending does nothing to inbound traffic
Reported

ISP-B is the backup link, prepended three times. Inbound traffic is still arriving over it, and adding more prepends has not helped.

You briefly became transit between two providers
Reported

A phone call from ISP-A: AS 65001 is announcing roughly 800,000 prefixes to them. Your links are saturated and latency is terrible.

What you see 
R1# show bgp ipv4 unicast neighbors 203.0.113.1 advertised-routes | count
Number of lines which match regexp = 812447

! should be 1
Immediate action 
! stop the bleeding first, investigate second
R1(config)# router bgp 65001
R1(config-router)# neighbor 203.0.113.1 shutdown

Shutting the session is the right first move. A route leak damages other networks as well as your own, and the priority is to stop announcing.

Diagnosis 
R1# show run | section router bgp
 neighbor 203.0.113.1 remote-as 65100
 address-family ipv4 unicast
  neighbor 203.0.113.1 activate
  ! no prefix-list out
  ! no filter-list out
  neighbor 203.0.113.1 route-map SET-LOCALPREF in

No outbound filter of any kind. Everything R1 learned from ISP-B via iBGP was being re-advertised to ISP-A — which is exactly what BGP is designed to do unless you tell it not to. The configuration had worked for years because R2's session to ISP-B was down; when it was restored, the leak began.

Root cause

Missing outbound policy on an eBGP session. The absence was latent and only became visible when the second provider session came up.

Fix 
ip prefix-list OUR-PREFIXES seq 5 permit 192.0.2.0/24
ip as-path access-list 1 permit ^$
!
router bgp 65001
 address-family ipv4 unicast
  neighbor 203.0.113.1 prefix-list OUR-PREFIXES out
  neighbor 203.0.113.1 filter-list 1 out
  neighbor 198.51.100.1 prefix-list OUR-PREFIXES out
  neighbor 198.51.100.1 filter-list 1 out
!
R1(config-router)# no neighbor 203.0.113.1 shutdown
R1# show bgp ipv4 unicast neighbors 203.0.113.1 advertised-routes
   Network          Next Hop     Metric LocPrf Weight Path
*> 192.0.2.0/24     0.0.0.0           0         32768 i

Total number of prefixes 1
Prevention
  • Both filters on every eBGP peer: prefix-list for what, ^$ for who.
  • Monitor advertised prefix count per peer and alert on any change.
  • Ask providers to filter your session by your IRR objects — defence in depth.
  • Publish ROAs so others can reject invalid announcements.
TakeawayRoute leaks are the most common serious BGP incident, and they are almost always caused by a missing outbound filter rather than anything exotic. The defence costs two lines per peer. Note how the fault stayed hidden for years — configuration gaps that depend on another device being down are the dangerous ones.
Traffic takes the wrong exit despite correct local-pref
Reported

Policy says prefer ISP-A. R3 obeys it. R2 keeps sending traffic out of ISP-B even for destinations where ISP-A should win.

What you see 
R3# show bgp ipv4 unicast 8.8.8.0/24 | include best|localpref
      Origin IGP, localpref 200, valid, internal, best

R2# show bgp ipv4 unicast 8.8.8.0/24
Paths: (2 available, best #2)
  65100 15169
    10.0.0.1 (metric 20) from 10.0.0.3 (10.0.0.3)
      Origin IGP, localpref 200, valid, internal
  65200 3356 15169
    198.51.100.1 from 198.51.100.1 (198.18.1.1)
      Origin IGP, localpref 200, valid, external, best

Both paths have LOCAL_PREF 200. The tie is therefore broken further down — and at step 7, eBGP beats iBGP. R2's own external path wins.

Diagnosis 
R2# show run | section route-map ISP-B-IN
route-map ISP-B-IN permit 10
 set local-preference 200
! should be 100

The inbound route-map on R2 was copied from R1 during a change and the value never adjusted. Both providers now arrive with LOCAL_PREF 200, so the intended preference disappeared and step 7 silently decided instead.

Root cause

Copy-paste between edge routers without changing the preference value. The symptom is subtle because nothing is broken — traffic flows, just not where intended, and only on the router with the local eBGP session.

Fix 
! R2
route-map ISP-B-IN permit 10
 set local-preference 100
!
R2# clear bgp ipv4 unicast 198.51.100.1 soft in
R2# show bgp ipv4 unicast 8.8.8.0/24 | include best
    10.0.0.1 (metric 20) from 10.0.0.3 (10.0.0.3), best
Takeaway"eBGP beats iBGP" at step 7 is what decides when LOCAL_PREF ties, and it means a router with its own external session will prefer it unless policy says otherwise. When traffic exits the wrong way, compare the attributes on the router making the decision — not on the router where the policy looks correct. Keep LOCAL_PREF values in a documented table rather than in each router's config alone.
Aggregate disappears whenever a site goes down
Reported

R1 advertises an aggregate 192.0.0.0/14 covering four sites. Whenever a particular site's WAN link fails, the entire aggregate is withdrawn from both providers and everything becomes unreachable.

What you see 
R1# show bgp ipv4 unicast 192.0.0.0/14
% Network not in table

R1# show bgp ipv4 unicast | include 192\.
! nothing — all four components gone
Diagnosis 
R1# show run | section aggregate
 aggregate-address 192.0.0.0 255.252.0.0 summary-only

R1# show run | section network
 ! components come from redistributed OSPF, not network statements
 redistribute ospf 1 route-map OSPF-TO-BGP

An aggregate exists only while at least one more-specific component is present in the BGP table. The components here are redistributed from OSPF. The failed site's link flapped, the OSPF routes for all sites briefly withdrew during an SPF recalculation, and with no components left the aggregate vanished.

Root cause

The aggregate's existence depends on dynamic routes that can all disappear at once. There is no stable anchor.

Fix 
! Anchor the aggregate with a discard route that never goes away
ip route 192.0.0.0 255.252.0.0 Null0 250
!
router bgp 65001
 address-family ipv4 unicast
  network 192.0.0.0 mask 255.252.0.0
  aggregate-address 192.0.0.0 255.252.0.0 summary-only

The static to Null0 guarantees the prefix exists in the RIB, so the network statement always injects it. The aggregate is then stable regardless of component state, and the Null0 route silently discards traffic for unallocated space inside the block.

TakeawayAggregates are conditional on their components by design. If an aggregate must always be announced, anchor it with a static route to Null0 and a network statement. The Null0 route is also what stops traffic for unused parts of your block from looping back out your default route — two problems, one line.
