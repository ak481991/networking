01Fundamentals

OSPF is a link-state protocol: every router in an area builds an identical map of that area, then independently runs the same algorithm over it. Almost every OSPF rule exists to protect that identical-database property.

Link state, not distance vector

Routers do not exchange routes. They exchange LSAs describing their own links, flood them unchanged throughout an area, and assemble them into a link-state database. Each router then runs Dijkstra's shortest path first algorithm over that database, with itself as the root, to compute its own routing table.

Three consequences follow immediately:

  • Every router in an area must have an identical LSDB. If two routers disagree, they compute different trees and you get loops. This is why you cannot filter LSAs inside an area — the protocol depends on everyone seeing the same thing.
  • Convergence is fast, because a change floods immediately rather than propagating hop by hop.
  • Scaling is bounded by database size and SPF cost, which is why areas exist.
The mental modelBGP asks "whose network will I use?" OSPF asks "what does the map look like, and what is the cheapest route across it?" The map is shared; the calculation is local.

Transport

OSPF rides directly on IP protocol 89 — no TCP, no UDP. It implements its own reliability through explicit acknowledgements and retransmission.

Because it uses multicast at layer 2, anything that blocks multicast — an ACL, a broken switch, an unsupported overlay — breaks adjacency formation while unicast ping still works perfectly. That is scenario 02.

Router ID

A 32-bit value written like an IPv4 address, uniquely identifying a router in the OSPF domain. Selection order:

  1. Explicitly configured router-id under the process.
  2. Highest IP address on an up loopback interface.
  3. Highest IP address on any other up interface.

Once chosen it is sticky — it does not change when a higher address appears. Changing it requires clear ip ospf process, which is disruptive.

router ospf 1
 router-id 1.1.1.1

show ip ospf | include Router ID
clear ip ospf process               ! disruptive — reconverges everything
Always configure the router ID explicitlyLetting it be derived means an interface change can alter it on the next reload, which breaks virtual links, confuses your LSDB, and makes troubleshooting miserable. Duplicate router IDs produce a particularly nasty failure — see scenario 04.

Cost

OSPF cost is derived from bandwidth: cost = reference-bandwidth / interface-bandwidth, rounded down, minimum 1. The default reference bandwidth is 100 Mbps, which was reasonable in 1998 and is actively harmful now — every interface at or above 100 Mbps gets cost 1, so a 100 Mbps link and a 100 Gbps link look identical.

router ospf 1
 auto-cost reference-bandwidth 100000     ! in Mbps, so 100 Gbps

interface GigabitEthernet0/0

Note the strictness of the ABR definition: a router with interfaces in area 1 and area 2 but none in area 0 is not a valid ABR, and its type 3 LSAs will not be accepted properly. That is the two-tier hierarchy rule, and it is the constraint behind virtual links.

The LSA header

Twenty bytes, prefixed to every LSA, and the part you read constantly in show ip ospf database.

FieldBytesNotes
LS Age2Seconds since origination. MaxAge is 3600 — an LSA at 3600 is being flushed
Options1As above
LS Type11–11
Link State ID4Meaning depends on type. Router ID, DR address, network address…

The triple LS Type + Link State ID + Advertising Router uniquely identifies an LSA. When two copies arrive, the newer one wins by: higher sequence number, then higher checksum, then lower age (with a 15-minute MaxAgeDiff tolerance).

Point-to-multipoint and its /32 routes

P2MP treats the segment as a collection of point-to-point links. It advertises a /32 host route for each neighbour rather than the subnet, which makes it resilient on partial-mesh topologies where not every router can reach every other.

R1# show ip route ospf | include 10.0.99
O       10.0.99.2/32 [110/64] via 10.0.99.2, Serial0/0
O       10.0.99.3/32 [110/64] via 10.0.99.3, Serial0/0

Those /32s are the feature, not a bug. On a hub-and-spoke where spokes cannot reach each other directly, P2MP ensures each spoke route goes via the hub rather than assuming direct reachability within the subnet — which is exactly what broadcast or NBMA types would wrongly assume.

NBMA and manual neighbours

router ospf 1
 neighbor 10.0.99.2 priority 0
 neighbor 10.0.99.3 priority 0
!
interface Serial0/0
 ip ospf network non-broadcast
 ip ospf priority 10              ! hub must become DR

On NBMA there is no multicast, so neighbours must be listed and Hellos are unicast. The hub must be the DR, because only the hub has connectivity to everyone — hence priority 0 on the spokes to make them ineligible. Getting this wrong elects a spoke as DR and the area never converges.

Mismatched network types can still reach FullPoint-to-point on one end and broadcast on the other may form an adjacency, because the Hello timers happen to align in some combinations, yet routing breaks subtly because one side expects a DR and the other does not. Always confirm both ends with show ip ospf interface.

Loopbacks

A loopback is advertised as a /32 host route regardless of its configured mask. If you need the real mask advertised — for an anycast service or a summarised block — change the network type:

interface Loopback0
 ip address 1.1.1.1 255.255.255.0
 ip ospf network point-to-point       ! now advertised as /24

06DR and BDR election

Why a DR exists

On a multi-access segment with n routers, a full mesh of adjacencies would be n(n−1)/2 — ten routers would mean 45 adjacencies, each flooding to each. The DR reduces this to 2n−3 by acting as a central relay: every router forms a full adjacency with the DR and BDR only, and stays at 2-Way with everyone else.

The DR also originates the type 2 network LSA describing the segment, which is what lets the rest of the area model a multi-access network as a single pseudo-node.

Election rules

  1. Highest interface priority wins. Default 1. Priority 0 means never eligible.
  2. On a tie, highest router ID wins.
  3. The election is non-preemptive. A better router joining later does not take over.
interface GigabitEthernet0/0
 ip ospf priority 100       ! make this the DR
 ip ospf priority 0         ! never eligible

show ip ospf interface Gi0/0 | include Designated|Priority
clear ip ospf process       ! the only way to force re-election — disruptive
Non-preemptive surprises peopleBring up your intended DR last and it will not become DR. Raise a priority on a running segment and nothing happens. The election only re-runs when the current DR fails, or when the OSPF process is cleared. Plan DR placement before the segment goes live.

Reading the result

R3# show ip ospf neighbor
Neighbor ID  Pri State        Dead Time  Address    Interface
4.4.4.4      100 FULL/DR      00:00:33   10.0.34.2  GigabitEthernet0/2
5.5.5.5        1 2WAY/DROTHER 00:00:31   10.0.34.3  GigabitEthernet0/2

2WAY/DROTHER is correct and permanent, not a fault. Two DROthers never form a full adjacency with each other — they exchange through the DR. Engineers new to OSPF frequently "fix" this, which is the one thing not to do.

Design guidance

  • On a two-router Ethernet link, use ip ospf network point-to-point and avoid the election entirely.
  • On a genuine multi-access segment, set the intended DR and BDR to high priorities and everything else to 0. That makes the outcome deterministic rather than an accident of boot order.
  • Place the DR on a stable, well-connected router — not on a device that reloads often.
  • On NBMA hub-and-spoke, the hub must be DR. Spokes get priority 0.

Type 2 — Network LSA

Originated by the DR only, one per multi-access segment, listing every router fully adjacent on that segment. Its Link State ID is the DR's interface address, not a router ID — a detail that confuses people reading the database.

No DR means no type 2. That is why point-to-point links produce a smaller, simpler database.

Type 3 — Summary LSA

Generated by an ABR to tell one area about a prefix in another. Crucially the ABR regenerates it rather than forwarding the original — which is why the ABR is the only place inter-area filtering and summarisation can happen.

The cost in a type 3 is the ABR's cost to reach the prefix, and each subsequent ABR adds its own. OSPF inter-area routing is therefore distance-vector in behaviour, even though intra-area routing is link-state. This is also why the two-tier area hierarchy exists: without area 0 as a mandatory transit, inter-area routing could loop.

Type 4 — ASBR Summary

Tells routers in other areas how to reach an ASBR. Without it, a router in area 2 would receive a type 5 LSA from ASBR 4.4.4.4 but have no idea how to reach 4.4.4.4, so the external route would be unusable.

Generated by the ABR of the area containing the ASBR, and regenerated by every subsequent ABR. The Link State ID is the ASBR's router ID.

The diagnosticExternal routes present in the database but missing from the routing table in a remote area usually means the type 4 is absent. show ip ospf border-routers on the complaining router tells you whether it knows a path to the ASBR at all.

Type 5 — AS External

Originated by an ASBR, flooded unchanged across the entire AS except into stub and NSSA areas. The flooding scope is what makes externals expensive — a redistributed BGP table would put every prefix into every router's database in every area.

Type 7 — NSSA External

A stub area cannot carry type 5 LSAs. An NSSA solves the case where a stub-like area nevertheless contains an ASBR: externals are carried as type 7 within the NSSA, and the ABR translates them into type 5 when flooding into the backbone.

The translating ABR is the one with the highest router ID among the NSSA's ABRs, unless overridden. The P bit in the type 7 controls whether translation happens at all — a type 7 with P clear stays inside the NSSA.

Choosing an area type

  • Standard — the default. Use it unless you have a reason not to.
  • Stub — the area has no ASBR and does not need external routes in detail. Removes type 5 and 4.
  • Totally stubby — as above, and the area has a single exit point so inter-area detail is wasted too. The most aggressive reduction, and ideal for branch sites.
  • NSSA — the area needs to be stub-like but contains an ASBR, for example a branch redistributing a local static or a small BGP session.
  • Totally NSSA — the combination: local ASBR, single exit, minimal database.
Rule of thumb for branch sitesTotally stubby, or totally NSSA if the branch redistributes anything locally. A branch router with a single uplink gains nothing from a full inter-area table, and the memory and SPF savings on hundreds of sites are substantial.

09SPF and route selection

Route preference order

When the same prefix is learned in more than one way, OSPF prefers in this order — regardless of cost:

  1. Intra-area (O)
  2. Inter-area (O IA)
  3. External type 1 (O E1) and NSSA type 1 (O N1)
  4. External type 2 (O E2) and NSSA type 2 (O N2)

An intra-area route with cost 10000 beats an inter-area route with cost 2. Only within the same class does cost decide.

This causes genuinely suboptimal routingIf a prefix exists in both area 1 and area 0, a router in area 1 always takes the intra-area path even when the inter-area path is physically shorter. The fix is a design fix — do not let the same prefix appear in two areas.

When SPF runs, and when it does not

ChangeTriggers
Type 1 or 2 LSA changesFull SPF for that area. Expensive
Type 3, 4, 5 or 7 LSA changesPartial SPF only. The tree is unchanged, just the leaves
LSA refresh with no content changeNothing. The checksum matches

That distinction is the reason summarisation helps so much: a flapping link inside an area forces a full SPF on every router in that area, but if the ABR summarises, routers in other areas see no change at all.

Throttling

router ospf 1
 timers throttle spf 50 200 5000
!                  |   |    +-- maximum wait between SPF runs, ms
!                  |   +------- incremental hold time, ms
!                  +----------- initial delay before first SPF, ms

 timers throttle lsa 50 200 5000       ! LSA generation
 timers lsa arrival 100                ! minimum interval between accepted LSAs
 timers pacing flood 33
 timers pacing lsa-group 240

Throttling uses exponential backoff: the first event is handled almost immediately, repeated events back off toward the maximum, and the timer resets after a quiet period. The defaults on older IOS (5s / 10s) are far too slow for a modern network; the values above are a reasonable starting point.

10Summarization

Two commands, two completely different places. Using the wrong one is the most common summarisation fault.

The two commands

CommandRuns onSummarisesAffects LSA
area X rangeABRIntra-area routes from area X, into other areasType 3
summary-addressASBRRedistributed external routesType 5 or 7
They are not interchangeablesummary-address on an ABR that is not an ASBR does nothing. area range on an ASBR that is not an ABR does nothing. Both fail silently — no error, no summary, just unchanged output. Check which role the router actually holds first.

area range — on the ABR

! R1 summarises area 1's internal prefixes toward area 0
router ospf 1
 area 1 range 10.0.0.0 255.255.0.0

! set the cost explicitly instead of taking the lowest component
 area 1 range 10.0.0.0 255.255.0.0 cost 100

! suppress entirely — a filtering tool, see the next section
 area 1 range 10.0.0.0 255.255.0.0 not-advertise

The summary's cost defaults to the lowest cost among its components, which means a single cheap component can make the whole summary look artificially attractive. Setting the cost explicitly is usually better in a multi-ABR design.

The ABR also installs a discard route to Null0 for the summary, preventing a loop when traffic arrives for an address inside the range that no longer exists:

R1# show ip route 10.0.0.0
O       10.0.0.0/16 is a summary, 00:12:04, Null0

summary-address — on the ASBR

! R4 is the ASBR; collapse the redistributed externals
router ospf 1
 summary-address 172.16.0.0 255.255.0.0
 summary-address 172.16.0.0 255.255.0.0 not-advertise
 summary-address 172.16.0.0 255.255.0.0 tag 500

This replaces the individual type 5 (or type 7) LSAs with a single one. Because type 5 floods the whole AS, summarising at the ASBR has the largest database impact of any single change you can make.

Design guidance

  • Summarise at every ABR for an area, with the same range. One ABR advertising specifics while another advertises a summary means traffic always follows the specific.
  • Allocate address space per area contiguously, from day one. Summarisation is impossible to retrofit onto scattered allocations — this is the real reason addressing plans matter.
  • Remember the trade-off: summarisation hides component flaps from other areas, which is the point, but it also hides genuine failures. A summary stays advertised while any component exists.
The flap-containment argumentWithout summarisation, a flapping link in area 1 re-floods LSAs and triggers SPF in every area. With it, the ABR absorbs the change and nothing outside area 1 notices. On a large network that difference is the whole stability story.

11Filtering

OSPF filtering is far more constrained than BGP, and understanding why prevents most of the wasted effort. You cannot filter LSAs inside an area, because every router must hold an identical database.

What you can and cannot filter

GoalPossible?Mechanism
Stop a prefix entering another areaYesarea filter-list prefix on the ABR
Stop a prefix being redistributedYesdistribute-list out on the ASBR, or a route-map on redistribute
Stop a route being installed in this router's RIBYesdistribute-list in — but the LSA is still in the LSDB
Stop externals entering an areaYesMake it a stub or NSSA
Suppress a summaryYesarea range not-advertise or summary-address not-advertise
Stop flooding an LSA out of one interfaceYesip ospf database-filter all out
Filter type 1 or 2 LSAs inside an areaNoWould break the identical-LSDB requirement
distribute-list in does not filter the databaseIt prevents routes being installed in this router's routing table. The LSAs remain in the LSDB and continue to be flooded to everyone else, who will still install them. It is a local RIB filter, not a routing-protocol filter, and using it to "block" a prefix across a network does not work.

area filter-list — the main inter-area tool

Filters type 3 LSAs at an ABR, in either direction relative to the named area.

ip prefix-list NO-MGMT seq 5 deny 10.99.0.0/16 le 32
ip prefix-list NO-MGMT seq 10 permit 0.0.0.0/0 le 32
!
router ospf 1
 ! filter LSAs going INTO area 1 from everywhere else
 area 1 filter-list prefix NO-MGMT in
 ! filter LSAs leaving area 1 toward other areas
 area 1 filter-list prefix NO-MGMT out
Get the direction rightin means "into this area", out means "out of this area" — both from the ABR's perspective, relative to the area named in the command, not relative to an interface. Applying the right filter in the wrong direction is scenario 09 and produces exactly no effect.

Remember the trailing permit: a prefix-list ends with an implicit deny, so a filter-list that only denies will block everything.

distribute-list in — local RIB only

ip prefix-list NO-INSTALL seq 5 deny 192.168.50.0/24
ip prefix-list NO-INSTALL seq 10 permit 0.0.0.0/0 le 32
!
router ospf 1
 distribute-list prefix NO-INSTALL in
 distribute-list prefix NO-INSTALL in GigabitEthernet0/1   ! per-interface
 distribute-list route-map FILTER-RIB in

Legitimate uses: stopping a particular router installing a route it should not use, or protecting a small-FIB device from a large table. Not a tool for network-wide policy.

distribute-list out — redistribution only

router ospf 1
 ! only filters routes being redistributed INTO OSPF
 distribute-list prefix ONLY-THESE out bgp 65001
 distribute-list prefix ONLY-THESE out static

Valid on an ASBR, and only against redistributed sources. It cannot filter OSPF-internal routes outbound — there is no such concept, because OSPF floods LSAs rather than advertising routes per neighbour.

A route-map on the redistribute statement is usually clearer and more capable:

route-map BGP-TO-OSPF permit 10
 match ip address prefix-list ALLOWED
 set metric 100
 set metric-type type-1
 set tag 65001
!
router ospf 1
 redistribute bgp 65001 subnets route-map BGP-TO-OSPF

Suppressing with range and summary-address

! ABR: hide area 1 internals from other areas entirely
 area 1 range 10.1.0.0 255.255.0.0 not-advertise

! ASBR: stop these externals being advertised at all
 summary-address 172.16.8.0 255.255.248.0 not-advertise

Often the cleanest way to hide a block: it is declarative, visible in the configuration alongside the summarisation, and does not depend on prefix-list direction semantics.

Per-interface flood suppression

interface GigabitEthernet0/2
 ip ospf database-filter all out

Stops all LSA flooding out of that interface while keeping the adjacency. Used on hub-and-spoke NBMA to prevent the hub reflecting LSAs back to spokes that already have them. Use it carefully — it can desynchronise databases if applied where a router genuinely needs the flood.

Area types as a filtering mechanism

The most effective OSPF filtering is structural. Making an area totally stubby removes every type 3, 4 and 5 LSA in one line — more than any prefix-list will achieve, with less configuration and no direction semantics to get wrong.

Reach for area types first, area filter-list second, and distribute-list only when the goal really is local.

12Redistribution

The basics

router ospf 1
 redistribute static subnets
 redistribute bgp 65001 subnets metric 100 metric-type 1 tag 65001
 redistribute eigrp 100 subnets route-map EIGRP-TO-OSPF
 redistribute connected subnets route-map CONNECTED-TO-OSPF
subnets is not optional in practiceWithout the subnets keyword, OSPF redistributes only classful networks — so 10.1.1.0/24 is silently dropped because it is not 10.0.0.0/8. It is a historical default that still catches people. Newer IOS-XE versions warn or assume it, but write it anyway.

Default metric for redistributed routes is 20 (except from BGP, where it is 1), and default metric type is E2.

E1 versus E2, concretely

R4 redistributes 172.16.0.0/16 with metric 100. R5, in area 2, is 300 cost away from R4.

Metric typeCost R5 seesBehaviour with two ASBRs
E2 (default)100Both look identical. Tie broken by cost to ASBR, but the displayed metric misleads
E1400Each router genuinely picks its nearest ASBR
 
R5# show ip route 172.16.0.0
! with E2

! with E1
O E1  172.16.0.0/16 [110/400] via 10.0.25.1
Default to E1 in multi-ASBR designsE2's fixed metric is useful only when you genuinely want every router to see the same cost regardless of distance. With two or more exits, E1 gives correct nearest-exit behaviour, and the metric in show ip route actually means something.

Default route origination

router ospf 1
 ! advertise 0.0.0.0/0 only if one exists in the RIB
 default-information originate

 ! advertise it unconditionally — dangerous
 default-information originate always

 ! with specific attributes
 default-information originate metric 50 metric-type 1 route-map HAVE-UPLINK
always is a black-hole generatoralways keeps advertising the default even when this router has lost all upstream connectivity. Every router in the area then forwards its internet traffic to a router that cannot deliver it. Use the conditional form with a route-map that tracks real upstream reachability.

A stub area gets its default automatically from the ABR — default-information originate is neither needed nor effective there.

Mutual redistribution and loops

Redistributing both ways between OSPF and another protocol can send a route out and back in, where it may look better than the original. Tags are the standard defence:

! mark everything that came from BGP
route-map BGP-TO-OSPF permit 10
 set tag 65001
!
! and refuse to send it back
route-map OSPF-TO-BGP deny 10
 match tag 65001
route-map OSPF-TO-BGP permit 20
!
router ospf 1
 redistribute bgp 65001 subnets route-map BGP-TO-OSPF
router bgp 65001
 address-family ipv4 unicast
  redistribute ospf 1 route-map OSPF-TO-BGP

Also raise the administrative distance of redistributed routes where appropriate, so the original source always wins on the router that holds both.

The forwarding address

A type 5 LSA can carry a non-zero forwarding address, telling routers to send traffic there rather than to the ASBR itself. It is set when the ASBR's next hop for the external route is on an OSPF-enabled interface, on a network type that is not point-to-point, and the next hop is not the ASBR.

Every router must be able to reach that address, or the external route is unusable. If externals appear in the database but not the routing table, check the forwarding address first:

show ip ospf database external 172.16.0.0 | include Forward
        Forward Address: 10.0.34.1
show ip route 10.0.34.1

13Virtual links

What they are for

OSPF requires every area to touch area 0, and area 0 to be contiguous. A virtual link is a logical adjacency across a transit area that repairs a violation of either rule.

Two legitimate uses: an area that cannot be physically connected to the backbone, and a backbone that has been split in two — usually after a merger or a link failure.

! Area 3 connects only to area 1, which connects to area 0.
! Build a virtual link across area 1 between the two ABRs.

! On R1 (ABR area 0 / area 1), router-id 1.1.1.1
router ospf 1
 area 1 virtual-link 3.3.3.3

! On R3 (ABR area 1 / area 3), router-id 3.3.3.3
router ospf 1
 area 1 virtual-link 1.1.1.1

The command names the transit area and the remote router ID — not an interface or an IP address. Both are common mistakes.

Rules

  • The transit area must be a standard area. Never a stub, totally stubby, or NSSA.
  • Both endpoints must be ABRs.
  • The transit area must have full routing information — it cannot itself be summarised in a way that hides the endpoints.
  • Router IDs must be reachable through the transit area.
  • The link is treated as an unnumbered point-to-point link in area 0, with demand-circuit behaviour so Hellos are suppressed.
show ip ospf virtual-links
show ip ospf neighbor | include OSPF_VL

R1# show ip ospf virtual-links

  Run as demand circuit
  DoNotAge LSA allowed.
  Transit area 1, via interface GigabitEthernet0/1
  Topology-MTID Cost  Disabled  Shutdown  Topology Name
        0         100    no        no       Base
  Transmit Delay is 1 sec, State POINT_TO_POINT

When not to use one

A virtual link is a repair, not a designIf your design requires one permanently, the area layout is wrong. They complicate troubleshooting, depend on the transit area staying healthy, and fail in ways that are hard to diagnose. Use one to recover from a backbone partition or during a migration, then fix the topology.

The modern alternative for permanently joining discontiguous areas is a GRE tunnel placed in area 0, which is explicit and behaves like a normal link. It carries its own risks — notably that the tunnel's path must not depend on the routes it carries — but it is easier to reason about.

16Scaling and tuning

What actually limits OSPF

  • LSDB size per area — memory, and SPF runtime which scales with the number of nodes and links.
  • SPF frequency — a churning area forces repeated full recalculation on every router in it.
  • Flooding volume — CPU spent on packet handling rather than computation.
  • Number of adjacencies per router — each one has state and retransmission queues.

Old guidance quoted hard limits like "50 routers per area". Modern hardware handles far more, and the real constraint is how much change an area absorbs, not how many routers sit in it. A stable 200-router area is easier than an unstable 30-router one.

Stub router / max-metric

router ospf 1
 ! advertise maximum cost so traffic routes around this router
 max-metric router-lsa

 ! automatically during startup, until BGP converges
 max-metric router-lsa on-startup wait-for-bgp
 max-metric router-lsa on-startup 300

 ! also de-preference the externals and summaries we originate
 max-metric router-lsa on-startup 300 summary-lsa external-lsa

The router stays in OSPF and keeps its adjacencies but advertises cost 65535 on transit links, so nobody routes through it. Two important uses: a graceful drain before maintenance, and preventing a freshly rebooted router from attracting transit traffic before BGP has finished converging.

on-startup wait-for-bgp is underusedA router that reboots, brings OSPF up in seconds, and then takes minutes to converge BGP will black-hole transit traffic in the meantime. This one line removes an entire class of outage on BGP-speaking core routers.

Prefix suppression

router ospf 1
 prefix-suppression
!
interface GigabitEthernet0/0
 ip ospf prefix-suppression

Stops advertising transit link prefixes, keeping only loopbacks and explicitly needed prefixes in the database. On a large core this cuts LSDB size substantially — point-to-point link subnets are rarely needed as destinations. Loopbacks are never suppressed, so management reachability survives.

Graceful restart and NSF

router ospf 1
 nsf ietf                            ! RFC 3623 graceful restart
 nsf ietf helper disable             ! refuse to help others
 nsf cisco                           ! Cisco NSF

During a control-plane restart, neighbours keep forwarding using the existing topology instead of reconverging. Requires neighbours to act as helpers. The grace LSA is a type 9 opaque LSA, which is why the O bit in the Options field matters.

Design rules that matter

  1. Allocate addresses per area contiguously. Everything else about scaling depends on being able to summarise, and you cannot retrofit it.
  2. Summarise at every ABR, identically.
  3. Make branch areas totally stubby. Biggest reduction for least configuration.
  4. Point-to-point network type on routed Ethernet. Smaller database, faster convergence.
  5. Consistent reference bandwidth, set once across the domain.
  6. Keep area 0 small and stable. It carries the consequences of every other area's instability.
  7. Use BFD rather than aggressive Hello timers.
  8. Passive-interface default. Adjacencies should be deliberate.

Ten incidents on the lab topology, each from the reported symptom to the fix. Try to reach the conclusion yourself before expanding the diagnosis.

Neighbour cycles between ExStart and Exchange forever
Reported

New link between R1 and R2. The neighbour appears, reaches ExStart, drops, reappears. It never reaches Full. Both interfaces are up and ping works.

What you see

! Correct fix — make them match

    30 permit udp any any eq snmp
    40 deny ip any any (4812 matches)

ICMP is permitted, which is why ping works. OSPF rides on IP protocol 89 to multicast 224.0.0.5, and nothing in the ACL permits it.

Root cause

A security hardening ACL applied to the interface without an exception for the routing protocol. The one-way symptom arises because R4's outbound Hellos are unaffected — only its inbound path is blocked.

Fix 
ip access-list extended PROTECT-IN
 5 permit ospf any host 224.0.0.5
 6 permit ospf any host 224.0.0.6
 7 permit ospf host 10.0.34.1 host 10.0.34.2
TakeawayInit on one side and nothing on the other is always a one-way path. Ping proves nothing about OSPF — it tests ICMP unicast, while OSPF needs protocol 89 to a multicast group. Other causes in the same family: multicast blocked on a switch, a unidirectional fibre strand, or an overlay that does not carry multicast.
Two routers sit at 2-Way and nobody becomes DR
Reported

On the R3–R4 broadcast segment, both routers show 2-Way and routes are not exchanged. A third router on the same segment also shows 2-Way to both.

What you see 
R3# show ip ospf neighbor
Neighbor ID  Pri State          Dead Time  Address    Interface
4.4.4.4        0 2WAY/DROTHER   00:00:34   10.0.34.2  Gi0/2
5.5.5.5        0 2WAY/DROTHER   00:00:36   10.0.34.3  Gi0/2

R3# show ip ospf interface Gi0/2 | include Designated|priority
  Network Type BROADCAST, Cost: 100
  No designated router on this network
  No backup designated router on this network
  Router Priority 0
Diagnosis

Every router on the segment has priority 0, which makes all of them ineligible. With no DR there is no type 2 network LSA and no full adjacency, so everybody rests at 2-Way permanently.

R3# show run interface Gi0/2 | include priority
 ip ospf priority 0
! same on R4 and R5 — copied from a template
Root cause

An interface template written for NBMA spokes, where priority 0 is correct, applied to a broadcast segment where it is not.

Fix 
! Option A — elect a deterministic DR and BDR
R3(config-if)# ip ospf priority 100      ! DR
R4(config-if)# ip ospf priority 50       ! BDR
! R5 stays at 0

! Option B — if only two routers are really on it, remove the election
R3(config-if)# ip ospf network point-to-point
R4(config-if)# ip ospf network point-to-point

Priority changes are not preemptive, so clear the process or bounce the interface to force a re-election.

Takeaway2-Way between DROthers is normal; 2-Way between everyone with no DR elected is not. The giveaway is "No designated router on this network" in show ip ospf interface. Always set DR and BDR deterministically on a multi-access segment rather than leaving it to boot order — and never apply an NBMA template to broadcast.

Area 2 cannot reach anything in area 1
Reported

R5 in area 2 has backbone routes but nothing from area 1. R1 and R2 both look healthy and all adjacencies are Full.

What you see 
R5# show ip route ospf
O IA  10.0.12.0/30 [110/200] via 10.0.25.1
O IA  1.1.1.1/32   [110/201] via 10.0.25.1
! nothing from area 1 — no 10.0.13.0/30, no 3.3.3.3, no 4.4.4.4
Diagnosis 
R2# show ip ospf database summary | include 10.0.13
! nothing — R2 is not generating a type 3 for it

R2# show ip ospf database summary adv-router 1.1.1.1 | include 10.0.13
! R1 is not advertising it into area 0 either

R1# show run | section router ospf
router ospf 1
 router-id 1.1.1.1
 area 1 range 10.0.0.0 255.255.0.0 not-advertise

An area range with not-advertise on R1 is suppressing every area 1 prefix inside 10.0.0.0/16 from reaching any other area.

Root cause

The range was added to summarise area 1, and not-advertise was included by mistake — most likely copied from a different range intended to hide a management block.

Fix 
R1(config-router)# no area 1 range 10.0.0.0 255.255.0.0 not-advertise
R1(config-router)# area 1 range 10.0.0.0 255.255.0.0 cost 100
R5# show ip route ospf | include 10.0.0.0
O IA  10.0.0.0/16 [110/300] via 10.0.25.1
Why it was hard to spot

Nothing is down, no adjacency is broken, no error is logged. Suppression is working exactly as configured. The only way to find it is to trace the LSA backwards: absent in R5's database, absent in area 0, therefore the ABR that should generate it is the place to look.

TakeawayWhen routes are missing with all adjacencies healthy, trace the LSA from the destination back toward its origin, checking each area boundary. Missing type 3 means look at the ABR — area range not-advertise, area filter-list, or a stub no-summary. All three suppress silently by design.
Traffic takes the slow path after a bandwidth upgrade
Reported

The R1–R2 link was upgraded from 1G to 10G. Traffic still prefers the longer path through R3. Costs look wrong but nobody changed them.

What you see 
R1# show ip ospf interface Gi0/0 | include Cost
  Process ID 1, Router ID 1.1.1.1, Network Type POINT_TO_POINT, Cost: 1

R1# show ip ospf interface Gi0/1 | include Cost
  Process ID 1, Router ID 1.1.1.1, Network Type POINT_TO_POINT, Cost: 1

A 10G link and a 1G link both cost 1. With the default 100 Mbps reference bandwidth, everything at or above 100 Mbps saturates at cost 1 and OSPF cannot tell them apart.

Diagnosis 
R1# show ip ospf | include Reference
 Reference bandwidth unit is 100 mbps

R2# show ip ospf | include Reference
 Reference bandwidth unit is 100 mbps
Root cause

Default reference bandwidth, unchanged since the network was built. The upgrade had no effect on path selection because the metric could not represent it.

Fix 
! On EVERY router in the domain, in the same change window
router ospf 1
 auto-cost reference-bandwidth 100000     ! 100 Gbps, in Mbps
R1# show ip ospf interface Gi0/0 | include Cost
  Network Type POINT_TO_POINT, Cost: 10        ! 10G
R1# show ip ospf interface Gi0/1 | include Cost
  Network Type POINT_TO_POINT, Cost: 100       ! 1G
Partial deployment is worse than noneReference bandwidth is a local calculation and is never advertised. If half the routers use 100 and half use 100000, they compute different costs for the same links, choose inconsistent paths, and can form transient loops. Change it everywhere in one window, or not at all.
TakeawaySet the reference bandwidth above your fastest link on day one. Choose a value with headroom — 100 Gbps or more — because raising it later means touching every router simultaneously. If you cannot do a domain-wide change, set explicit ip ospf cost on the links that matter instead.
External routes present in the database but not in the routing table
Reported

R5 in area 2 cannot reach 172.16.0.0/16. R3, in area 1 alongside the ASBR, reaches it fine.

What you see 
R5# show ip route 172.16.0.0
% Network not in table

R5# show ip ospf database | include 172.16
! nothing at all

Not merely uninstalled — the LSA is absent entirely. That narrows it immediately.

Diagnosis 
R5# show ip ospf | include Area 2|stub
    Area 2
        It is a stub area

Area 2 is a stub, and stub areas block type 5 LSAs by design. R5 should instead be using the default route the ABR injects.

R5# show ip route 0.0.0.0
% Network not in table

R2# show run | section router ospf
router ospf 1
 area 2 stub no-summary
 ! but R2 is NOT generating the default

R2# show ip ospf | include Area 2|stub|default
    Area 2
        It is a stub area, no summary LSA in this area
        generates stub default route with cost 1

R2 believes it is generating the default. R5 is not receiving it. Checking the adjacency reveals the real problem:

R2# show ip ospf neighbor | include 5.5.5.5
5.5.5.5    1  EXSTART/  -  00:00:33  10.0.25.2  Gi0/1
Root cause

Two faults stacked. Area 2 being a stub is correct and intentional — externals should be absent and replaced by a default. But the R2–R5 adjacency was stuck in ExStart (an MTU mismatch, as in scenario 01), so R5 never received the default either. The missing external was a red herring.

Fix 
R5(config)# interface GigabitEthernet0/0
R5(config-if)# mtu 9000
R5# show ip route ospf
O*IA  0.0.0.0/0 [110/101] via 10.0.25.1, 00:00:21, Gi0/0
TakeawayTwo lessons. First, in a stub area the absence of external LSAs is correct — look for the default route instead, not the externals. Second, verify adjacency state before investigating LSA propagation. A stuck neighbour explains every downstream symptom, and chasing the symptom wastes the time you should spend on show ip ospf neighbor.

Core routers at 80% CPU. Routing is working but convergence is slow and management sessions are sluggish. No configuration changed.

  00:00:06  4        0       0    0      0   0     4     R
  00:00:04  4        0       0    0      0   0     4     R

Full SPF every few seconds, reason R — a router LSA keeps changing. Find which:

area filter-list is configured but nothing is filtered
Reported

Management network 10.99.0.0/16 should not be visible in area 2. A filter-list was configured on R2 but the prefix still appears.

What you see 
R5# show ip route ospf | include 10.99
O IA  10.99.0.0/16 [110/200] via 10.0.25.1    ! still there

R2# show run | section router ospf
router ospf 1
 area 2 filter-list prefix NO-MGMT out
!
ip prefix-list NO-MGMT seq 5 deny 10.99.0.0/16 le 32
ip prefix-list NO-MGMT seq 10 permit 0.0.0.0/0 le 32
Diagnosis

The prefix-list is correct. The direction is not. out filters type 3 LSAs leaving area 2 — that is, prefixes originating inside area 2 and being advertised to other areas. The management prefix originates in area 0 and is travelling into area 2.

R2# show ip ospf | include filter
    Area 2
        Area has prefix filter-list NO-MGMT (outbound)
! the filter is applied, it just never sees this LSA
Root cause

Direction keywords are relative to the area named in the command, not to an interface and not to the router. in means into area 2; out means out of area 2.

Fix 
R2(config-router)# no area 2 filter-list prefix NO-MGMT out
R2(config-router)# area 2 filter-list prefix NO-MGMT in
R5# show ip route ospf | include 10.99
! gone
The alternative 
! If area 2 needs nothing inter-area at all, this is simpler
! and removes every type 3 in one line
R2(config-router)# area 2 stub no-summary
TakeawayRead area X filter-list ... in|out as "into area X" and "out of area X". Getting it backwards produces a configuration that looks right, reports as applied, and does nothing. Before reaching for a filter-list, ask whether a totally stubby or totally NSSA area would achieve the same thing more simply.
Backbone splits in two after a link failure
Reported

The R1–R2 backbone link failed. Area 1 and area 2 can each still reach their own ABR, but cannot reach each other, even though a physical path exists through area 1.

What you see 
R1# show ip ospf neighbor
Neighbor ID  Pri State    Dead Time  Address    Interface
3.3.3.3        1 FULL/  -  00:00:36   10.0.13.2  Gi0/1
! R2 is gone — the backbone adjacency is down

R5# show ip route ospf | include 3.3.3.3
! nothing from area 1

R3# show ip route ospf | include 5.5.5.5
! nothing from area 2
Diagnosis

Area 0 is now in two disconnected pieces: R1's backbone interfaces on one side, R2's on the other. Inter-area routing requires area 0 to be contiguous, so type 3 LSAs cannot cross between the fragments. A physical path exists through area 1 to R3, but OSPF will not use a non-backbone area as transit between areas.

R1# show ip ospf | include Area 0|Number of
    Area BACKBONE(0)
        Number of interfaces in this area is 1
        Number of fully adjacent neighbors in this area is 0
Immediate fix — a virtual link

If a path exists through a standard transit area between two ABRs, a virtual link repairs the backbone across it. Here R1 and R2 do not share a transit area, so first check what does connect them. Assume R2 also has an interface in area 1:

! R1
router ospf 1
 area 1 virtual-link 2.2.2.2

! R2
router ospf 1
 area 1 virtual-link 1.1.1.1
R1# show ip ospf virtual-links
Virtual Link OSPF_VL0 to router 2.2.2.2 is up
  Transit area 1, via interface GigabitEthernet0/1
  State POINT_TO_POINT
If there is no suitable transit area 
! GRE tunnel placed in area 0 — explicit, behaves like a normal link
interface Tunnel0
 ip address 10.255.0.1 255.255.255.252
 tunnel source Loopback0
 tunnel destination 2.2.2.2
 ip ospf 1 area 0
 ip ospf cost 5000                   ! make it a last resort
The tunnel must not depend on the routes it carriesIf the GRE endpoints are reachable only via OSPF routes learned through the tunnel, it will flap endlessly. Source and destination must be reachable by some independent means — a static route, or another area.
The real fix
  • Restore the failed backbone link.
  • Then address the design: a single backbone link between two ABRs is a single point of partition. Add a second diverse path in area 0.
  • Remove the virtual link once the physical topology is sound.
TakeawayA partitioned backbone breaks all inter-area routing even when physical paths exist, because OSPF will not transit a non-backbone area. Virtual links and GRE tunnels are recovery tools, not designs — if your topology needs one permanently, the area layout is wrong. Build redundancy into area 0 first.
