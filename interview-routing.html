01Forwarding fundamentals

Almost every routing interview opens here, and almost every candidate under-prepares it because it feels too basic. Interviewers use these to calibrate — a crisp answer on RIB versus FIB buys you credit for the rest of the hour.

What is the difference between the RIB and the FIB, and why does CEF exist?Core

The RIB is the control plane's database of every route it has learned and the best path per prefix. The FIB is the data plane's pre-computed lookup table derived from the RIB, built so that forwarding needs no recursion and no process involvement.

Detail

The RIB — what show ip route displays — holds the result of route selection per prefix, with next-hops that may be recursive. "Next hop 10.1.1.1" is not directly usable by hardware; something has to resolve 10.1.1.1 to an outgoing interface and a rewrite MAC.

CEF does that resolution once, in advance, and stores the result:

  • The FIB is a prefix-to-next-hop table, with recursion already flattened.
  • The adjacency table holds the layer 2 rewrite information — the destination MAC, source MAC, and encapsulation — for each next-hop.
  • A forwarding decision becomes one lookup plus one rewrite, which is what you can implement in an ASIC or in a tight software loop.

The alternative, process switching, resolved recursion per packet and consulted the RIB per packet. That is why pre-CEF routers forwarded at a fraction of their interface speed and why the first packet of a flow behaved differently from the rest under fast switching's cache model.

show ip route 10.2.2.0              ! control plane view, may be recursive
show ip cef 10.2.2.0 detail         ! data plane view, recursion resolved
show adjacency detail                ! the L2 rewrite
show ip cef exact-route 10.1.1.10 10.2.2.20

! platform-specific hardware FIB
show platform software ip switch active F0 cef
show ip route repair-paths 10.2.2.0
Follow-ups to expect
  • "What does a CEF glean adjacency mean?" — the prefix is directly connected but the host's MAC is unresolved, so the packet is punted to trigger ARP.
  • "What is a punt adjacency?" — traffic needing CPU handling: IP options, TTL expiry, fragmentation.
  • "What happens if CEF is disabled?" — on modern platforms you cannot disable it meaningfully; on older ones forwarding collapses to process switching and the CPU becomes the bottleneck.
What they're testingWhether you distinguish control plane from data plane as a habit of thought. It predicts how you will troubleshoot: an engineer who conflates them tries to explain a forwarding problem with show ip route and misses that the RIB can be perfect while the FIB is wrong — which is exactly what a hardware programming failure looks like.
Two protocols advertise the same prefix. Walk me through exactly how the router chooses.Core

Longest prefix match first, always. Only among routes of identical prefix length does administrative distance decide, and only within one protocol does metric decide.

Detail

The order is strict and the most common mistake is collapsing it:

  1. Longest prefix match. A /24 from RIP beats a /16 from OSPF for an address inside the /24. AD never enters into it. This is the step candidates skip.
  2. Administrative distance, among routes with the same prefix length from different sources. Lower wins. The loser is not installed in the RIB at all — it stays in the protocol's own database.
  3. Metric, among routes with the same prefix and the same AD from the same protocol. Protocol-specific comparison.
  4. Equal everything → multiple paths installed, up to the maximum-paths setting, and CEF load-shares between them.

  • "Why is eBGP 20 and iBGP 200?" — eBGP is trusted over IGP because it represents an external administrative decision; iBGP is deliberately worse than every IGP so that an iBGP-learned path never beats the IGP path to the same internal destination, which would create a loop.

What they're testingPrecision under a familiar question. Everyone knows the AD table; far fewer state the three stages in the right order without prompting, and the ordering is what actually determines behaviour in a redistribution incident.
What is recursive route resolution, and why does a static route pointing at an interface behave differently from one pointing at a next-hop IP?Deep

A recursive route's next-hop must itself be looked up to find an egress interface. A static route with only a next-hop IP is recursive and stays valid as long as that IP is routable; one with an exit interface is directly attached and tracks the interface state instead.

Detail
FormBehaviourFails when
ip route 10.2.0.0 255.255.0.0 10.1.1.1Recursive. Resolved via the route to 10.1.1.110.1.1.1 becomes unroutable
ip route 10.2.0.0 255.255.0.0 Gi0/1Directly attached. ARPs for every destination out that interfaceGi0/1 goes down
ip route 10.2.0.0 255.255.0.0 Gi0/1 10.1.1.1Fully specified. Both conditions must holdEither the interface drops or the next-hop is unreachable

Three consequences worth stating:

  • Interface-only statics on multi-access media are dangerous. The router proxy-ARPs for every destination in the prefix, filling the ARP table and depending on something answering. On a broadcast segment this scales badly and fails silently.
  • Recursive statics survive topology change, which is usually what you want. The route to the next-hop can change path without the static flapping.
  • Fully specified is the correct form on multipoint interfaces — and on Ethernet generally — because it pins both the egress and the next-hop without relying on ARP for distant addresses.
The recursion-to-default trapip route 10.2.0.0 255.255.0.0 10.1.1.1 where 10.1.1.1 is only reachable via a default route. The static resolves recursively through 0.0.0.0/0, so it is installed and appears healthy — and traffic is being sent wherever the default points, which may be the internet. Guard against it with ip route static resolve-default behaviour awareness, or by fully specifying the route.

Follow-ups to expect
  • "How do you make a static route track reachability properly?" — IP SLA plus a tracked object, or BFD with static route tracking. A static route is up because the interface is up, which says nothing about the far end.
  • "What is a floating static?" — a static with a raised AD so it only installs when the preferred dynamic route disappears.
What they're testingWhether you have been burned by this. The interface-only static and the recursion-through-default are both real outage causes, and an engineer who has seen them talks about failure modes rather than syntax.
How does CEF load-share across equal-cost paths, and what is CEF polarization?Deep

CEF hashes per-destination by default — or per source-destination pair — so a given flow always takes one path and stays in order. Polarization is what happens when several layers of devices hash the same fields with the same algorithm and seed, so downstream layers inherit an already-skewed distribution and some paths carry nothing.

Detail

Hashing, not round-robin, because round-robin reorders packets within a flow and TCP interprets reordering as loss. The hash inputs depend on platform and configuration:

ModeHash inputsNote
per-destinationSrc + dst IP typicallyDefault. Flow order preserved
per-packetNone — round robinReorders. Essentially never appropriate
L4 hashingAdds portsBetter entropy for few-host, many-flow traffic
Tunnel / overlayOuter header only unless the platform looks deeperThe usual cause of poor sharing on GRE or IPsec

Polarization is the multi-tier failure. If a distribution pair and a core pair both hash the same five-tuple with the same function and the same seed, the core sees only the subset of flows that the distribution layer already sent one way, and that subset hashes consistently again. Result: half the core links idle while the others congest, with every device reporting a correct ECMP configuration.

The answer they want for the fixVary the algorithm or the seed between tiers — universal adds a per-router seed, and the ID can be set explicitly. Add L4 ports where traffic is few-host and many-flow. On overlays, ensure the encapsulation is giving the transport entropy: GRE keys, IPsec with sensible SPIs, or VXLAN's deliberately randomised source UDP port, which exists precisely so the underlay has something to hash.
Follow-ups to expect
  • "Why does VXLAN randomise the source UDP port?" — the inner flow's entropy is hidden from the underlay, so the VTEP folds it into the outer source port, giving underlay ECMP something per-flow to hash on.
  • "A single large flow is saturating one of four links. What do you do?" — nothing at layer 3; one flow is one hash bucket. The answer is to split the flow at the application, or move to a technology that can spray and reorder, which is a deliberate trade not a configuration change.
What they're testingWhether you understand that ECMP is statistical, not fair. Candidates who say "it load-balances 50/50" have not operated it. Candidates who ask about flow counts and hash inputs have.
Why does summarization create a route to Null0, and what breaks without it?Deep

The discard route stops the summarizing router from forwarding traffic for unused parts of the summary back out along a less specific route — usually its own default — which would form a loop. It makes the summary authoritative locally.

Detail

Consider a router advertising 10.1.0.0/16 while only holding 10.1.1.0/24 and 10.1.2.0/24 internally, and having a default route pointing upstream. A packet for 10.1.99.1 arrives because the upstream believed the /16 advertisement. Without a discard route:

  1. Longest match finds no /24 for 10.1.99.1.
  2. It falls through to 0.0.0.0/0 and goes back upstream.
  3. Upstream still believes the /16 and sends it back.
  4. The packet loops until TTL expires — and so does every packet for every unused address in the summary.

The Null0 route for 10.1.0.0/16 breaks step 2: longest match finds the /16 pointing at Null0 and the packet is dropped locally. One ICMP unreachable, no loop.

A ping to the router's interface succeeds but traffic through the router for the same destination fails. What does that tell you, and where do you look?Expert

It tells you the control plane is reachable and the data plane is not, so the two must be investigated separately. Traffic to the box is punted and handled by the CPU; traffic through the box is forwarded in hardware using the FIB and the adjacency table, and those can be wrong while the RIB is perfect.

Detail

The useful framing: a successful ping to an interface proves ARP, the interface, and the CPU path. It proves nothing about hardware forwarding for transit traffic. Candidates who treat "I can ping the router" as evidence that the router is forwarding have conflated the planes.

Where to look, in order:

  1. Is the FIB consistent with the RIB? show ip cef <prefix> detail versus show ip route <prefix>. A route present in one and absent or different in the other is a programming failure.
  2. Is the adjacency complete? An incomplete or glean adjacency means the rewrite information is missing and packets are punted or dropped.
  3. Is hardware programming failing for a resource reason? TCAM exhaustion silently stops new entries being installed. The software state looks correct; the hardware never received it.
  4. Is a feature dropping it? ACL, uRPF, a policy-map, ZBFW, a VRF mismatch on one interface. Use packet-trace on QFP platforms or FED drop counters on Catalyst.
  5. Is the return path the problem? Forward and reverse are independent. Transit failure that is actually asymmetric routing is extremely common and a ping to the interface will not reveal it.

Say the diagnostic principle out loud"Reachability to the box and reachability through the box test different planes, so I treat them as two separate questions." Follow-ups to expect
  • "How would you prove it is hardware and not routing?" — RIB and FIB agree, adjacency is complete, and a packet-trace or FED drop counter shows the drop with a reason. If the reason is a resource counter, it is hardware.
  • "What if the CPU is at 90%?" — then transit traffic may be being punted when it should be hardware-forwarded. Check punt causes; a feature that is unsupported in hardware on that platform punts everything matching it.
What they're testingThis is an escalation-level question and the answer they want is a method, not a cause. Anyone can list things that break. What distinguishes a senior candidate is immediately partitioning the problem into planes and directions, then naming the command that settles each partition.
Explain unicast RPF, its modes, and where it breaks legitimate traffic.Deep

uRPF validates that a packet's source address is one the router would route back out of the interface the packet arrived on. Strict mode requires the best return path to be that exact interface; loose mode only requires the source to exist in the routing table at all.

Detail
ModeCheckUse where
StrictSource must be routable via the ingress interfaceSingle-homed customer edge, access layer
LooseSource must have any route that is not Null0Asymmetric cores, multihomed transit — filters only unrouted space
VRFSource must be routable in a named VRF's tableMulti-tenant edges

show ip interface Gi0/1 | include verify|drop

show cef interface Gi0/1 internal | include RPF

Where strict mode breaks legitimate traffic — this is the real content of the question:

  • Asymmetric routing. Traffic arrives on one link and the best return path is another. Entirely normal in a multihomed network, and strict uRPF drops it.
  • Multihomed customers whose return traffic prefers the other provider.
  • Default-route-only interfaces. Without allow-default, sources only reachable via 0.0.0.0/0 fail the check.
  • Unequal-cost paths. With one best path installed, the alternate ingress fails strict even though the topology is valid.
  • Tunnels and overlays, where the ingress interface for decapsulated traffic is not the interface the source is routed through.
The deployment answer matters more than the definitionStrict uRPF at the access edge is good practice and cheap. Strict uRPF in a core or on a multihomed edge causes intermittent, direction-dependent, traffic-specific drops that are extremely painful to diagnose — the packets vanish with no ACL hit and no obvious counter. Loose mode in the core gets you the anti-spoofing value that matters (filtering unrouted source space) without the breakage.
Follow-ups to expect
  • "How does uRPF relate to BCP 38?" — it is the mechanism for implementing it at the edge.
  • "How is this different from multicast RPF?" — multicast RPF is structural, not optional: PIM builds trees by checking that traffic arrives on the interface toward the source, and that check is how loop-free distribution trees are formed at all.
What they're testingWhether you can describe a security control together with its operational cost. A candidate who recommends strict uRPF everywhere has not supported it. A candidate who names asymmetry as the limiting factor and places loose mode in the core has.

02ARP, DHCP & DNS

The three protocols everything else depends on, and the three nobody revises. Interviewers like them precisely because a candidate who can explain a glean adjacency, the giaddr field and the ARP-versus-MAC-aging mismatch has clearly operated a network rather than studied one.

Walk through ARP resolution on a router. What is a glean adjacency?Core

For a directly connected prefix, CEF installs a glean adjacency — meaning "the destination is on this segment but I do not yet know its MAC". The first packet to an unresolved host is punted to the CPU, which triggers an ARP request; once the reply arrives, a complete adjacency is installed with the rewrite information and subsequent packets are forwarded in hardware.

High ARP Input CPU is a symptom with a specific shapeThe ARP process spikes when many packets arrive for addresses on a connected subnet that do not exist — because each one gleans, punts, and generates an ARP request that nobody answers. The two causes are a scan sweeping a subnet, and a routed subnet with few or no hosts that still attracts traffic. Both produce a flood of incomplete adjacencies. show ip arp summary showing a large incomplete count alongside ARP Input CPU is conclusive, and the remedy is upstream filtering or ARP rate limiting rather than tuning the ARP process.
Follow-ups to expect
  • "Why is the first packet of a flow sometimes lost?" — because it was punted to trigger ARP, and the punt path is rate-limited and slower than forwarding. Most stacks retransmit, so it is invisible; on a latency-sensitive first packet it is not.
  • "What is the ARP table limit?" — on a layer 3 switch, ARP and ND entries consume hardware adjacency and TCAM resources, so the ceiling is a platform resource rather than a software table. show platform hardware fed switch active fwd-asic resource tcam utilization is where you check it, and a large flat subnet can exhaust it.
What they're testingWhether you connect ARP to the forwarding plane rather than treating it as a standalone protocol. Glean, complete and incomplete are the three words that show you understand how the control plane populates the data plane.
What is proxy ARP, what is local proxy ARP, and why would you disable both?Deep

Proxy ARP makes a router answer ARP requests for addresses it can route to but that are not on the asking segment, so a host with a wrong subnet mask still works. Local proxy ARP makes it answer for addresses that are on the same subnet, forcing intra-subnet traffic through the router. The first hides misconfiguration and is a security and scaling liability; the second is a deliberate tool for specific designs.

Why proxy ARP is a problem:

  • It hides misconfiguration. A host with a /16 mask on a /24 subnet works perfectly because the router answers for everything. The day proxy ARP is disabled — or that host moves — it breaks, and nobody remembers why it ever worked.
  • ARP table bloat. The router accumulates entries and the hosts accumulate entries pointing at the router's MAC for many addresses.
  • A security exposure. An attacker on the segment can ask the router for any address it can route to and get an answer, which aids reconnaissance and can be used to intercept traffic.
  • It confuses troubleshooting. Traffic that should be routed appears to be bridged, and show ip arp on the host shows the router's MAC for a remote address.

What they're testingWhether you know proxy ARP is on by default and should usually be off. The local-proxy-ARP-plus-no-redirects pairing is the expert detail and it is directly relevant to private VLAN and wireless isolation designs.
What is gratuitous ARP used for, and what problems does it cause?Deep

A gratuitous ARP is an unsolicited announcement of your own IP-to-MAC mapping. Its legitimate uses are duplicate address detection, and telling a segment that a mapping has changed — after a NIC team failover, a VM migration, a cluster failover, or an FHRP event. Its problem is that ARP has no authentication, so the same mechanism is how ARP spoofing works.

Detail
Legitimate useWhat it achieves
Duplicate address detectionA host announces its address; a reply means somebody else has it
NIC team or bond failoverThe IP has moved to a different MAC — everyone must update
VM migrationSame MAC, new location — updates the switches' MAC tables immediately rather than waiting for aging
Cluster or appliance failoverA service address moves between nodes
FHRP state changeSent on becoming active, to flush any stale mapping

Why HSRP does not depend on it: because HSRP uses a shared virtual MAC that moves with the active role, hosts never need to update their ARP entries at all — the MAC they have is still correct. The gratuitous ARP on state change is belt-and-braces to flush the switches' MAC tables so frames for the virtual MAC reach the new active router quickly. That distinction — virtual MAC means no host relearning — is worth stating, because it explains why FHRP failover is faster than a cluster failover that relies on GARP propagation.

A GARP storm during a failover event is a real failure modeA cluster or hypervisor platform that announces several hundred addresses by gratuitous ARP when it fails over sends a burst of broadcasts, each of which every host and switch processes. On a large flat VLAN that is a brief but genuine broadcast event, and on a device with ARP inspection rate limits it can trip the limit and err-disable the port — so the failover mechanism takes the port down. The mitigations are smaller VLANs, ARP inspection rate limits set with headroom and burst tolerance, and err-disable recovery configured for ARP inspection.
What they're testingWhether you know what legitimately generates gratuitous ARP, because the answer tells you whether an observed burst is an attack or a failover. The HSRP virtual-MAC point is a good differentiator.
ARP timeout is four hours and MAC aging is five minutes. What does that mismatch cause?Deep

Persistent unknown unicast flooding. A host that is quiet for more than five minutes loses its MAC table entry on the switches while every other host still has a valid ARP entry for it — so traffic sent to it is flooded to every port in the VLAN until the host transmits something and is re-learned.

Detail

The sequence: host A has an ARP entry for host B, valid for four hours. Host B goes quiet for six minutes, so the switches age out its MAC. Host A sends to B's MAC, which is now unknown, so every switch in the VLAN floods the frame out every port. B replies and is re-learned, and the flooding stops — until B goes quiet again.

For a normal host this is a brief, barely noticeable event, because hosts rarely stay silent for five minutes. It becomes a real problem in three cases:

  • Genuinely silent devices. Some printers, sensors, licence dongles and appliances only ever receive. They are never re-learned, so all traffic to them floods permanently.
  • Asymmetric paths. A firewall sandwich or one-armed load balancer means a server's replies leave by a different path, so the switch on the request path never learns its MAC from a frame in that direction.
  • High-rate flows to a quiet destination. A monitoring or replication stream to a device that does not talk back floods at full rate across the VLAN.

Explain DHCP relay. What does giaddr do, and what else does ip helper-address forward?Deep

The relay receives the client's broadcast, writes its own receiving-interface address into the giaddr field, and unicasts the request to the server. The server uses giaddr to decide which scope to allocate from, so that one field determines which subnet the client gets an address in. And ip helper-address does not only forward DHCP — by default it forwards eight UDP services.

The flow
  1. Client broadcasts DISCOVER to 255.255.255.255 from 0.0.0.0.
  2. The SVI or routed interface receives it, sets giaddr to its own primary address on that interface, increments the hop count, and unicasts it to each configured helper address.
  3. The server matches giaddr against its configured scopes and allocates from the matching one. It sends the OFFER unicast back to giaddr.
  4. The relay delivers it to the client, broadcast or unicast depending on the broadcast flag.
  5. REQUEST and ACK follow the same path.
ip helper-address forwards eight UDP services, not oneBy default it relays TIME (37), TACACS (49), DNS (53), BOOTP server and client (67, 68), TFTP (69), NetBIOS name and datagram service (137, 138). So configuring a helper address pointing at a DHCP server also forwards broadcast DNS, TFTP and NetBIOS traffic to that host — which is unnecessary load, an information leak, and occasionally a genuine problem when a broadcast-heavy legacy application starts reaching a server it should not. A stub resolver on the client asks a recursive resolver, which walks the hierarchy on its behalf — root, then the TLD's servers, then the zone's authoritative servers — caching each answer for its TTL. Anycast DNS advertises the same resolver address from many locations and lets ordinary routing pick the nearest instance, which works because DNS queries are stateless.

OSPF questions separate people who have configured it from people who understand the LSDB. The discriminating topics are the forwarding address, type 4, what actually triggers a full SPF, and the ABR rule that makes inter-area routing loop-free.

Why does OSPF elect a DR on a broadcast network but not on point-to-point, and what do the network types change?Core

On a multi-access segment, n routers would otherwise form n(n−1)/2 adjacencies and each would originate its own view of the segment. The DR reduces that to a star and originates one type 2 LSA representing the segment. On point-to-point there are only ever two routers, so there is nothing to optimise and no segment to describe.

Detail

Two separate jobs the DR does, and candidates usually name only the first:

  • Flooding reduction. Routers form full adjacencies with the DR and BDR only, so flooding is star-shaped rather than mesh.
  • Segment representation. The DR originates the type 2 network LSA, which lists every router attached to the segment. Without it there is no way to express "these five routers share one transit link" in the LSDB, and the SPF graph would be wrong.

What is the forwarding address in a type 5 LSA, when is it non-zero, and what happens if it is unreachable?Expert

A zero forwarding address means "send traffic for this external prefix to me, the advertising ASBR". A non-zero one means "send it directly to this address instead", letting routers bypass the ASBR when the real next-hop is itself inside OSPF. If the forwarding address is not reachable in OSPF, the external route is not installed at all.

Detail

The ASBR sets a non-zero forwarding address when the next-hop toward the external destination is on an interface where all of the following hold:

  • OSPF is enabled on that interface,
  • the interface is not passive,
  • and the network type is not point-to-point or point-to-multipoint.

In other words: the next-hop lives on a broadcast or NBMA segment that OSPF already knows about, so there is no reason to funnel traffic through the ASBR. The canonical case is redistributing a static route whose next-hop is a router on a shared Ethernet segment that is also running OSPF.

The failure mode is the point of the questionIf the forwarding address is unreachable — because the segment it sits on is not advertised into OSPF, or it is in a different area that has been summarized away, or a filter removed the type 3 covering it — then every router computes "I cannot reach the forwarding address" and silently does not install the external route. The type 5 LSA is present in the database on every router, looks completely healthy, and the route is absent from the RIB. This is one of the hardest OSPF faults to spot because the LSDB gives no hint that anything is wrong.

Type 7 LSAs in an NSSA behave the same way and, by design, carry a non-zero forwarding address. When the ABR translates type 7 to type 5 it preserves that forwarding address, so the reachability requirement now applies across the whole AS. An NSSA whose internal segments are summarized at the ABR can therefore produce externals that nobody outside can use.

Follow-ups to expect
  • "How do you fix an unreachable forwarding address?" — advertise the segment into OSPF, or stop the summarization or filtering that removed it, or change the ASBR's interface so the forwarding address is zero (make it passive, or point-to-point), which forces traffic through the ASBR.
  • "Why would you want a non-zero forwarding address?" — it avoids a suboptimal hop through the ASBR when a better direct path exists.
What they're testingThis is a genuine expert discriminator. It is not in the basic curriculum, it causes real outages, and the symptom — LSA present, route absent, no error anywhere — is one you only recognise if you have met it or studied the LSA format properly.
In an NSSA, which router translates type 7 to type 5, and how is it chosen?Deep

The NSSA ABR with the highest router ID among those eligible performs the translation. With multiple ABRs only one translates, to avoid duplicate type 5 LSAs for the same prefix entering the backbone.

Detail

The type 7 LSA carries a P bit (propagate). The elected translator takes type 7 LSAs with the P bit set, re-originates them as type 5 with itself as the advertising router, preserves the forwarding address, and floods them into the rest of the AS. It also originates a type 4 for itself into the backbone so other areas can resolve the new ASBR.

  • Election is by highest router ID among NSSA ABRs, and it is re-evaluated if the translator fails, so this is a failover mechanism not a static assignment.
  • The P bit is cleared when the originating router is itself the NSSA ABR, because translation would be redundant.
  • You can force a router to translate regardless of election with translate type7 always, which is occasionally needed and is also a way to create duplicate type 5s if you set it on two routers.

What does a virtual link actually do, and why is it not a tunnel?Deep

A virtual link logically extends area 0 across a non-backbone transit area, so an ABR that is physically disconnected from the backbone still has a backbone interface. It carries OSPF control traffic only, as ordinary unicast IP routed through the transit area — there is no encapsulation and no user data path, which is why it is not a tunnel.

Detail

Mechanically it is treated as an unnumbered point-to-point link in area 0 between the two ABRs' router IDs. Both endpoints appear in each other's area 0 type 1 LSA, which restores backbone contiguity from OSPF's point of view.

  • Configured between router IDs, not interfaces, and must be configured on both ends.
  • The transit area cannot be a stub area — it needs full routing information to carry the backbone's LSAs and to route between the two router IDs.
  • Both routers must have reachability to each other's router ID through the transit area.
  • LSAs flooded over a virtual link have the DoNotAge bit set, because virtual links are treated as demand circuits. This is a favourite detail to ask about.
  • User traffic does not follow the virtual link. It follows ordinary routing through the transit area. The virtual link only fixes the LSDB's view of topology.

Which LSA changes trigger a full SPF run and which do not? Why does that matter for design?Expert

Only type 1 and type 2 changes alter the topology graph, so only those require a full Dijkstra run — and only within the affected area. Type 3, 4, 5 and 7 changes are leaf prefixes hanging off an already-computed graph, so they trigger a cheaper partial route calculation instead.

The design consequences follow directly, and this is what the question is really after:

  • Areas bound the cost of instability. A flapping link generates type 1 and 2 churn, and full SPF, only inside its own area. Every other area sees at most a type 3 change and a partial calculation. This — not LSDB size — is the main argument for areas.
  • Summarization at the ABR hides the churn entirely. If the flapping prefix is inside a summarized range, the type 3 does not even change, so other areas compute nothing. Summarization converts a topology event into a non-event.
  • Many externals are cheap; many intra-area links are expensive. Ten thousand type 5 LSAs cost memory and partial calculations. A few hundred routers in one area cost full SPF runs on every flap, repeatedly, on every router in the area.
  • Throttling protects the CPU during instability, at the price of convergence time.

What exactly makes a router an ABR, and what rule stops inter-area routing from looping?Expert

An ABR has interfaces in two or more areas, one of which must be area 0 with an active backbone connection. The loop-prevention rule is that an ABR computes inter-area routes only from type 3 LSAs received over the backbone, and never re-advertises a type 3 learned from a non-backbone area back into the backbone. Inter-area traffic is therefore forced through area 0.

Detail

Because type 3 carries a prefix and a cost rather than a topology, OSPF cannot detect an inter-area loop by graph computation the way it does inside an area. It needs a structural rule instead, and that rule is the backbone-as-hub constraint:

  • Every area attaches to area 0. Traffic between area 10 and area 20 transits area 0.
  • An ABR only trusts summaries learned from the backbone for its own route computation. A summary learned from a non-backbone area is not used and is not propagated into the backbone.
  • Consequently a chain of non-backbone areas cannot form a transit path, and a loop cannot be built out of summaries.

RFC 3509 sharpened the definition: a router with an area 0 interface that is down is not functionally an ABR, and should not be originating type 3 LSAs into other areas as though it had backbone connectivity. Older implementations differed here, which is why "has an interface in area 0" is a weaker answer than "has an active backbone connection".

The practical consequence candidates missAn ABR that loses its backbone connection but keeps its other area interfaces up can, on implementations that do not follow RFC 3509, continue advertising summaries it can no longer reach — attracting traffic into a black hole. A virtual link is the sanctioned repair for a partitioned backbone precisely because it restores a real active backbone connection rather than papering over the loss.

  • "Why does OSPF need this when EIGRP does not?" — EIGRP's loop prevention is per-route and arithmetic (the feasibility condition), so it needs no topological constraint. OSPF's inter-area loop prevention is topological, so it does. That contrast is a strong answer and sets up the EIGRP section.
  • "Does an ABR summarize by default?" — no. Type 3 LSAs are generated per intra-area prefix unless you configure area range. People assume ABRs aggregate automatically; they do not.

04EIGRP

EIGRP interviews live or die on the feasibility condition. Everything else — queries, stub routers, SIA, variance — follows from it, and a candidate who can state it precisely can derive the rest on the spot.

State the feasibility condition and explain why it guarantees a loop-free path.Core

A neighbour is a feasible successor if its reported distance is strictly less than my feasible distance. That works as a loop guarantee because a neighbour routing through me would necessarily report a distance equal to or greater than my own best metric, so a lower reported distance proves it has an independent path.

Detail
The four terms, precisely
TermDefinition
Reported distance (RD), also advertised distanceThe metric the neighbour advertises — its cost to the destination, not including my link to it
Feasible distance (FD)The lowest metric known since the route last went passive — not necessarily the current best metric
SuccessorThe neighbour giving the lowest total metric (RD plus my cost to that neighbour)
Feasible successorA neighbour with RD < FD. A pre-validated backup, installable with no computation

The intuition to say out loud: "if your cost to the destination is lower than my best-ever cost, you cannot be going through me." That is the whole loop-prevention argument, and it is arithmetic rather than topological — which is why EIGRP needs no areas, no backbone and no split-horizon rules between regions.

The FD definition is the trapFD is the lowest metric since the last transition to passive, not the current metric. So if the metric to a destination rises while the route stays passive, FD stays at the old lower value — and neighbours that would now qualify as feasible successors still fail the test against the stale, lower FD. The route can end up with no feasible successor despite viable alternate paths existing, and go active unnecessarily. Candidates who define FD as "my current best metric" get the mechanism wrong in exactly the case that matters.

Give the EIGRP metric formula, the default K values, and explain why wide metrics were introduced.Deep

By default the metric is 256 × (107/minimum bandwidth in kbps + total delay in tens of microseconds), because only K1 and K3 are non-zero. Wide metrics exist because 107/bandwidth saturates at high speeds — a 10 Gbps and a 100 Gbps link produce the same bandwidth term, so classic EIGRP cannot tell them apart.

Detail 
! classic composite metric
metric = 256 * [ K1*BW + (K2*BW)/(256-Load) + K3*Delay ] * [ K5 / (Reliability + K4) ]

  BW    = 10^7 / minimum bandwidth along the path, in kbps
  Delay = sum of all delays along the path, in tens of microseconds

! defaults: K1=1  K2=0  K3=1  K4=0  K5=0
! when K5 = 0 the entire reliability term is omitted, not treated as zero

! so in practice
metric = 256 * ( 10^7/min_BW + sum_delay/10 )
  • Bandwidth is the minimum along the path, not the sum — it represents the bottleneck.
  • Delay is cumulative. That makes delay the right knob for influencing path selection, since changing bandwidth also affects QoS reservations, ingress shaping references and other features that read the interface bandwidth.
  • K values must match on both sides or the adjacency will not form. They are carried in hello packets. A K-value mismatch is a classic "neighbour will not come up with no obvious reason" cause.
  • Load and reliability are off by default for good reason — enabling them makes the metric time-varying, which produces continuous reconvergence. Say this if asked whether to turn them on: the answer is no.

Wide metrics (EIGRP named mode) address the scaling ceiling:

  • The metric becomes 64-bit internally, so high-speed links are distinguishable.
  • A sixth constant, K6, is added for extended attributes such as jitter and energy.
  • Because the RIB still holds a 32-bit metric, a RIB scale factor (default 128) divides the wide metric down on installation. Two different wide metrics can therefore scale to the same RIB metric, which is worth knowing when metrics look surprisingly equal.
  • Classic and wide metric routers interoperate — the metric is converted at the boundary — but you lose the resolution that wide metrics provide.

When does an EIGRP route go active, and what is Stuck-In-Active?Deep

A route goes active when its successor is lost and no feasible successor exists, forcing the router to query its neighbours for an alternative. Stuck-In-Active is what happens when some neighbour fails to reply within the active timer — by default three minutes — and the router tears down the adjacency to that neighbour to break the deadlock.

Detail

The sequence: successor lost → check for a feasible successor → if one exists, install it immediately with no query and no delay (this is the fast case, and the entire point of the feasibility condition) → if none, mark the route active and query every neighbour except the one the route was lost through, then wait for a reply from each.

The router cannot converge until every outstanding reply arrives. One slow, busy or broken neighbour therefore stalls the whole computation, and that is the root of SIA.

Cause of SIAWhy
Query domain too largeQueries propagate until they hit a boundary; a flat network has none, so one flap queries everything
Overloaded or slow router in the pathCPU-starved router cannot process and reply in time
Unidirectional linkQuery leaves, reply never arrives
Packet loss on a WAN linkEIGRP queries and replies are reliable, but retransmission takes time
Low-bandwidth link with insufficient EIGRP bandwidth shareDefault caps EIGRP at 50% of interface bandwidth; on a congested slow link, replies queue
Very high neighbour count on one routerMany replies to generate, serially

Modern IOS mitigates this with SIA-Query and SIA-Reply: at roughly half the active timer the router asks the silent neighbour "are you still working on this?". A neighbour that answers buys more time; one that does not gets its adjacency reset. This prevents an innocent, healthy neighbour being torn down because a router three hops beyond it is slow.

In a flat network with no boundaries, one link flap can query every router in the AS. The three real boundaries are summarization, stub routers, and filtering.

What does an EIGRP stub router advertise, and what are the options?Deep

By default eigrp stub advertises connected and summary routes only, and — the more important half — its neighbours stop sending it queries entirely. The stub declares itself incapable of being a transit path, which both reduces its advertisements and removes it from the query domain.

Explain variance. Why is traffic rarely split the way people expect?Deep

Variance installs additional paths whose total metric is less than the multiplier times the feasible distance — but only paths that already pass the feasibility condition. Traffic is then shared inversely proportional to metric, not evenly, so a path twice as costly carries roughly half the traffic.

Detail

Two constraints, and candidates usually state only the first:

  1. Total metric < variance × FD.
  2. The path must be a feasible successor. A path that fails RD < FD is never installed no matter how high you set variance. This is the constraint that surprises people: you raise variance, nothing changes, and the reason is feasibility, not the multiplier.
router eigrp 100
 variance 2
 traffic-share balanced            ! default — proportional to metric
 traffic-share min across-interfaces   ! use only the best, but keep alternates in the FIB
 maximum-paths 4

show ip eigrp topology all-links    ! what failed feasibility and why

traffic-share min across-interfaces is worth knowing: it keeps unequal-cost paths in the topology table and the FIB as pre-installed backups while sending traffic only over the best path. You get instant failover without the suboptimal routing that actually using the worse path entails — which is usually what people wanted when they reached for variance.

Unequal-cost load sharing is usually the wrong toolSplitting a flow set across paths of genuinely different quality means a predictable fraction of users get the worse experience, and which users varies with the hash. Jitter-sensitive traffic on the slow path is worse than all traffic on the fast one. If an interviewer asks whether to deploy variance, the defensible answer is: rarely, and traffic-share min for fast failover much more often. Saying that shows operational judgement rather than feature enthusiasm.
What they're testingTwo things: whether you know feasibility gates variance, and whether you can say "this feature is usually a bad idea" about something EIGRP is famous for. Confidently recommending against a textbook feature, with reasons, reads as senior.
You are running EIGRP over DMVPN. Spokes cannot reach each other's prefixes. What is happening?Expert

Split horizon on the hub's multipoint tunnel interface is suppressing re-advertisement of routes back out the interface they were learned on, so spoke A's prefixes never reach spoke B. The companion problem is that the hub rewrites the next-hop to itself, forcing all spoke-to-spoke traffic through the hub even once the routes are present.

Detail

Two independent settings, and a complete answer needs both:

  • no ip split-horizon eigrp <as> on the tunnel interface lets the hub advertise spoke routes back out the same multipoint interface. Without it spokes learn only the hub's own prefixes. This is the fix for routes missing.
  • no ip next-hop-self eigrp <as> stops the hub rewriting the next-hop to itself, so spoke B learns spoke A's prefix with spoke A as the next-hop. This is the fix for traffic hairpinning through the hub, and it is what allows a dynamic spoke-to-spoke tunnel to be built at all.

Phase 2Direct, built on demandSpokes need the specific prefix with the spoke as next-hop. no ip next-hop-self required; summarization at the hub breaks it
Phase 3Direct, via NHRP redirect and shortcutHub can summarize — NHRP installs a shortcut on redirect. The usual modern choice

Follow-ups to expect
  • "Why is MTU always a problem on DMVPN?" — GRE plus IPsec overhead exceeds what is left of a 1500-byte path. Set ip mtu on the tunnel and ip tcp adjust-mss so TCP negotiates a fitting segment size; without the MSS clamp, large TCP flows stall while ping works, which is the signature.
  • "Why not BGP over DMVPN?" — it scales better for very large spoke counts and is common in modern designs; the trade is slower convergence and more configuration per spoke unless you use dynamic peer groups.

Why is next-hop-self needed for iBGP, and what are the alternatives?Core

When an eBGP route is advertised into iBGP, the next-hop attribute is left unchanged — it still points at the external peer's address on the eBGP link. Internal routers have no route to that address, so the path fails the reachability gate and is never selected. next-hop-self rewrites it to the advertising router's own address, which the IGP already knows.

Detail

The default behaviour is deliberate: preserving the next-hop allows optimal forwarding on a shared exchange fabric, where a third-party next-hop on the same segment is directly reachable. Inside a normal enterprise or SP core it is simply broken, because the DMZ link is not in the IGP.

Why does iBGP require a full mesh, and why does AS_PATH not solve it?Deep

AS_PATH is only modified when a route crosses an AS boundary, so two routers inside the same AS see identical AS_PATHs and cannot use them to detect a loop. BGP therefore applies a blunt structural rule instead: a router never advertises an iBGP-learned route to another iBGP peer. Because propagation stops after one hop, every internal speaker must hear it directly — a full mesh.

Detail

This is the cleanest way to show you understand BGP's loop prevention as layered:

  • Between ASes: AS_PATH. A router rejects any path containing its own AS number. Arithmetic-free, works at internet scale.
  • Within an AS: AS_PATH is useless, so the rule is "do not re-advertise iBGP to iBGP". Loop prevention by topology constraint.
  • Relaxations then need their own loop prevention, which is exactly what route reflectors and confederations provide.

The cost of a full mesh is n(n−1)/2 sessions. Forty routers is 780 sessions, each with its own TCP connection, update generation and memory for received paths. It becomes unmanageable well before it becomes impossible.

RelaxationLoop prevention usedTrade-off
Route reflectorsORIGINATOR_ID and CLUSTER_LISTSimple to add incrementally; reduces path diversity
ConfederationsAS_CONFED_SEQUENCE in AS_PATHReal policy boundaries between sub-ASes; a bigger structural change
Why route reflectors wonConfederations are architecturally tidier — they give you genuine policy boundaries and let different regions run independently. Route reflectors won in practice because they can be introduced into an existing full mesh one router at a time with no renumbering and no coordinated change. If asked which you would choose, that deployment-friction argument is the honest answer, and mentioning that very large SPs sometimes combine both (confederations with RRs inside each sub-AS) shows range.
What they're testingWhether you can explain a rule by its purpose. Plenty of candidates state the full-mesh requirement; far fewer explain that it exists because AS_PATH does not change internally, and that RRs and confederations are each substituting a different loop-prevention mechanism in its place.

Why is MED only compared between paths from the same AS? What do always-compare-med and deterministic-med do?Expert

MED is a hint set by a neighbouring AS about which of its entry points to prefer. Two different ASes have no shared scale — one may use 10 and 20, another 1000 and 2000 — so comparing across them is meaningless. always-compare-med removes that restriction and makes path selection depend on arbitrary external numbering; deterministic-med makes the outcome independent of the order paths were received.

Detail

Why the default restriction is right: MED is the one attribute an AS uses to influence its neighbour's inbound traffic. AS 100 setting MED 10 on its London link and 20 on its Frankfurt link is saying "prefer London for traffic to me". That statement is only coherent within AS 100's own announcements. Comparing AS 100's 10 against AS 200's 5 compares two unrelated internal policies and lets whichever AS happens to use smaller numbers win.

SettingEffectRisk
bgp always-compare-medCompare MED across all ASesCedes your path selection to other people's numbering. Can also cause oscillation
bgp deterministic-medGroup paths by neighbouring AS, pick the best in each group, then compare groupsNone meaningful. Should arguably be on everywhere
bgp bestpath med missing-as-worstTreat a missing MED as infinity rather than 0Changes selection; default treats missing MED as the best possible value
bgp bestpath med confedCompare MED among confederation sub-AS pathsConfederation-specific

What deterministic-med actually fixes: without it, BGP compares paths in the order they were received, and because MED comparison is conditional on the neighbouring AS matching, the comparison is not transitive. Path A can beat B, B can beat C, and C can beat A. The winner then depends on which session established first — so two identically configured routers choose differently, and a router chooses differently after a reload. With deterministic-med, paths are grouped by neighbouring AS first, so the comparison becomes well-defined and the result is reproducible.

MED oscillation is a real documented failureMED's non-transitivity combined with route reflection can produce persistent route oscillation — the network never settles, with BGP continuously re-advertising and withdrawing. This is the subject of RFC 3345. The practical mitigations are deterministic-med, avoiding always-compare-med, and not relying on MED across a reflected topology. If an interviewer asks for an example of a protocol that can fail to converge by design, this is an excellent one to have ready.

Enable it where the paths are equivalent by construction; be cautious where they are only equal in hop count.

What is RPKI origin validation, what are the three states, and what does it not protect against?Deep

A router fetches validated data from a cache over the RTR protocol and classifies each path as Valid, Invalid or NotFound. It validates only the origin — it says nothing about whether the rest of the AS_PATH is genuine.

What it does not protect against — the discriminating half of the answer:

  • Path manipulation. An AS can leave the origin intact and insert itself into the middle of the path to attract traffic. ROV sees a valid origin and accepts it.
  • Route leaks. A customer re-announcing a transit provider's routes to another provider has a perfectly valid origin. This is the most common real incident type and RPKI does not address it — that is what RFC 9234 roles / Only-To-Customer and ASPA are for.
  • Missing coverage. NotFound is not safe, merely unvalidated, and most operators cannot reject it without losing reachability.
  • maxLength mistakes. A ROA with a loose maxLength permits more-specific hijacks within your own space, which is a self-inflicted hole and a documented operational pitfall.

What they're testingWhether security knowledge is current and appropriately bounded. The three states are table stakes. Knowing that route leaks are the common failure and are not covered by RPKI is what distinguishes a well-informed answer from a headline-level one.

06Redistribution & policy

Redistribution is where most real routing outages come from, so interviewers weight it heavily. The questions are rarely about syntax — they are about whether you can see the loop before you create it.

Two routers mutually redistribute OSPF and EIGRP. What goes wrong and how do you prevent it?Deep

A route can leave one domain, cross into the other, come back through the second redistribution point, and be re-advertised into its original domain with a better administrative distance than the native route — producing a loop or a black hole. The standard prevention is route tagging: tag on the way out and deny tagged routes on the way back in.

Detail

The mechanism in order:

  1. Prefix 10.1.1.0/24 originates in OSPF.
  2. Router A redistributes it into EIGRP. It is now an EIGRP external route, AD 170.
  3. Router B hears it in EIGRP and redistributes it back into OSPF as an E2 external, AD 110.
  4. On a router that hears both, the re-injected external at AD 110 competes with the native OSPF route — and in parts of the topology the loop route wins.
  5. Traffic is forwarded toward the redistribution point rather than toward the actual destination.

Two things make it worse: the metric is lost at each boundary, so comparisons are meaningless; and asymmetry means different routers choose differently, which is how you get a loop rather than simply a suboptimal path.

Prevention, strongest first

One-way redistribution plus a defaultRedistribute only in one direction; use a default route the other way. The cleanest design where it fits

Follow-ups to expect

  • "What if the two domains share a subnet range?" — then tagging is the only workable answer, because prefix-based filtering cannot distinguish the two directions.
What they're testingWhether you have cleaned up after a redistribution incident. The AD-based explanation of why the loop forms, and the preference for tags over prefix lists on maintainability grounds, are both experience markers.

Explain route-map processing order, the implicit deny, and what continue does.Deep

Clauses are evaluated in sequence number order and processing stops at the first clause whose match conditions are all satisfied. That clause's permit or deny then decides the outcome, and its set statements apply. If no clause matches, an implicit deny applies — which in redistribution means the route is not redistributed.

The implicit deny is the single most common route-map outageSomeone writes a route-map to set an attribute on a subset of routes, applies it to redistribution or to a BGP neighbour, and everything not matched is dropped. Half the routing table disappears and the configuration reads as though it only added a metric. The discipline: every route-map that is meant to modify rather than filter ends with a bare permit clause at a high sequence number. Say that as a rule you follow, not as a fact you know.

  • "How do you verify a route-map is doing what you think?" — show route-map for per-clause hit counts, and for BGP show ip bgp neighbors X advertised-routes or received-routes with soft-reconfiguration. What they're testingWhether you can be trusted to write policy on a production router. The implicit deny and the AND/OR semantics are exactly the two things that cause accidental outages, and interviewers for senior roles are screening for the person who will not cause one.

A colleague proposes fixing a routing problem by changing administrative distance. Why is that usually wrong?Expert

Administrative distance is purely local — it changes which route this router installs and nothing about what any protocol advertises. So you alter one router's forwarding decision while every other router keeps its own, which is how you turn a suboptimal path into asymmetric forwarding and, with redistribution in the picture, into a loop.

Detail

Three properties that make AD manipulation hazardous:

  • It is not advertised. Unlike local preference, AD is not a protocol attribute. Nothing propagates, so consistency across routers is entirely up to you remembering to configure every one of them.
  • It does not change protocol behaviour. The losing protocol still holds the route in its own database and still advertises it according to its own rules. You have changed the RIB, not the control plane.
  • It is invisible in troubleshooting. A non-default AD set years ago on one router in a route-map clause is extremely hard to find when the symptom appears elsewhere.

Walk a packet from CE through an MPLS VPN core to the far CE, naming every label.Deep

Two labels in the stack. The outer transport label gets the packet across the core to the remote PE and is swapped at every P router; the inner VPN label tells the remote PE which VRF the packet belongs to and is only read at the end.

Detail
  1. CE → ingress PE: a plain IP packet arrives on a VRF interface.
  2. Ingress PE lookup: the PE looks up the destination in that VRF's table. It finds a VPNv4 route whose BGP next-hop is the remote PE's loopback, carrying a VPN label the remote PE allocated.
  3. Label imposition: the PE pushes the VPN label (inner) and then the transport label (outer) for the remote PE's loopback, learned from LDP or derived from a segment-routing prefix SID.
  4. P routers: each swaps the outer label only, using its LFIB. A P router never sees the VPN label and holds no customer routes — which is the entire scalability argument for MPLS VPN.
  5. Penultimate hop: pops the outer label, because the egress PE advertised implicit null. The packet arrives at the PE carrying only the VPN label.
  6. Egress PE: reads the VPN label, which identifies the VRF and often the exact outgoing interface, pops it, and forwards plain IP to the CE.

Why is MTU a recurring problem in MPLS, and what does no mpls ip propagate-ttl do?Deep

Every label adds four bytes, and a VPN packet carries at least two — more with fast reroute or traffic engineering. What problem does LDP-IGP synchronisation solve, and how does segment routing avoid it entirely?Expert

The IGP and LDP converge independently, so a restored link can be in the IGP's shortest path before LDP has exchanged labels on it. Traffic is then forwarded over a path with no label binding and is dropped — a black hole lasting until LDP catches up. LDP-IGP sync holds the link at maximum IGP metric until LDP is ready. Segment routing removes the problem by deriving labels from the IGP itself, so there is no second protocol to be out of step with.

Detail

The failure sequence, which is worth narrating:

  1. A core link is restored.
  2. The IGP forms its adjacency in a second or two and installs the link as the best path.
  3. LDP's own discovery and session establishment take longer.
  4. For the gap between the two, labelled traffic is directed over a link with no label binding for the destination.
  5. The packet is dropped, or forwarded unlabelled into a core that cannot route the customer prefix. Either way, a black hole — and only for MPLS traffic, so plain IP tests pass.

08Multicast

Multicast questions sort candidates fast because the failure modes are unusual — RPF, state in the middle of the network, and a layer 2 behaviour that depends on something sending queries. Most engineers have configured it; far fewer have debugged it.

Compare PIM dense mode, sparse mode, SSM and bidirectional PIM.Core

Dense mode floods and prunes, assuming receivers are everywhere — wrong for almost every real network, and effectively deprecated. Sparse mode requires an explicit join toward a rendezvous point, which is the general-purpose answer. SSM drops the RP entirely by having receivers name the source. Bidir builds one shared tree used in both directions for many-to-many applications.

Why SSM is the modern default where the application allows it: no RP means no RP redundancy design, no MSDP, no Auto-RP or BSR, no shared tree, no switchover, and no registration. The receiver signals (S,G) with IGMPv3 and the tree is built straight to the source. An entire category of multicast failure simply does not exist. What is the multicast RPF check, and why is it the most common cause of multicast failure?Deep

A router accepts a multicast packet only if it arrives on the interface that the unicast routing table says is the way toward the source. Anything else is dropped. That single rule is how PIM builds loop-free trees without any topology computation — and it means multicast forwarding depends entirely on the unicast routing table being symmetric.

Explain the switchover from the shared tree to the shortest-path tree, and when you would suppress it.Deep

A receiver's first-hop router joins (*,G) toward the RP, so traffic initially flows down the shared tree. Once packets arrive, the last-hop router learns the actual source address, joins (S,G) directly toward the source, and once that traffic arrives on the correct RPF interface it sends an (S,G) RP-bit prune toward the RP to stop the duplicate. By default this happens on the first packet.

Detail
  1. Receiver sends an IGMP report. Last-hop router creates (*,G) and sends a PIM join toward the RP.
  2. Source starts sending. Its first-hop router unicasts PIM register messages to the RP, which joins (S,G) toward the source and then sends a register-stop.
  3. Traffic flows source → RP → shared tree → receiver. Possibly a long way round.
  4. The last-hop router now knows the source address from the packets themselves, so it joins (S,G) toward the source directly.
  5. When (S,G) traffic arrives on the right interface, the T flag is set and the router sends an (S,G) RP-bit prune up the shared tree, cutting the duplicate.
  6. Steady state: traffic follows the shortest path from source to receiver, and the RP is out of the data path.

ip pim spt-threshold infinity            ! never switch; stay on the shared tree

When to suppress it with spt-threshold infinity:

  • Many low-rate sources per group. Each (S,G) is state on every router in the path. A thousand sources means a thousand entries; staying on the shared tree means one (*,G). This is the main reason, and it is a state-scaling argument.
  • Bidir-PIM does this inherently — it has no (S,G) concept at all.
  • Deliberately steering all traffic through the RP, for instance so it passes a specific inspection or accounting point.
The trade-off to state explicitlySwitching to the SPT gives optimal paths and takes the RP out of the data path, at the cost of (S,G) state proportional to the number of sources. Staying on the shared tree gives minimal state and suboptimal paths, with the RP carrying all the traffic. The right choice depends entirely on source count versus bandwidth: few high-rate sources favour the SPT, many low-rate sources favour the shared tree. Framing it as state-versus-optimality rather than reciting the default is what makes this a senior answer.
What they're testingWhether you can describe multicast as distributed state rather than as configuration. The RP-bit prune step is the detail that shows you understand how the duplicate is avoided, and candidates frequently omit it.

The 32-to-1 MAC overlap — the expert follow-upAn IPv4 multicast group maps to a MAC address by placing the low 23 bits of the group address into 0100.5e00.0000. The group's low 23 bits, from a 28-bit group identifier, means 32 different groups share one multicast MAC. 239.1.1.1 and 239.129.1.1 both map to 0100.5e01.0101. A switch forwarding purely on MAC therefore delivers both groups to the ports that joined either one, so a receiver gets traffic for a group it never joined. On a high-rate feed that is real unwanted load, and it looks like a snooping bug. The mitigation is an addressing plan that avoids collisions in the low 23 bits — and the reason to know it is that no amount of snooping configuration will fix it.
Follow-ups to expect

  • "What does immediate-leave do and when is it unsafe?" — it removes the port on receiving a leave without waiting for a group-specific query. Safe with one receiver per port; unsafe with several hosts behind a hub or a VM host, where it cuts off receivers that are still interested.
What they're testingThe querier answer is the one they want, and getting it quickly demonstrates layer 2 multicast experience. The MAC overlap is a bonus that very few candidates know, and volunteering it tends to end the multicast section on a high note.

Three flags in the router advertisement decide. Follow-ups to expect

What they're testingWhether you know RAs are not optional. It is a single fact and it is the one that separates people who have deployed IPv6 from people who have read the addressing chapter.
Walk through Neighbor Discovery. What replaced ARP, and what are the security implications?Deep

ND is a set of ICMPv6 messages that replaces ARP, router discovery and redirects in one protocol. Neighbor solicitation and advertisement do address resolution using solicited-node multicast rather than broadcast; router solicitation and advertisement handle gateway and prefix discovery. Because it runs over ICMPv6 and is unauthenticated, any host on the link can impersonate the router or any neighbour.

Solicited-node multicast is the efficiency improvement worth naming: instead of broadcasting, a host joins ff02::1:ff00:0/104 with the low 24 bits of its address appended. Where to deploy it:

  • Links where loss of light does not mean loss of path — anything crossing a carrier Ethernet service, a DWDM system, a media converter or a switch. The router's own interface stays up while the path is dead, so there is no link-down event to react to. This is the primary use case.
  • eBGP sessions to transit providers, where the 180-second hold timer is otherwise your detection time.
  • Core links where sub-second IGP convergence is a requirement.

Where not to:

  • Not aggressively alongside NSF or SSO. A supervisor switchover takes longer than a 150-millisecond BFD detection, so BFD declares the peer down during a successful, non-disruptive switchover — and the HA mechanism you deployed to avoid an outage causes one. Timers must be compatible with the switchover time, or BFD must be NSF-aware on that platform.
  • Not on sessions that are not in the forwarding path, such as route reflector peerings. There is nothing to protect.
  • Not at very short intervals without hardware offload. Software BFD at 50 milliseconds on a busy CPU produces false positives under load, which is the worst possible failure — flapping caused by the monitoring.
  • Not where the physical layer already gives you a reliable, immediate down event and millisecond detection is not worth the risk.
The false-positive trade is the real content of this questionEvery reduction in detection time increases the chance of declaring a healthy path dead. A false positive causes a reconvergence, which is more disruptive than the extra few hundred milliseconds you were trying to save. The honest position: use BFD where detection is genuinely the bottleneck, offload it, and pick the slowest timers that meet the actual requirement — not the fastest the platform supports. A candidate who says "300 by 3 with offload, and I would need a reason to go lower" sounds like they have operated it; one who reaches for 50 milliseconds does not.
What they're testingWhether you understand what BFD is for — paths that fail without a link-down event — and whether you know its interaction with SSO. That interaction has caused real outages and is a favourite follow-up.
Explain LFA, remote LFA and TI-LFA. What problem does each solve that the previous one did not?Expert

LFA precomputes a backup next hop that provably will not send the packet back, so failover needs no recomputation — but coverage depends on topology and is poor in rings. Remote LFA extends coverage by tunnelling to a node from which the destination is reachable without looping. TI-LFA uses a segment-routing SID list to steer the packet along the post-convergence path, giving complete coverage and eliminating microloops.

Detail

LFA: neighbour N is a loop-free alternate for destination D if N's cost to D is less than N's cost to me plus my cost to D. In other words, N's own shortest path to D does not go through me, so it is safe to hand it the packet with no further signalling.

MechanismCoverageNeeds
LFADirect neighbour as backup next hopTopology dependent — good in meshes, poor in ringsNothing extra

Why rings break LFA: in a ring, the only alternate to your primary neighbour is the neighbour on the other side, whose shortest path to the destination runs back through you. There is no loop-free direct alternate, so coverage is zero for those destinations — and rings are extremely common in metro and access networks, which is exactly why remote LFA was needed.

The microloop point, which is TI-LFA's real advantage: during convergence routers update at different moments. A router that has converged forwards to a neighbour that has not, which sends the packet back — a transient loop lasting tens or hundreds of milliseconds, long enough to drop traffic and reorder flows. LFA and rLFA repair paths are not the same as the eventual post-convergence path, so traffic moves twice: onto the repair path, then onto the final path, with a microloop opportunity in between. TI-LFA's repair path is the post-convergence path, so traffic moves once and there is nothing to loop.

Distinguish SSO, NSF, graceful restart and NSR.Deep

SSO is hardware redundancy — a standby supervisor with synchronised state takes over. NSF is the forwarding behaviour during that event: keep using the existing FIB while the control plane recovers. Graceful restart is the protocol extension by which neighbours agree to help, holding routes during the grace period. NSR replicates the protocol state itself, so no neighbour cooperation is needed at all.

Why stage 6 dominates and why it changes the answer: with a full internet table, failover that requires rewriting the next hop for every affected prefix takes time proportional to the prefix count. Hundreds of thousands of hardware writes is seconds, not milliseconds, and no amount of timer tuning touches it. The fix is architectural: make failover change a shared structure that many prefixes point at, rather than each prefix individually. That is precisely what prefix-independent convergence means — one indirection update covers every prefix behind it.

Which reframes the whole question: the goal is not to converge faster but to avoid needing to converge. FRR, TI-LFA and BGP PIC all precompute the alternate and install it, so the failure event becomes a local switch to an already-programmed path. Reconvergence then happens in the background, at whatever speed, with traffic already restored.

Why is routing over a vPC a problem, and what is layer3 peer-router for?Expert

Because of the vPC loop-prevention rule: a frame received on the peer-link is never forwarded out a vPC member port. A routed packet that arrives at the wrong vPC peer and needs to reach a device attached by vPC would have to cross the peer-link and then egress a member port — which the rule forbids, so it is dropped. layer3 peer-router relaxes that specifically for routed traffic, which is what makes a dynamic routing adjacency over a vPC workable.

Detail

The rule exists for a good reason. For bridged traffic, the peer that received a frame from the fabric has already delivered it to the dual-attached device locally, so forwarding the peer-link copy out a member port would duplicate it. For routed traffic that reasoning does not hold — the packet may legitimately need to traverse the peer-link to reach its next hop — but the ASIC rule does not distinguish, so the packet is discarded.

12Overlays & SR

Every modern overlay is the same idea — separate identity from location and distribute the mapping with a control plane. Showing that you see the pattern across VXLAN EVPN, LISP, SD-WAN and segment routing is worth more than deep recall of any single one.

Explain VXLAN EVPN. What are the main route types and what does each carry?Deep

VXLAN is the data plane — a 24-bit VNI in a UDP header on port 4789, encapsulating the original frame between VTEPs. EVPN is the control plane: an MP-BGP address family that distributes MAC and IP reachability so the fabric does not have to learn by flooding. The combination gives you layer 2 and layer 3 overlay with no unknown-unicast flooding.

Why did VXLAN move from flood-and-learn to EVPN? Explain the distributed anycast gateway and symmetric IRB.Deep

Flood-and-learn has no control plane, so every unknown destination and every ARP floods across the entire fabric, host moves are learned only by re-flooding, and there is no way to coordinate multihoming. EVPN replaces data-plane learning with BGP advertisement, which removes the flooding, enables ARP suppression, handles mobility explicitly with sequence numbers, and makes multihoming possible.

All three separate identity from location and use a control plane to distribute the mapping. LISP uses a pull model with map-servers answering queries; SD-WAN uses OMP to push routes and transport locators from a controller; EVPN uses MP-BGP to push MAC and IP reachability. The difference is push versus pull and who holds the authoritative mapping.

Compare SR-MPLS and SRv6. What does SRv6 enable, and what does it cost?Expert

Both use source routing with a list of segments. SR-MPLS encodes segments as 4-byte MPLS labels and needs an MPLS data plane; SRv6 encodes them as full 128-bit IPv6 addresses in a segment routing header, so it needs only native IPv6 forwarding. SRv6 buys you a single data plane and network programmability; it costs header overhead and requires hardware that can process the SRH.

Network programming is the real argument for SRv6. Because a SID is structured — a locator identifying the node plus a function identifying what that node should do — the packet header can express an instruction, not just a path. End.DT4 means "decapsulate and look up in this IPv4 VRF"; End.X means "forward out this specific adjacency". That is why compressed SID schemes — uSID and similar — exist: they pack several short identifiers into one 128-bit address so a multi-segment path fits in a single SID. 13Methodology

For senior and escalation roles these matter more than any protocol question. The interviewer is deciding whether they would hand you a live P1, and what they are listening for is a repeatable method rather than a list of causes.

You are handed a problem on a technology you have never worked with. Walk me through your approach.Core

Establish the facts before the theory: what changed, what exactly is broken, and what still works. Then bisect the path rather than guessing at causes, and compare the broken case against a working one. Unfamiliarity with the technology changes how long each step takes, not the steps.

Detail
  1. Define the failure precisely. "The application is slow" is not a problem statement. Which source, which destination, which port, since when, for everyone or some, all the time or intermittently. Most of the diagnosis is in getting this right.
  2. Find what changed. Change records, config diffs, software upgrades, certificate expiries, a provider's maintenance window. The overwhelming majority of incidents have a change behind them, and the ones that do not usually have a capacity threshold instead.
  3. Establish what works. A working comparison case is the most powerful tool available — another site, another VLAN, another user, the same flow yesterday. The difference between working and broken is a much smaller search space than the whole system.
  4. Bisect the path. Test the midpoint, not the ends. Each test halves the remaining search space, so a ten-hop path takes three or four tests rather than ten.
  5. Work the layers, in the direction the evidence points. Physical and interface counters first if there is any hint of a physical problem, because they are cheap to check and definitive. Otherwise start where the symptom lives.
  6. Change one thing at a time, and record it. Two simultaneous changes mean you cannot attribute the result, and in an incident you will not remember.
  7. For unfamiliar technology, read the state before the documentation. show output tells you what the box believes. Then find the document that explains what it should believe. Reversing that order means reading a lot of material you did not need.
Say the bisection principle explicitly"I test the middle of the path, not the ends, because each test halves the search space." It is a short sentence that tells the interviewer you have a method rather than a habit. Then add the honest bit about unfamiliar technology: you are slower per step, so you lean harder on the working comparison and on bisection, because those work without domain knowledge.
Follow-ups to expect
  • "What if there is no working comparison?" — create one. Build a minimal test case: a second VLAN, a loopback-to-loopback ping, a test VRF. Manufacturing the control case is often faster than reasoning without one.
  • "What if nothing changed?" — then look for something that crossed a threshold: a table filling, a licence or certificate expiring, a counter wrapping, a lease pool exhausting, traffic growth meeting a policer. "Nothing changed" usually means nothing changed in configuration.
What they're testingWhether you are systematic under pressure. Candidates who list protocols they would check are pattern-matching; candidates who describe narrowing the problem space are troubleshooting. For an escalation role this is frequently the single most important answer in the interview.
How do you decide when to stop investigating and escalate, or involve a vendor?Deep

Escalate on evidence, not on frustration. The trigger is reaching the boundary of what you can observe or change — a suspected software defect, a hardware fault, something inside a provider's network — or hitting a time box you set at the start against the business impact. Escalating with a tight problem statement and the state already collected is the skill; escalating because you are stuck is not.

Detail

Four conditions that justify escalation:

  • You have reached the observability boundary. The evidence points inside a black box — vendor software, another organisation's network, a hardware component you cannot interrogate.
  • The evidence points at a defect. State that is internally inconsistent: RIB and FIB disagree with no resource explanation, a counter that cannot be what it says, a process behaving against documented behaviour. That is a vendor case, and continuing alone wastes the outage.
  • The time box has expired. Set one up front, scaled to impact. For a P1, parallelise immediately — open the vendor case while you keep working, because the case queue time is the long pole and it costs nothing to start it early.
  • Someone else can act faster. If a different team owns the component, handing it over with good evidence beats learning their system during an incident.

What a good escalation contains — and this is the part interviewers actually probe:

  1. A one-sentence problem statement with scope and start time.
  2. The working comparison case, which is often the most useful thing you can hand over.
  3. What you have ruled out, with the evidence that ruled it out. Not "it is not routing" but "RIB and FIB agree and packet-trace shows the drop at the output ACL".
  4. The state already collected: configurations, relevant show output, a capture, logs with timestamps.
  5. Your current hypothesis, labelled as a hypothesis.
  6. Business impact and what you need from them.
Collect the volatile state before you change anythingReloading a device or clearing a process destroys the evidence that would have identified the cause, and you have then committed to the same outage happening again. Before any disruptive action: capture the counters, the logs, the relevant show tech or targeted output, and in a crash case the core file or traceback. The discipline of preserving state before restoring service — and knowing when impact is severe enough to skip it — is exactly what an escalation role is for, and saying this unprompted lands very well.
Follow-ups to expect
  • "What if the vendor says it is a configuration problem and you disagree?" — narrow it to a reproducible minimal case. A two-router lab reproduction with twelve lines of configuration ends that argument immediately, and is worth the effort for anything recurring.
  • "How do you handle pressure to just reload it?" — sometimes reloading is right, and say so plainly. Restore service, then make sure the state was captured first so the incident is not repeated next month. Being dogmatic about evidence over service restoration is the wrong answer; being deliberate about the order is the right one.
What they're testingFor an escalation role, directly: judgement about when to hold and when to hand off, and whether your handoffs are useful. Anyone can escalate. Escalating with a problem statement, a control case, evidence-backed exclusions and preserved state is what makes someone senior.
"Tell me about the hardest network problem you have solved." How should you structure that?Core

Pick a problem whose difficulty was diagnostic, not operational — something where the cause was genuinely hidden rather than something that was merely stressful or long. Then structure it as impact, what made it hard, the step that broke it open, the fix, and what you changed afterwards so it could not recur.

Detail

Choose the story for what it demonstrates. The strongest ones share a shape: the obvious explanation was wrong, the evidence was misleading, and a specific insight or measurement resolved it. Avoid stories whose answer is "it was a hardware fault and we replaced it" — there is nothing to show.

A structure that works, in about three minutes:

  1. Impact in one sentence. What was broken, for whom, how badly. This frames why it mattered.
  2. Why it was hard. Name the misleading evidence. "Every capture was clean" or "the symptom only appeared on one of four identical switches" or "it recovered before anyone could look".
  3. What you ruled out and how. Briefly — this is where you show method, not thoroughness.
  4. The turn. The one observation or test that broke it open. Every good debugging story has exactly one, and this is the part the interviewer remembers.
  5. The fix, and the real root cause. Distinguish them if they differ.
  6. What changed afterwards. Monitoring, a standard, a template, a check added to a build process. This is the senior marker: you did not just fix it, you made the class of problem less likely.
Have three stories ready, deliberately differentOne where the cause was a protocol subtlety, one where it was a platform or hardware behaviour, and one where it was organisational — a change nobody recorded, a misunderstanding between teams, a monitoring gap that let it run for weeks. Interviewers often ask for a second example, and reaching for the same kind of story twice makes a deep specialism look like a narrow one. Rehearse the structure rather than the words, so it stays conversational.
Follow-ups to expect
  • "What would you do differently?" — have a real answer. "I spent two hours on the capture before checking the policer counters, because I assumed the problem was on the wire." A specific, small, honest regret is far more credible than "nothing" and shows you reflect on your own method.
  • "What did you change so it would not happen again?" — if the answer is nothing, pick a different story. The prevention step is most of what makes the story worth telling.
What they're testingWhether you can communicate technical work to someone who was not there — which, at senior level, is most of the job. The content proves you can do the work; the structure proves you can hand it over, write the post-incident review and explain it to a director.

Reference topology · AS 65001, four protocol domains, one redistribution boundary.

Four domains with deliberate boundaries. eBGP at the edge taking defaults only; OSPF as the IGP with area 0 in the core and the campus in its own area, summarised at the ABR; iBGP carried through the core with the cores as route reflectors; and two further domains — an eBGP-underlay VXLAN fabric and an MPLS L3VPN — attached through border devices rather than merged into the IGP.

Trace a packet from a branch user at 10.20.5.50 to a public web service. Name every lookup.Deep

Six lookups and two label operations. The branch CE routes on its default toward the PE; the PE imposes a VPN label and a transport label; the core switches the transport label only; the WAN PE pops into the global table at the edge; the edge router routes on its default toward the ISP and translates the source; and the ISP routes it onward.

The path
  1. Branch CE. Destination is not in the branch's EIGRP table, so it follows the default route learned from the PE and forwards to the PE across the access circuit.
  2. WAN PE, ingress. Looks the destination up in the branch's VRF table. Finds a default pointing out of the VRF — which requires a deliberate leak or a per-VRF default toward the internet edge. Imposes the VPN label for the egress and the transport label for the next PE or the border.
  3. Core. Swaps the outer transport label only. Holds no branch routes and never sees the VPN label — which is why 200 branches cost the core nothing.
  4. Exit from the VPN. At the egress point the labels are popped and the packet is in the global table, now routed by the OSPF and iBGP state in the core.
  5. Core routing. The destination is covered by the default route learned via iBGP from the edge routers, with the next hop resolved by OSPF to an edge loopback. Two equal paths means an ECMP hash picks EDGE-1 or EDGE-2.
  6. Edge router. Routes on its own eBGP default toward the ISP, and translates the source address from 10.20.5.50 to something in 203.0.113.0/24. The connection state for the return path lives here.
  7. ISP. Routes it onward. Return traffic arrives at the public address, is un-translated, and follows the reverse path — which must come back through the same edge router, because that is where the translation state is.
The return path is the interesting half, and it constrains the designBecause NAT state lives on the edge router that created it, return traffic must arrive at that same router. With two edge routers and two ISPs, inbound traffic to 203.0.113.0/24 could arrive at either — and if it arrives at the wrong one, there is no translation entry and the packet is dropped. The resolutions are: advertise the public range such that it is reliably drawn to one edge, use a shared translation pool with state synchronisation if the platform supports it, or terminate NAT on a stateful pair that shares its table. Volunteering this unprompted is the strongest thing you can say about this topology, because it is the real design problem hiding behind a simple-looking diagram.

EDGE-1 loses power. Walk through what happens, in order, with timings.Expert

Open-ended design and diagnosis questions, where there is no single right answer and the interviewer is watching how you reason. Say your assumptions out loud, ask about constraints, and state trade-offs rather than picking silently.

Design a dual-homed internet edge with two providers. Talk me through it.Deep

Start by asking what the requirement actually is — resilience only, or active-active load sharing, and whether you own address space and an AS number. Those answers change the design completely, and asking is part of the answer.

Questions to ask first
  • Do you have your own AS number and provider-independent address space? Without both, BGP multihoming is not available and the design is NAT-based failover instead.
  • Resilience only, or do both links need to carry traffic?
  • One edge router or two? A single router is a single failure domain regardless of how many providers terminate on it.
  • Do you need full tables, default only, or partial? This drives the hardware.
  • What is the failover expectation — seconds, or does it need to be sub-second?
The design
  • Two edge routers, one provider each, iBGP between them. Otherwise router failure takes out both providers.
  • Default routes from each provider, not full tables, unless there is a specific reason. A default plus the provider's own customer routes gives you most of the path-selection benefit at a fraction of the memory and convergence cost. Take full tables only if you genuinely do best-path selection against them.
  • Outbound policy with local preference. This is yours and it works absolutely. Prefer provider A for everything, or split by destination using the providers' own routes.
  • Inbound influence — and be honest that it is influence. Advertise your aggregate to both, use each provider's published communities to request a lower preference on the backup, and keep AS-path prepending as a secondary measure. Expect inbound to be imperfect.
  • iBGP with next-hop-self, peering from loopbacks, with the IGP carrying the loopbacks.
  • BFD on the eBGP sessions, because an Ethernet handoff to a provider will not go down when their far-end router fails.
  • Prefix limits and inbound filtering on every eBGP session — maximum-prefix with a threshold, and a sanity prefix list rejecting anything shorter than /8 or longer than /24 and your own space.
  • Outbound filtering that advertises only your own aggregate. Use ^$ on the AS path. This is how you avoid becoming a transit provider by accident, which is the most common and most embarrassing multihoming failure.

A campus has 400 switches across 12 buildings. Design the routing. How many OSPF areas, and where do you summarize?Deep

Area boundaries should follow the addressing plan, and the addressing plan should follow the physical topology — so each building gets a contiguous block and becomes an area, summarized at its distribution layer into area 0. If the addressing does not allow contiguous summarization, fix the addressing first, because areas without summarization deliver only a fraction of the benefit.

The design
  • Area 0 is the core — the collapsed core or core pair, plus the links to each distribution block.
  • One area per building, bounded at the distribution layer. The distribution pair are the ABRs.
  • A contiguous address block per building, sized with headroom, so one area range summarizes the whole building.
  • Totally stubby areas for buildings that contain no ASBR and need no external detail. They receive a default route and nothing else, which minimises both LSDB size and the work a distribution switch has to do.
  • Routed access, or layer 2 access with SVIs at distribution — and the choice matters more than the area design. Routed access removes spanning tree and FHRP from the access layer and shrinks the failure domain to a single switch.
  • Loopbacks for router IDs, advertised, with a documented numbering scheme.
Why this shape

The argument to state is the one from the OSPF section: a flapping link generates type 1 and type 2 churn and a full SPF within its own area only. Other areas see a type 3 change and run a partial calculation. With summarization at the ABR, if the flapping prefix is inside the summarized range, the type 3 does not even change — other areas compute nothing at all. Areas bound the blast radius; summarization removes it.

Inbound traffic is arriving almost entirely over your backup link. You have tried prepending and it did not help. What now?Expert

Prepending failed because AS_PATH is step 4 of best-path selection and the provider has already decided at step 2 with local preference — typically because one path comes from a customer and the other from a peer or transit. The options, in order of reliability: the provider's published communities, then selective more-specific advertisement, then conditional advertisement, then a conversation with the provider.

Why prepending failed

Say this first, because it demonstrates you understand the mechanism rather than the recipe. If the distant AS sets local preference on ingress based on the relationship — customer routes highest, then peers, then transit — the decision is made two steps before AS_PATH is ever examined. You can prepend twenty times and change nothing. That is not a misconfiguration; it is how essentially every provider's policy works.

What to try, in order
  1. The provider's communities. Most transit providers publish a community set that lets a customer request a lower local preference on specific prefixes, or request prepending toward their own peers. This acts at step 2, which is the step that matters. It is by far the most effective mechanism and it is the first thing to ask for.
  2. Selective more-specifics. Advertise the aggregate out both links and a more specific out the preferred one. Longest match beats all policy on every router in the path, so this works. Costs: extra global table entries, some providers filter longer prefixes, and you must still advertise the aggregate everywhere or you create a hole when the specific is withdrawn.
  3. Conditional advertisement. Advertise the backup path only when the primary disappears, using advertise-map with non-exist-map. Genuinely active-standby rather than an attempt at weighting, and the failover is slower because it depends on the condition being detected.
  4. MED, where both links go to the same provider. Then MED is comparable and is the right tool. Across different providers it is almost useless.
  5. Talk to them. For a significant customer, a provider will often apply a static local-preference policy on request. Unglamorous and frequently the fastest route to the outcome.

One prefix is unreachable from one region, intermittently, and everything else is fine. Where do you start?Expert

The specificity is the evidence. One prefix means the problem is per-prefix state rather than a link or a device. One region means the divergence is somewhere between that region and the rest. Intermittent means either something is flapping or two paths exist and one of them is broken — and the second is far more common than the first.

Reading the three constraints
ConstraintWhat it rules inWhat it rules out
One prefixPer-prefix state: a route, a FIB entry, an ACL line, a specific policy clause, a hardware entryLink failures, device failures, anything that would affect everything
One regionA divergence point — where that region's view differs from everyone else'sA problem at the destination itself
IntermittentTwo paths, one broken, selected per flow by ECMP hash — or a genuine flapA static misconfiguration affecting all traffic equally

The ECMP hypothesis deserves to be stated first, because "intermittent" misleads people into looking for something changing over time. If two paths exist and one black-holes the prefix, then which path a flow takes depends on the hash of its five-tuple — so the same source gets a consistent result, a different source port fails, and the aggregate looks random. Nothing is actually flapping.

The investigation
  1. Establish the pattern precisely. Is it per-flow consistent? Test from one host with several source ports. If some ports always work and others always fail, it is a hash-selected path, and that single test has solved most of the problem.
  2. Compare control plane views. show ip bgp <prefix> or show ip route <prefix> in the affected region and in a working one. Different next hops, different path counts, or present-versus-absent all point straight at the divergence.
  3. Walk the path from the divergence point. Use show ip cef exact-route with a failing five-tuple and a working one to get the two actual paths, then follow the failing one hop by hop.
  4. At the hop where it breaks, compare RIB against FIB and check for a hardware programming or resource problem. A prefix correct in software and absent or wrong in hardware is a classic single-prefix failure, and TCAM exhaustion is the usual reason.
  5. Check per-prefix policy. A route map clause, a single prefix-list line, a community-based policy, an RPKI invalid state — anything that could treat this prefix differently from its neighbours.
  6. Check for a more specific route somewhere in the region. A leaked or stale /32 or /25 covering part of the prefix wins on longest match and sends a subset of traffic somewhere wrong, which again produces an apparently intermittent result.
