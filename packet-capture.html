01Choosing the tool

Every tool taps the packet path at a different point, and that point decides what you can and cannot see. Pick the wrong one and you get an empty buffer with no error — the single most common way capture work goes wrong.

Tap points · the row a tool sits on determines whether transit traffic is visible to it at all.

Three questions before you capture anything

  1. Is the traffic even reaching this box? Check interface counters first. A capture that returns nothing and a link that is counting zero input packets are the same finding, and the counter takes two seconds.
  2. Which direction, and at which point? Ingress on the switch nearest the source answers "did the client send it". Egress on the switch nearest the destination answers "did we deliver it". Capturing in the middle answers neither cleanly.
  3. What does this cost the box? SPAN is almost free — done in the ASIC. EPC, Ethanalyzer and anything punt-based costs CPU. On a production core switch at 60% CPU, an unfiltered capture is a self-inflicted outage.
Capture at the edges, reason about the middleTwo captures — ingress at the first hop and egress at the last — bound the problem to a segment. Then move inward. Starting in the middle of a path means every result is ambiguous: you cannot tell whether the packet never arrived or arrived and was dropped.

Control plane versus data plane, and why it matters most

The distinction decides which tools can possibly work:

  • Data plane / transit — switched or routed in the ASIC without the CPU ever seeing it. Normal user traffic. Visible to SPAN and ELAM. Invisible to Ethanalyzer.
  • Control plane — destined to or sourced from the box: routing protocol adjacencies, ARP, CDP/LLDP, STP, SSH to the management IP, SNMP, DHCP relay. Punted to the CPU. Visible to EPC with control-plane, Ethanalyzer, and tcpdump on the mgmt interface.
  • Punted exceptions — data-plane traffic that needs CPU help: TTL expiry, options, fragmentation, glean/unresolved adjacency, ACL log. Shows up in punt counters, which is how you catch the CPU spike nobody can explain.
The Ethanalyzer trapEngineers run ethanalyzer local interface inband expecting to see user traffic through a Nexus, see nothing, and conclude the traffic is not arriving. Ethanalyzer taps the supervisor inband channel — it only ever sees packets the box itself sends or receives. Transit traffic on a Nexus needs SPAN, ERSPAN or ELAM. Nothing about the empty output tells you this.

02IOS-XE Embedded Packet Capture

EPC — the monitor capture family — is the single most useful tool on any IOS-XE box. It captures into an on-box buffer or straight to flash, decodes in the CLI, and exports a real pcap. No SPAN destination port, no second device, no cabling.

The five-step shape, every time

Every EPC session is the same five moves. Learn the shape and the syntax follows.

! 1 — where to tap (attachment point)
monitor capture CAP interface GigabitEthernet1/0/1 both

! 2 — what to keep (filter) — mandatory, capture will not start without one
monitor capture CAP match ipv4 host 10.1.1.10 host 10.2.2.20

! 3 — how much (buffer and limits)
monitor capture CAP buffer size 10 circular
monitor capture CAP limit duration 60 packet-len 128

! 4 — run it
monitor capture CAP start
   ... reproduce the problem ...
monitor capture CAP stop

! 5 — look at it, then clean up
show monitor capture CAP buffer brief
monitor capture CAP export flash:cap.pcap
no monitor capture CAP
A capture point with no filter will not startEPC refuses to start without a filter — you get Filter not attached to capture or similar. This is deliberate: an unfiltered capture on a busy box punts everything to the CPU. If you genuinely want everything, you must say so explicitly with match any, and you should know why before you do.

Attachment points are additive. One capture point can hold several, which is how you watch a flow enter one port and leave another in a single buffer with consistent timestamps.

monitor capture CAP interface Gi1/0/1 both
monitor capture CAP interface Gi1/0/24 both
monitor capture CAP match ipv4 any any
monitor capture CAP start
control-plane is the one people forgetWhen the box itself is the problem — an OSPF adjacency that will not form, DHCP relay that is not relaying, RADIUS that times out — control-plane both shows you exactly what the CPU received and what it sent. It is usually faster than any amount of protocol debugging, and it proves whether a reply ever arrived.

Circular plus "it happened an hour ago" loses the evidenceA circular buffer keeps the most recent packets. If the event you care about is the moment a session broke and traffic kept flowing afterwards, the interesting packets are overwritten by the boring ones that followed. For a one-shot event use linear (buffer size with no circular) so capture stops at the event and preserves it, or add limit packets.

Limits — the safety rails

monitor capture CAP limit duration 60          ! stop after 60 seconds
monitor capture CAP limit packets 500          ! stop after 500 packets
monitor capture CAP limit packet-len 128       ! slice: headers only, 128 bytes
monitor capture CAP limit pps 100              ! rate cap, protects the CPU
monitor capture CAP limit every 5              ! sample every 5th packet

! combine them on one line
monitor capture CAP limit duration 120 packets 1000 packet-len 160
  • packet-len is the one to reach for first. Headers are where the answers are. 128–160 bytes gives you Ethernet, IP, TCP/UDP and the start of the payload, at a fraction of the buffer and CPU cost.
  • duration is cheap insurance against walking away from a running capture. Always set it.
  • pps matters on a box you cannot afford to load. Combined with a tight match it makes EPC safe on production.
Always set a duration, even when you plan to stop it manuallyCaptures get forgotten. A forgotten capture on a core switch is a CPU leak that nobody associates with the change you made three weeks ago. limit duration makes it self-terminating. Pair it with no monitor capture when done — stop alone leaves the capture point configured.

Cleaning up properly

monitor capture CAP stop        ! stops capturing, config remains
monitor capture CAP clear       ! empties the buffer, config remains
no monitor capture CAP          ! removes the capture point entirely

show monitor capture            ! confirm nothing is left running
delete /force flash:cap.pcap

EPC configuration is not saved to startup-config, so a reload clears it — but a box that is not reloaded for a year will happily run a forgotten capture for a year. Make show monitor capture part of your exit check.

03EPC filters and ACLs

The filter is where captures are won or lost. A loose filter floods the buffer and the CPU; a filter that covers only one direction produces a capture that looks like a one-way conversation and sends you chasing a problem that does not exist.

Inline match syntax

! everything — know why before you do this
monitor capture CAP match any

! IPv4 by address: host, prefix or any
monitor capture CAP match ipv4 any any
monitor capture CAP match ipv4 host 10.1.1.10 any
monitor capture CAP match ipv4 host 10.1.1.10 host 10.2.2.20
monitor capture CAP match ipv4 10.1.1.0/24 10.2.2.0/24

! by protocol and port
monitor capture CAP match ipv4 protocol tcp any any
monitor capture CAP match ipv4 protocol tcp host 10.1.1.10 any eq 443
monitor capture CAP match ipv4 protocol udp any eq 67 any eq 68
monitor capture CAP match ipv4 protocol icmp host 10.1.1.10 host 10.2.2.20
monitor capture CAP match ipv4 protocol 89 any any      ! OSPF

! IPv6
monitor capture CAP match ipv6 any any
monitor capture CAP match ipv6 host 2001:db8::10 any
monitor capture CAP match ipv6 protocol tcp any any eq 443

! Layer 2 — src mac, src mask, dst mac, dst mask
monitor capture CAP match mac 0011.2233.4455 0000.0000.0000 any any
A second match command replaces the first, it does not add to itInline match holds one expression. Entering a second one silently overwrites it, so a session built up over several lines captures only whatever you typed last. For anything with more than one clause, use an ACL. Verify what is actually attached with show monitor capture CAP parameter, not with what you think you typed.

ACL-based filters — the real answer

An ACL gives you multiple clauses, both directions, and a hit counter that tells you whether the filter is even matching.

ip access-list extended CAP-FILTER
 ! BOTH directions — this is the part people miss
 permit tcp host 10.1.1.10 host 10.2.2.20 eq 443
 permit tcp host 10.2.2.20 eq 443 host 10.1.1.10
 ! and the control traffic that explains failures
 permit icmp host 10.2.2.20 host 10.1.1.10
!
monitor capture CAP interface Gi1/0/1 both
monitor capture CAP access-list CAP-FILTER
monitor capture CAP buffer size 10
monitor capture CAP limit duration 120 packet-len 160
monitor capture CAP start

! is the filter matching at all?
show ip access-lists CAP-FILTER
The ACL hit counter is a free sanity checkEmpty capture plus zero ACL hits means your filter is wrong or the traffic is not on that interface. Empty capture plus non-zero ACL hits means the filter matched but the capture is not storing — look at rate limits, buffer state and platform restrictions instead. That one command splits the problem in half.
! a reusable symmetric filter for one host pair
ip access-list extended CAP-PAIR
 permit ip host 10.1.1.10 host 10.2.2.20
 permit ip host 10.2.2.20 host 10.1.1.10

! one host, everything it touches
ip access-list extended CAP-HOST
 permit ip host 10.1.1.10 any
 permit ip any host 10.1.1.10

Verifying the filter before you trust the result

show monitor capture CAP parameter

   monitor capture CAP interface GigabitEthernet1/0/1 BOTH
   monitor capture CAP access-list CAP-FILTER
   monitor capture CAP buffer size 10
   monitor capture CAP limit pps 1000

!   Status : Active
!   Packets received / dropped — the dropped counter is the one to read

Three things to read before concluding anything from a capture: the attachment point is the interface you meant, the direction is the one you meant, and the drop counter is zero. A non-zero drop counter means you are looking at a sample, and absence of a packet proves nothing.

04Catalyst 9000 behaviour

On a Catalyst 9000 the ASIC forwards in hardware and the CPU never sees transit traffic. EPC works by making the ASIC punt a copy of matched packets to the CPU — which is why it is rate-limited, why the drop counter matters, and why a busy flow gives you a sample rather than a conversation.

What EPC actually does on UADP

Attaching a capture point programs a filter into the ASIC. Matched packets are replicated onto a CPU punt queue, policed on the way, and handed to FED and then to the capture process. The original packet is forwarded normally — capture does not change forwarding.

The consequences are worth internalising:

  • It is lossy by design. The punt path is policed. A 1 Gbps flow will not land in your buffer in full, and nothing in the capture output says so except the drop counter.
  • Absence is not evidence. If packets were policed away, "the packet is missing from the capture" and "the packet never arrived" look identical.
  • It costs CPU. A loose filter on a busy port is a genuine risk on a box already under load.
! did the capture drop anything?
show monitor capture CAP
!   Packets received : 1842
!   Packets dropped  : 29571     ← you have a sample, not a capture

! what the punt path is doing overall
show platform software fed switch active punt cause summary
show platform software fed switch active punt cpuq all

! CPU policer — are legitimate punts being starved?
show platform hardware fed switch active qos queue stats internal cpu policer
Never conclude "the packet was dropped by the network" from an EPC gapWith a non-zero capture drop counter, a missing packet tells you nothing. Tighten the filter until drops are zero, re-run, and only then treat absence as meaningful. On a high-rate flow, add limit packet-len 128 and a narrow ACL — or stop using EPC and SPAN it to a host.

05Classic IOS platforms

Plenty of production networks still run boxes that have never heard of monitor capture. Classic IOS has an entirely different EPC syntax, the older access switches have SPAN and nothing else, and the 6500 and 4500 each have their own CPU-side capture tooling.

Classic IOS EPC — the three-part form

On IOS 15.x routers (ISR G2 1900/2900/3900, older 7200/ASR with classic IOS) EPC is built from separate objects: a buffer, a capture point, and an association between them.

! 1 — the buffer
monitor capture buffer BUF size 2048 max-size 1518 circular

! 2 — the capture point: switching path matters here
monitor capture point ip cef POINT GigabitEthernet0/0 both
!   ip cef               — CEF/hardware-switched packets
!   ip process-switched  — packets punted to the CPU
!   ipv6 cef / ipv6 process-switched

! 3 — tie them together
monitor capture point associate POINT BUF

! 4 — optional filter
monitor capture buffer BUF filter access-list CAP-ACL

! 5 — run
monitor capture point start POINT
monitor capture point stop POINT

! 6 — read and export
show monitor capture buffer BUF dump
show monitor capture buffer all parameters
show monitor capture point all
monitor capture buffer BUF export tftp://10.100.1.50/cap.pcap

! 7 — remove
no monitor capture point ip cef POINT GigabitEthernet0/0 both
no monitor capture buffer BUF
ip cef and ip process-switched are different capturesThis is the classic-IOS trap with no modern equivalent. A capture point of type ip cef will not show you a packet that was punted to the CPU, and ip process-switched will not show you a CEF-switched one. When you are investigating why traffic is being process-switched — the usual reason for a CPU spike on an ISR — you need the process-switched point, and the CEF point will look empty and mislead you completely.

Older access switches — SPAN and nothing else

Catalyst 2960, 2960-X, 3560, 3560-X, 3750 and 3750-X running classic IOS have no packet capture at all. SPAN to a host is the only option.

monitor session 1 source interface FastEthernet0/1 both
monitor session 1 destination interface FastEthernet0/24
show monitor session 1
show monitor session all
no monitor session 1
  • Two local SPAN sessions is the limit on these platforms.
  • No ERSPAN. RSPAN works if you have an end-to-end layer 2 path.
  • No CPU capture, so control-plane problems on these boxes are debugged with protocol debugs and counters, not captures.
The 3650 and 3850 are the dividing lineThose two were the first IOS-XE Catalyst switches, so they do have monitor capture — unlike the 3750-X that sits next to them in many wiring closets and looks like a peer. If you are unsure which side of the line a switch is on, show version and look for IOS-XE, or just try monitor capture ?.

06Local SPAN

SPAN is done in the ASIC, so it is close to free and it sees real transit traffic at real rates — the two things EPC cannot promise. The cost is that you need somewhere to send it, and the destination port becomes a dedicated, half-dead port while the session exists.

SPAN family · the replication is identical; the transport is what you are choosing between.

Direction, and why both can double your packets

KeywordCopiesUse when
rxFrames the switch receives on the port"Did the host actually send it?"
txFrames the switch transmits — after rewrite, ACL and QoS"Did we deliver it, and what did it look like?"
bothBoth of the aboveDefault. Most troubleshooting

tx is the direction that shows you what the switch did to the frame — the rewritten MAC addresses, the decremented TTL, the remarked DSCP, the VLAN tag as it goes out. rx shows you the frame as it arrived, before any of that.

Two source ports on the same path produce duplicatesIf a flow enters Gi1/0/1 and leaves Gi1/0/2, and you SPAN both ports with both, every packet appears twice — once as rx on the ingress port, once as tx on the egress port. That looks exactly like a duplication problem in the network and has sent many engineers hunting a loop that does not exist. Either SPAN one port, or know to expect the pairs.

What the destination port becomes

  • Dedicated. It leaves normal forwarding entirely. Anything plugged in loses connectivity the moment the session is created.
  • Silent. It does not participate in STP and sends no BPDUs, so it cannot be used as an uplink while it is a SPAN destination.
  • Deaf. Traffic arriving on it is dropped, unless you add ingress vlan <n>, which lets the analyzer send as well as receive.
  • Untagged, unless told otherwise. Without encapsulation replicate the copy is sent untagged, so VLAN tags are lost — which matters a great deal if the question is about tagging.
  • Not reusable. A destination port generally cannot be a source in another session, nor a member of an EtherChannel.
encapsulation replicate whenever VLANs are part of the questionNative VLAN mismatches, voice-VLAN problems, trunk tagging arguments and QinQ all turn on the tag. Without encapsulation replicate the capture strips it and you lose the evidence silently. There is no downside to adding it other than the analyzer NIC needing to accept tagged frames.

Oversubscription — the quiet failure

SPAN has no flow control and no backpressure. If the sum of the sources exceeds the destination port's speed, the ASIC drops the excess copies. Your capture is incomplete and nothing in Wireshark announces it.

! eight 1G sources into one 1G destination = guaranteed loss under load
monitor session 1 source interface Gi1/0/1 - Gi1/0/8 both   ! up to 16 Gbps of copies
monitor session 1 destination interface Gi1/0/48            ! 1 Gbps of capacity

! fix it: narrow the source, filter VLANs, or use a faster destination
monitor session 1 filter vlan 100
show interfaces Gi1/0/48 counters
show interfaces Gi1/0/48 | include drops|output
Retransmissions and gaps that are artefacts of your own captureAn oversubscribed SPAN produces missing packets, which Wireshark reports as previous-segment-not-captured and spurious retransmissions. Engineers then report a network loss problem that exists only in the capture. Before escalating any loss finding from a SPAN capture, confirm the destination port was not saturated and that source aggregate bandwidth fits.

Rules worth knowing before you configure

  • Do not mix source ports and source VLANs in the same session — most platforms refuse it.
  • Session count is platform dependent: two local sessions on classic access switches, more on modern Catalyst. show monitor session all tells you what is in use.
  • filter vlan applies to trunk sources, not to the destination. It is the cheapest way to cut volume.
  • Whether L2 control frames — BPDU, CDP, LLDP, LACP — are copied depends on platform and on whether the source is a port or a VLAN. If you are specifically hunting one of these, prove you can see it before trusting an absence.
  • SPAN copies the frame; it does not tell you the forwarding verdict. A frame appearing in a tx capture means it was transmitted. A frame missing could mean dropped, or could mean never received.

07RSPAN

RSPAN carries the copies in a dedicated VLAN so the analyzer can sit on a different switch. It works well and it is widely supported — but it floods that VLAN across every trunk in the path, which is a design decision, not an implementation detail.

Missing remote-span on a transit switch is the number one RSPAN failureIf an intermediate switch has VLAN 999 as an ordinary VLAN, it learns MACs in it, applies normal flooding rules, and the copies either get dropped or behave unpredictably. The source and destination configuration both look perfect and the analyzer sees nothing. Walk the path and run show vlan remote-span on every hop — including the ones nobody thinks of as being "in" the capture.

Properties of an RSPAN VLAN

  • No MAC learning. That is the point — copies flood to every port in the VLAN on every switch, which is how they reach the destination session without a forwarding entry.
  • No SVI. Do not give it an IP. Do not route it.
  • No access ports. Any host in that VLAN receives every copied frame, which is both a performance problem and a security exposure.
  • Cannot be the native VLAN on the trunks carrying it.
  • Consumes trunk bandwidth on every link along the path, in both the capture direction and anywhere else the VLAN is allowed.
RSPAN is a bandwidth and security decisionCopies of production traffic flooding across trunks and reachable by anything in that VLAN is a real exposure — you are duplicating potentially sensitive traffic onto a broadcast domain. Prune VLAN 999 to exactly the trunks in the path, put nothing else in it, and remove the whole configuration when the capture is done rather than leaving it configured "for next time".

MTU, and why ERSPAN fragments

Each copy grows by roughly 50 bytes. A 1514-byte frame becomes about 1564 bytes, which does not fit a 1500-byte path.

  • Best answer: raise MTU on the path between the source and the analyzer to 1600 or more. Jumbo on the transport solves it properly.
  • Workable answer: set mtu 1464 in the session so ERSPAN truncates the copy before encapsulating. You get headers, not full payloads — usually fine, and the T bit records that it happened.
  • Bad answer: let it fragment. Fragmented GRE arrives out of order, some analyzers reassemble badly, and the capture becomes unreliable in ways that look like network problems.
! raise it on the transport path
interface Gi1/0/49
 mtu 9216
system mtu 9198

! check what you actually have end to end
show interfaces Gi1/0/49 | include MTU
ping 10.100.1.50 size 1600 df-bit
Truncating on purpose is almost always rightFor protocol troubleshooting the first 128–256 bytes carry every header you need. Setting mtu 1464 makes ERSPAN fit any normal path, removes fragmentation entirely, and cuts transport bandwidth by most of the payload. Only payload inspection — DPI, file extraction, voice media — needs the full frame.

Terminating ERSPAN on a Linux host instead

Since ERSPAN is just GRE to an IP address, you do not need a switch to terminate it. Point the session at a server and capture the GRE directly — Wireshark and tshark decode ERSPAN and show the inner frame.

! on the analyzer host
sudo tcpdump -i eth0 -nn -s 0 'ip proto gre' -w erspan.pcap
sudo tcpdump -i eth0 -nn 'ip proto gre and src 10.100.1.1'

! decode the inner frame while watching live
sudo tshark -i eth0 -f 'ip proto gre' -Y 'erspan'
sudo tshark -r erspan.pcap -Y 'ip.addr==10.1.1.10'

! separate two feeds by session id
sudo tshark -r erspan.pcap -Y 'erspan.spanid==101'
This is the escape route when the destination platform cannot terminate ERSPANIt sidesteps the whole question of ERSPAN destination support, gives you unlimited capture duration and disk instead of a switch buffer, and lets one host receive feeds from many sites separated by erspan-id. For long-running or multi-site capture it is the better design regardless of platform capability.

13Nexus Ethanalyzer

Ethanalyzer is tshark built into NX-OS, tapping the supervisor's own channels. It is excellent at what it does — control-plane traffic to and from the switch — and completely blind to transit traffic unless you deliberately mirror that traffic to the CPU.

The two interfaces, and what each sees

InterfaceSees
inbandSupervisor inband channel: routing protocols, ARP, STP, CDP/LLDP, HSRP, vPC, and anything addressed to an SVI or front-panel IP
mgmtThe mgmt0 port only: SSH, SNMP, NTP, syslog, AAA over out-of-band
front-panelA front-panel port directly — platform and release dependent, not universally available
Transit traffic is not on either of themA flow passing through the Nexus never touches the supervisor. ethanalyzer local interface inband will show you nothing, and the empty output is indistinguishable from the traffic not existing. For transit traffic you need SPAN, ERSPAN, ELAM, or the SPAN-to-CPU technique below — not Ethanalyzer on its own.

Core syntax

15Nexus ELAM

ELAM — Embedded Logic Analyzer Module — captures a single packet inside the ASIC and reports the forwarding decision: which lookups hit, what destination index was chosen, and whether it was dropped and why. It answers the question no capture can: not what the packet looked like, but what the hardware decided to do with it.

What makes it different

  • One packet. The trigger is single-shot. You arm it, the first matching packet is captured, and it disarms.
  • Non-intrusive. The packet is forwarded normally. ELAM observes the pipeline; it does not copy traffic anywhere.
  • Per-ASIC. You must arm it on the ASIC instance that the ingress port actually maps to — which is not the same as the module number.
  • Hardware truth. Where SPAN shows you a frame and says nothing about its fate, ELAM gives you the verdict and the reason.
Syntax is specific to the ASIC generation, not to NX-OSTahoe, NorthStar, LSE, Sundown, Homewood on the Nexus 9000, and Flanker, Orion and others on the Nexus 7000 each have their own command tree, trigger keywords and report format. A procedure copied from a blog for a different line card will be rejected or, worse, arm a trigger that never fires. Confirm the ASIC on your hardware before using any specific sequence — and treat ELAM as a TAC-grade tool you use with a case open, not a first resort.

Step one, always: map the port to an ASIC

show interface Ethernet1/1 hardware-mappings
show hardware internal dev-port-map
show module

The output gives you the module, the ASIC instance and the internal port for that front-panel interface. Arming ELAM on the wrong instance produces a trigger that stays armed forever while the traffic sails past on a different slice of silicon — the single most common reason an ELAM "does not work".

Nexus 9000 with a Tahoe ASIC — canonical flow

attach module 1

module-1# debug platform internal tah elam
module-1(TAH-elam)# trigger init in-select 6 out-select 0
module-1(TAH-elam-insel6)# reset
module-1(TAH-elam-insel6)# set inner ipv4 src_ip 10.1.1.10 dst_ip 10.2.2.20
module-1(TAH-elam-insel6)# start
module-1(TAH-elam-insel6)# status

!   Triggered   — captured; now read it
module-1(TAH-elam-insel6)# report

! re-arm for another packet
module-1(TAH-elam-insel6)# reset
module-1(TAH-elam-insel6)# start

! leave
module-1(TAH-elam-insel6)# end
module-1# exit
in-select — which header the trigger matches on
ValueMatchesUse for
in-select 6Outer L3 and L4 headersOrdinary routed or switched IPv4/IPv6 traffic

The keyword is inner for in-select 6 and outer for the encapsulation when using in-select 7 — which reads backwards until you internalise that "inner" refers to the packet under any tunnel, and with no tunnel present that is simply the packet.

reset before set, every timeConditions accumulate. Without a reset you can end up with a trigger carrying leftover conditions from a previous attempt, which will never match the traffic you are now interested in. reset, set, start, status — in that order, every time.

Reading the report

The exact fields depend on the ASIC, but the questions the report answers are consistent:

Look forIt tells you
Source and destination as the ASIC parsed themWhether the packet is what you think it is — and whether a tunnel is present
Ingress VLAN / BD and ingress portWhether it arrived in the VLAN you expect
L2 and L3 lookup resultsWhether the destination was resolved, and to what
Destination index / egress portWhere the hardware decided to send it
Drop flags and drop reasonWhether it was dropped in the pipeline, and by which stage

A Triggered status with a drop flag set is conclusive: the packet reached this ASIC and this box discarded it. A trigger that never fires with a correct condition on a verified ASIC instance is almost as useful — it means the packet is not arriving here at all, and the problem is upstream.

The negative result is a real result"ELAM armed correctly on the right ASIC, traffic generated, trigger never fired" proves the packet is not reaching this device on that port. That is a strong, defensible finding that moves the investigation one hop upstream, and it is often faster to establish than any capture.

Nexus 7000, in outline

The 7000 uses a different command tree, entered per ASIC by name and instance:

attach module 2
module-2# show hardware internal dev-port-map
module-2# elam asic flanker instance 0
module-2(fln-elam)# ! set ingress (dbus) and egress (rbus) conditions
module-2(fln-elam)# start
module-2(fln-elam)# status
module-2(fln-elam)# show dbus      ! what arrived
module-2(fln-elam)# show rbus      ! what the lookup decided

The ingress bus (dbus) shows the packet as received; the result bus (rbus) shows the forwarding result. The conceptual split is the valuable part — the condition syntax for each ASIC should come from documentation matching your exact line card, not from memory.

Do not improvise ELAM conditions on production hardwareMistyped triggers are usually harmless, but this is undocumented-adjacent internal tooling with real variation between line cards, and on some generations an incorrectly armed ELAM has been associated with unexpected behaviour. If you are reaching for ELAM on a production fabric, that is normally the point at which a TAC case is the right call — and TAC will walk the exact sequence for your hardware.

When ELAM is the right tool

For everything else — is the traffic present, what does it contain, is it retransmitting — SPAN or ERSPAN to a host is faster, safer and gives you a file you can keep.

The vlan keyword shifts every offset after itvlan is not a match, it is an instruction to skip four bytes for everything that follows. So tcpdump 'tcp port 80' finds nothing on tagged traffic, and tcpdump 'vlan and tcp port 80' finds it. Conversely, putting vlan in front when the traffic is untagged breaks the filter. If a filter inexplicably matches nothing, tagging is the first thing to suspect.
Quote your filtersBPF uses characters the shell wants: &, |, (, ), <, >. Single-quote the whole expression and the problem disappears. An unquoted filter that the shell mangles produces a syntax error if you are lucky and a silently different filter if you are not.

18Why the capture is empty

An empty buffer is the most common and least informative outcome in capture work, because almost every possible mistake produces exactly the same result. Work through it in order rather than guessing, and above all do not conclude the traffic is absent until you have proved the capture would have shown it.

The order to check things

  1. Is the capture actually running? show monitor capture CAP or show monitor session all. On Nexus and for ERSPAN, confirm the session is not administratively down — no shut is missing more often than anything else on this list.
  2. Is the traffic reaching the box at all? show interface <x> counters, cleared and re-read. Zero input packets settles it in two seconds and saves an hour.
  3. Can this tool see this class of traffic? Ethanalyzer on inband cannot see transit. Packet-trace does not exist on Catalyst 9000. Classic-IOS ip cef capture points cannot see process-switched packets.
  4. Is the filter right — in both directions? A one-directional ACL is the most frequent genuine filter mistake. Check hit counts: show ip access-lists.
  5. Is it the right direction and the right attachment point? show monitor capture CAP parameter echoes exactly what is attached. Read it rather than trusting what you typed.
  6. Is the traffic encapsulated? CAPWAP, VXLAN, GRE, MPLS. A filter on the inner addresses will not match the outer header, and the capture looks empty while the tunnels pour past.
  7. Is it being dropped on the way to the tool? Punt policer, CoPP, SPAN rate limiter, oversubscribed destination port. Check the drop counters.
  8. Is the filter programmed in hardware? TCAM exhaustion means the filter was accepted and never installed. show platform hardware fed switch active fwd-asic resource tcam utilization, or the Nexus equivalent.
  9. Is the traffic even taking this path? Asymmetric routing, an ECMP hash sending it over the other link, a different member of a port-channel, HSRP active on the other box. This is the answer surprisingly often.
Prove the capture works before trusting a negative resultAdd a line to the filter that matches something you can generate on demand — a ping from a known host, your own SSH session. If that appears and the traffic you care about does not, the capture is sound and the absence is real. If nothing appears at all, the capture is broken and you have learned nothing about the traffic. This one habit prevents most wrong conclusions in capture work.

19Real-world scenarios

Ten incidents where the capture itself was the hard part. In seven of them the first conclusion drawn from the capture was wrong, which is the pattern worth taking away.

EPC on a 9300 returns nothing, and the traffic is definitely there
Reported

Application team says TLS sessions to a server are failing intermittently. Network team configures a capture on the access port and gets an empty buffer. They report back that no traffic is reaching the switch and the problem is on the host.

What you see 
show monitor capture CAP
  Status : Active
  Packets received : 0
  Packets dropped  : 0

show interfaces Gi1/0/14 | include packets input
  5 minute input rate 18000 bits/sec
  482910 packets input

Half a million packets on the port and zero in the capture. The capture is running and dropping nothing.

Diagnosis 
show monitor capture CAP parameter
  monitor capture CAP interface GigabitEthernet1/0/14 BOTH
  monitor capture CAP access-list CAP-TLS

show ip access-lists CAP-TLS
Extended IP access list CAP-TLS
    10 permit tcp host 10.1.1.10 host 10.2.2.20 eq 443 (0 matches)

Zero ACL hits. The filter is not matching, so the capture never had a chance.

Root cause

The client was behind a NAT boundary and arrived with a translated source address, so host 10.1.1.10 matched nothing. A second, separate issue compounded it: the ACL only covered client-to-server, so even with the right address the return traffic would have been invisible.

Fix 
ip access-list extended CAP-TLS
 no 10
 10 permit tcp any host 10.2.2.20 eq 443
 20 permit tcp host 10.2.2.20 eq 443 any
TakeawayThe ACL hit counter is the cheapest diagnostic in capture work and nobody looks at it. Zero hits means the filter is wrong; non-zero hits with an empty buffer means something else entirely. Check it before you report that traffic is absent — and write filters in both directions as a reflex, because a half-filter produces a capture that misleads rather than one that is empty.
Ethanalyzer shows nothing for traffic crossing a Nexus
Reported

Server team reports slow transfers between two VLANs routed by a pair of Nexus 9300s. The on-call engineer runs Ethanalyzer, sees only OSPF and ARP, and escalates saying the traffic is not traversing the switch.

What you see 
ethanalyzer local interface inband limit-captured-frames 50
  ... OSPF hellos, ARP, CDP, HSRP ...
  ! nothing resembling the server traffic
Diagnosis 
show interface Ethernet1/5 counters
  ! millions of packets, both directions, rate consistent with the transfer

The traffic is plainly crossing the box. Ethanalyzer taps the supervisor inband channel — it can only ever see packets the supervisor itself sends or receives. Transit traffic never touches it.

Root cause

Wrong tool for the traffic class. Nothing about the empty output communicates this, and the control-plane packets that do appear make it look like the capture is working correctly.

Fix 
! brief SPAN-to-CPU to get an immediate look
monitor session 1
  source interface Ethernet1/5 both
  destination interface sup-eth0
  no shut
!
ethanalyzer local interface inband mirror limit-captured-frames 200 \
  limit-frame-size 256 write bootflash:span.pcap
no monitor session 1

! and ERSPAN to the analyzer for the real investigation
monitor session 10 type erspan-source
  erspan-id 101
  vrf default
  destination ip 10.100.1.50
  source interface Ethernet1/5 both
  mtu 1500
  no shut
TakeawayControl plane and data plane are captured by different tools, and the tool gives no hint when you have picked the wrong one. On a Nexus, Ethanalyzer is for traffic to and from the switch. SPAN-to-CPU bridges the gap for a quick look — but it points production traffic at the supervisor, so keep it to seconds and never leave it configured.
ERSPAN is configured correctly and the analyzer receives nothing
Reported

A new always-on monitoring feed from four leaf switches. Three work. The fourth delivers nothing, with configuration that was copy-pasted from a working one.

What you see

  session 10
  type              : erspan-source
  state             : down
  erspan-id         : 101
  destination-ip    : 10.100.1.50

The session is administratively down — no shut was omitted. Correcting that produced GRE packets leaving the switch but still nothing at the analyzer.

  no shut
!

  Request timed out
ping 10.100.1.50 vrf management
  ! 5 packets transmitted, 5 received
Root cause

Two independent faults stacked. The session was never enabled, and the analyzer was only reachable over the management VRF while the session used the default VRF. The three working switches had the analyzer reachable in the default VRF, so the copied configuration was correct for them and wrong here.

Fix

  no shut

Both faults here were invisible in a config diff against a working switch: one was an absent command and the other was correct syntax with a different meaning on this box. And when ERSPAN silently delivers nothing, prove reachability from the VRF the session will actually use — a plain ping tests the wrong table.
Capture shows heavy packet loss that does not exist
Reported

Escalation opened against the network: a SPAN capture of a database replication link shows thousands of TCP retransmissions and previous-segment-not-captured warnings. Application owner wants the "packet loss in the core" fixed.

OSPF adjacency flapping with a perfectly clean capture
Reported

An OSPF adjacency on a Nexus 9300 drops every few minutes. Captures on both ends show hellos sent and received on schedule with correct contents. Interface counters are clean. CPU is around 30%. Two teams have each proved it is not their side.

What you see

  limit-captured-frames 100 detail
  ! hellos arriving every 10s, correct area, correct netmask, correct timers

  ! all zero

  %OSPF-5-ADJCHG: ... from FULL to DOWN, Neighbor Down: Dead timer expired

   ... wait for one flap ...

    module 1 : dropped 48219 bytes
  class-map copp-system-p-class-critical
    module 1 : dropped 1824 bytes
Root cause

A misconfigured monitoring system was sweeping the management plane hard enough to saturate a CoPP class. OSPF hellos reached the ASIC, were visible in a capture taken on the wire, and were then discarded by CoPP before the supervisor processed them. The dead timer expired on packets that had demonstrably arrived.

Fix

Rate-limited the monitoring source and reviewed the CoPP profile against actual control-plane volumes. The adjacency stabilised immediately.

TakeawayA capture proves a packet reached the box. It says nothing about whether the control plane was allowed to process it. When a protocol fails and every capture is clean, the next command is a policer counter — CoPP on Nexus, punt and CPU policer counters on Catalyst. This failure mode is completely invisible to packet capture and it is far more common than its reputation suggests.

Every packet appears twice and a loop is suspected
Reported

A capture taken during a performance investigation shows every frame duplicated. A layer 2 loop is suspected and a change freeze is requested pending investigation of the spanning-tree topology.

What you see 
show monitor session 1
  source: Gi1/0/11  both
  source: Gi1/0/12  both
  destination: Gi1/0/48
tshark -r cap.pcap -nn -c 6
 1  0.000000  10.1.1.10 -> 10.2.2.20  TCP 1514
 2  0.000003  10.1.1.10 -> 10.2.2.20  TCP 1514   ← 3 microseconds later
 3  0.000189  10.2.2.20 -> 10.1.1.10  TCP 66
 4  0.000192  10.2.2.20 -> 10.1.1.10  TCP 66
Diagnosis

The duplicates are three microseconds apart — far too close for a loop, which would show a propagation delay and usually a decremented TTL. The flow enters Gi1/0/11 and leaves Gi1/0/12, and both ports were spanned with both, so each frame was copied twice: once as received on the ingress port and once as transmitted on the egress port.

Root cause

Capture artefact. There was no loop and the spanning-tree topology was correct throughout.

Fix 
monitor session 1
 no source interface Gi1/0/12
! one port, or keep both and expect the pairs
TakeawayMicrosecond-spaced duplicates with identical TTL are your own SPAN session, not the network. A real loop shows measurable delay between copies and, for routed traffic, a decrementing TTL. Check the session source list before the topology — and when you deliberately span both ends of a path through a switch, note it so the next reader of the capture is not misled.
Wireless clients associate and never get an address
Reported

On one new SSID, clients authenticate successfully and then sit without an IP address. A capture on the controller's uplink was taken filtered on the client's IP range and showed nothing, leading to a report that the clients were never requesting DHCP.

What you see

  IPv4 Address      : Unknown

Reported

A payment integration times out roughly once an hour over an ISR 4451. Thousands of transactions succeed between failures. Three previous capture attempts each ran for ten minutes and caught nothing.

A trunk tagging dispute that the capture could not settle
Reported

A voice deployment at one site has phones failing to get onto the voice VLAN. The switch team insists the access port is tagging voice traffic correctly; the voice vendor insists frames arrive untagged. A SPAN capture is produced showing untagged frames, and the vendor's position is treated as confirmed.

What you see

  destination: Gi1/0/47

21Capture checklist

What to settle before you type anything, what to verify while it runs, and what to clean up afterwards. The last of those is the one that causes incidents weeks later.

Before

  • State the question in one sentence. "Does the server reply to the client's SYN?" is a capture plan. "Look at the traffic" is not.
  • Decide which device and which direction answers that question. Capture at the edges of the suspect segment, not in the middle.
  • Confirm the traffic reaches the box: interface counters, cleared and re-read.
  • Pick the tool that can see this class of traffic — transit versus control plane, hardware-switched versus punted.
  • Write the filter in both directions, and prefer an ACL over inline match for anything with more than one clause.
  • Check what is already running: show monitor capture, show monitor session all, show platform condition.
  • Know the cost. On a loaded box, a tight filter, packet-len and a pps limit are the difference between a capture and an incident.

While it runs

  • Read the state, not the config. Sessions that start down and missing switchport monitor look identical to working ones in a config diff.
  • Watch the drop counter. A non-zero drop means you have a sample, and absence proves nothing.
  • Watch CPU: show processes cpu sorted. If it climbs, stop and tighten.
  • Check the filter is matching: ACL hit counts. Zero hits is a filter problem, not a traffic problem.
  • Confirm you can see something you generated — a ping, your own session. That proves the instrument works before you trust a negative result.

After

  • no monitor capture CAP — stop leaves the capture point configured.
  • no monitor session <n> — and give the destination port back its real configuration.
  • clear platform condition all and clear platform packet-trace configuration.
  • undebug all, and separately reset any set platform software trace level you raised — undebug does not touch those.
  • Remove RSPAN VLANs from trunks and delete the VLAN. Do not leave it "for next time".
  • Delete capture files from flash. They are large, and they contain production traffic.
  • Final sweep: show monitor capture, show monitor session all, show platform condition, show debug.
Forgotten capture state is a real cause of later incidentsA SPAN destination that was never restored, a trace level left at verbose, an RSPAN VLAN still flooding across trunks, an EPC point still punting to the CPU. Each is invisible in normal operation and each turns up months later as an unexplained problem on a box nobody has touched. The cleanup sweep takes thirty seconds and is the most valuable habit on this page.

Handing a capture to someone else

  • Say where it was taken — device, interface, direction — and what filter was applied. A capture without provenance cannot be reasoned about.
  • Say whether anything was truncated, and to what length.
  • Include capinfos output, or at least confirm the drop counter was zero.
  • If you spanned both ends of a path, say so, or the reader will find a loop that is not there.
  • Note the clock source. Correlating two captures from devices with unsynchronised clocks produces conclusions that are confidently backwards.
Provenance is part of the evidenceHalf the wrong conclusions in this page's scenarios came from a capture that was technically accurate and described imprecisely. "Ingress on Gi1/0/14, filtered to the host pair, nothing truncated, zero drops" lets the next person trust the file. A bare pcap with no context invites exactly the kind of confident mistake that costs days.
